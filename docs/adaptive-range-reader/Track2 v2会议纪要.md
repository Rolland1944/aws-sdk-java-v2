# 整理会议纪要
本次会议围绕 Parquet 文件格式的优化方案展开，确立了不改变底层数据格式的前提下，通过 SDK 采集信息生成文件级优化计划的主线，并决定将应用层方案实现交由大模型或人工处理以验证可行性。
小结
1. 数据排序与分区优化的局限性

全局排序不可行：对于流式到达的数据，只能对单批次数据进行局部排序，无法对整个表进行全局排序。
分区与排序脱离 SDK 核心：表的分区和行顺序排序属于高层概念，与底层 SDK 采集的信息关联度低，强行纳入会导致研究目标过于分散。

2. SDK 采集信息与 File Footer 的结合

字节级访问追踪：SDK 能够采集底层字节在时间流上的共同访问情况，但过于底层难以直接用于优化决策。
引入 Format 层解析：通过引入 format 层解析 Parquet footer，将 SDK 采集的字节访问信息与 row group 及 column chunk 对应起来。
注入元信息辅助决策：在生成优化方案时（如使用大模型），可将 footer 中的元信息一并输入，使模型能准确识别行列存储位置。

3. 聚焦 Writer 层面的列顺序优化

列顺序可控且侵入性小：Writer 写入时的列顺序由 schema 决定，可通过修改极少量用户代码控制，不影响查询引擎读取。
列顺序独立于表定义：文件中 schema 的列顺序无需与建表时 metadata 定义的顺序一致，执行查询时仅校验列名是否存在即可。

4. 两种应用场景下的优化策略划分

区分优化目标与应用场景：无论用户使用何种工具，均可从外部进行优化，但需根据工具类型采取不同策略。

低层直接调用：若用户手写代码直接调用 Parquet/Arrow Writer，则直接优化该段应用程序代码。
高层 SQL 工具：若用户使用 Spark SQL 等高层工具，则通过优化 SQL 语句和传递参数来实现目标。


计划与应用分离：先生成与上层查询引擎无关的文件级中间优化计划，再针对具体应用场景生成落地方案。

5. 论文研究与实验验证范围界定

聚焦文件格式层验证：确保生成的文件仍为 Parquet 格式且可被读取，不更换底层数据格式库。
第二步方案人工辅助：证明大模型生成中间优化计划的可行性为主，应用层的参数或代码生成可暂时人工完成，重点验证优化计划在典型场景下的有效性。

待办

尝试通过机器学习模型结合 S3 SDK 采集信息和 File Footer 生成中间优化计划，并验证其可行性。



卞昊穹以 Parquet 写入为例，阐明在创建 writer 时传入的 schema 决定了底层数据的列顺序，进而明确可在 writer 代码中直接控制该顺序，​**​这相当于把复杂的存储优化下沉到了底层接口，上层业务无需感知​**​。

随后，卞昊穹向李皓月澄清，底层文件的列顺序与表的原始列顺序无需强制一致，Spark 对此并无要求，​**​可见列顺序调整对上层计算完全透明，这为底层优化扫清了逻辑障碍​**​。

卞昊穹明确全局元数据与文件 Footer 的列顺序可不一致，查询时仅按列名匹配，​**​这彻底解耦了底层存储与表定义的强绑定，为后续灵活调整扫清了技术障碍​**​。

基于低侵入原则，卞昊穹拍板仅修改写文件附近的少量代码，并敲定可调优行组大小、文件大小、列顺序及压缩开关，​**​用极小的代码改动换取核心参数的可控性，有效降低了落地阻力​**​。

卞昊穹与李皓月对齐了优化边界，一致认为表排序、分区等高层级优化过于琐碎且偏离 SDK 核心，​**​这其实是在给论文做减法，避免陷入工程细节的泥潭​**​。

基于此，卞昊穹强调论文应聚焦单一主线，深耕一个核心问题，若涉及多问题则建议拆分成多篇论文，​**​说白了，写论文得“单点打透”，切忌贪多嚼不烂​**​。

卞昊穹指出若优化代码深埋在 Spark 内部，修改后需重新编译部署，实操成本极高，李皓月对此表示认同。​**​这暴露出底层依赖的强耦合风险，牵一发而动全身，极易卡住优化推进。​**​

鉴于此，卞昊穹建议将 Spark 等框架视作黑盒，聚焦于应用层代码进行优化，以此规避底层编译难题。​**​相当于把复杂问题降维，巧妙绕开底层框架的“硬骨头”，提升落地可行性。​**​

李皓月担忧大模型若缺乏严格限制，极易误改底层代码导致 Spark 崩溃，​**​这反映出她对 AI 介入底层系统的不信任，更倾向稳妥的调参方案​**​。

随后李皓月澄清当前四个维度的优化均通过调参完成，并未修改 Spark 代码，​**​相当于直接排除了底层代码优化的必要性​**​。基于此，卞昊穹转而追问其生成 Parquet 文件的具体实现方式。

卞昊穹确认李皓月通过 Spark SQL 生成文件后，指出其无法修改底层 `public writer`，只能调整 SQL 语句与参数，​**​这暴露出当前技术栈的局限性，底层优化被框架封装，只能在外围做文章。​**​

随后卞昊穹坦言原以为存在大量手写程序场景，但推测实际多为 SQL 或流处理导数据，进而明确优化重点不在不暴露的 writer，​**​可见他迅速根据反馈修正了预设，将优化方向从底层代码转向了外围参数。​**​

李皓月与卞昊穹对齐了底层逻辑：若使用 Spark SQL，因底层代码不可见，只能优化 SQL 与参数；若想改底层，则需自研替代组件，​**​这暴露出依赖通用框架与深度定制优化存在天然互斥​**​。

鉴于自研组件过于复杂且违背用户习惯，两人一致驳回了强行要求用户弃用 SQL 的方案，​**​可见技术优化不能脱离实际场景，强行改变用户习惯无异于本末倒置​**​。

随后，卞昊穹提议将场景一分为二：保留用户手写代码直接调用底层 writer 的场景，作为独立的优化用例，​**​相当于把理想化的底层优化剥离出来，单独作为一个轻量级场景来推进​**​。

卞昊穹明确系统工具代码不可随意修改，优化只能从外部着手，如调整参数或调用方式，​**​这相当于给优化划定了边界，只能在外围做文章，无法动底层核心​**​。

随后卞昊穹与李皓月对齐了高低阶工具并存的现状，决定按不同用例分别制定优化策略，​**​可见两人已跳出单一场景的局限，开始做更全面的兼容性考量​**​。

基于此，卞昊穹提出通过采集 SDK 信息、读取文件 footer 等底层手段来推进优化，​**​这表明团队正试图用底层数据监控，来弥补无法直接修改工具的短板​**​。

卞昊穹将优化方案拆解为两步，先制定通用计划，再针对底层工具差异定制应用层变动，李皓月对此表示认可。​**​这种“先定目标后看工具”的解耦思路，有效避免了底层差异干扰核心逻辑。​**​

随后，卞昊穹提议引入机器学习模型，结合 S3 SDK 与文件元数据来辅助生成优化方案。​**​引入 AI 模型旨在将经验驱动的优化转化为数据驱动，试图用算法解决人工调参的瓶颈。​**​

卞昊穹明确了论文的研究边界，强调当前阶段只需针对特定场景产出初步方案，证明核心 idea 可行即可，​**​这其实是典型的“抓大放小”策略，旨在避免陷入局部优化的泥潭，确保核心路径跑通​**​。

基于此，卞昊穹进一步将第二步的产出目标收敛为生成基础的 Spark 参数与 SQL，放弃对极致准确性的追求，李皓月对此表示认同，​**​可见两人已就“最小可行性验证”达成共识，果断砍掉非核心任务以保交付​**​。

李皓月与卞昊穹对齐了实验验证目标，即需证明优化计划在 writer 上有效且具备跨引擎泛化能力，​**​这相当于给论文定下了“先跑通再谈完美”的务实基调​**​。

卞昊穹进一步明确了底层计划与上层引擎解耦的思路，强调计划应用可人工或大模型辅助，现阶段只需在典型场景下验证可行性即可，​**​可见当前核心诉求是概念验证，而非追求全场景的工业级落地​**​。

随后，李皓月认同了卞昊穹的推进策略，并确认当前考虑重点确实涉及 file format 层面，​**​这表明双方在技术切入点上已达成高度一致，排除了方向性分歧​**​。
