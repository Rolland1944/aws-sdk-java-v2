## 1. Introduction
随着数据湖与湖仓的普及，基于对象存储的 datalake 与lakehouse 已经变成了同时承载大规模摄入、交互式 SQL、机器学习和图处理的平台。这些系统必须在高时延的对象存储上支撑从亚秒级交互式查询到 PB 级批处理这样跨度极大的负载[^15]。与本地存储不同，对象存储的一次 Range GET 包含一笔几乎与传输字节无关的固定成本。因此，请求的次数是一个被现有查询优化器忽视的成本维度——引擎无法看到这一点，也缺乏针对对象存储设计的文件布局。

缓存已被证明是有效的手段。Snowflake 报告，在计算节点的临时存储上机会式缓存热的持久化文件，配合简单的 LRU 淘汰，可以改善大量查询的执行时间[^6]；Hadoop S3A 的预取[^7]与 Spark 的 RDD 缓存[^8]也在各自的读路径上做了优化。然而这些机制的准入与淘汰粒度都很粗：S3A 以固定大小的块预取，把取回粒度与缓存粒度绑定；Spark 以 RDD 分区为单位缓存计算结果而非远端字节；Snowflake 使用简单 LRU。我们在七条真实负载 trace 上的离线回放量化了这一代价：固定块缓存的成败取决于工作集与缓存预算之比。一旦超出预算，块被反复淘汰重取，读放大 68 倍[^10]。

改写文件布局同样有效。Pixels 为云对象存储重新设计了列存布局并配合 I/O 调度[^11]；PTO 用负载驱动的预测模型为 Iceberg 表选择分区列、排序等物理参数[^9]；qd-tree 用谓词把记录切分到块中，使含谓词的查询能够跳过大量块[^12]。但它们各有适用边界：Pixels 引入新的存储格式，PTO 绑定 Iceberg 并依赖查询级负载信息，qd-tree 依赖谓词，对不含谓词的全量扫描、KV 点查或机器学习的多轮遍历帮助有限。更根本的是，由于引擎与 Parquet 紧耦合，新的文件格式、访问路径和存储介质都难以被采纳[^5]——任何落在单一引擎内部的优化都无法被其他引擎复用。因此，一个既不修改引擎源码、也不引入新格式，同时能服务多种引擎的优化层仍然缺失。

对象存储 SDK 是所有引擎访问数据的公共路径，这一层此前只被用于降低单次检索的开销。Durner、Leis 和 Neumann 首次对对象存储的检索做了深入测量，给出了代价与性能最优的检索配置，并实现了下载管理器 AnyBlob，在最大化吞吐的同时最小化 CPU 开销[^13]。该工作优化的是单次检索的吞吐与 CPU 成本，而不是是否应当发起这次请求。这正好为互补的工作留出了空间。

因此，我们提出了 Reconfiguration and Caching SDK（Short as RECAS），一个使用在线缓存和离线布局重写优化的 SDK。我们在 SDK 的读路径上做了两件事。第一，在线缓存：拦截 Range GET，以请求为单位进行缓存准入与淘汰。我们的策略扩展了 W-TinyLFU，为其增添了大小和成本感知的准入机制。第二，离线布局：SDK 记录的字节轨迹与 Parquet footer 按纯几何关联，获得访问热点列，据此生成文件级布局计划，包括列顺序、压缩与编码、行组与文件大小，再用 parquet writer重写为标准 Parquet，重写一次后所有 reader 受益。由于只看字节区间与 footer，不读 SQL、查询计划或谓词，这套方法对 SQL 与非 SQL 负载一致。实验结果显示，对于 clickbench sf8，在同区 AWS S3 上，组合方案把 43 条查询的查询时间中位数减少 25.9%，远端 GET 减少83%。在腾讯云 COS 上，43 条查询的查询时间中位数减少 55.0%；两边被消除的请求数几乎相同，可见对于 GET 固定成本越大的系统，该方法效果越好。代价是 Spark driver 峰值堆从约 8 GiB 升到 21–25 GiB，GC 时间不增加。

我们的贡献：
- 可插拔、用户无感知的智能 SDK：优化在 SDK 内部进行，不读 SQL、查询计划或谓词，对上层只是一个配置项。
- 请求级、代价感知的透明缓存：在 SDK 读路径上以"频率 × 远端代价"做请求级原子准入，取代固定尺寸阈值与朴素 LRU。
- 字节轨迹与 footer 的推断的布局重写：由 SDK 观测的 GET 区间与 Parquet footer 生成文件级布局计划，并用公开 writer API 落地为标准 Parquet，因此对任意引擎透明。

## 3. Overview
### 3.1 系统架构
图 x 给出了 RECAS 的高层架构，分为两部分：Reconfiguration 和 Caching。前者为离线重写，一次重写所有 reader 都可收益。后者为在线缓存，运行时以请求为单位进行缓存准入与淘汰，消除重复的远端 HTTP GET。两部分只依赖 SDK 能够观测得到的证据——每次请求的字节级 Range 轨迹和 Parquet footer。下面简要介绍一下这两个模块：
Reconfiguration。SDK 拦截发出的 HTTP GET 请求头，获取请求的字节级轨迹，并从 Parquet footer 中解析出文件的物理布局。之后对轨迹和文件布局进行几何关联，产出 access profile。文件重布局的动作空间为五维，对每一维生成有限候选。候选计划为五维候选的笛卡尔积。为了确保生成的计划是 writer 可写的，并补偿估价时的盲区，候选需要先经过 L0 可行性校验，对不满足硬标准的候选进行剪枝。然后进行 L1 估价。L1 从实测基线几何缩放出候选几何，再根据目标函数为每个候选进行定价并排序。根据估价最终得到的重布局计划，使用 parquet writer 重写原文件，得到 Reconfigured Layout parquet。之后所有 reader 都可以读取这一 parquet 文件并从中受益。
Caching。在这一部分中，代理拦截 getObject，在每次 HTTP GET 请求发出前获取请求范围。RECAS 将其归一化为半开区间\[start, endExclusive)，用于检查这段内容是否在缓存中。如果命中缓存，那么就将 cache 中的这部分块 pin 住，通过 zero copy 返回内存流，不再发起 HTTP GET。未命中缓存进行两步决策。先进行尺寸与模式过滤，未通过的请求走 exact-range GET，通过的请求走 S3 响应流，同时将字节收入 buffer。buffer 读满后使用优化的 w-tinylfu 算法进行请求级原子缓存准入和淘汰。优化的 w-tinylfu 算法增加了代价感知机制，比较分数为候选请求 `频率 × 估计远端代价`，与所有 victim 的收益之和比较。被拒绝的请求计入 range ghost，准入的请求替换 victim 进入缓存。
### 3.2 协同机制
具体运行方式分为三阶段：观测、重构、服务。观测阶段，在一次基线运行中记录每个请求的偏移、长度、起止时间与线程，用于重构阶段的候选估价。重构阶段，离线运行一次，通过上述 Reconfiguration 过程重写布局，产物是标准 Parquet。服务阶段，每进程运行时启动，开启透明缓存，运行时以请求为单位做准入与淘汰，消除重复的远端 Range GET。两部分在设计上弱依赖——布局重排不改变缓存的准入逻辑，缓存也不改变 footer 几何——因此可以各自单独部署，也可以叠加。§x 的 2×2 网格既是最终结果，也是这一弱依赖假设的实证检验。注意采集器独立于缓存层：轨迹必须在缓存关闭的基线运行中采集，否则命中会抑制 GET，轨迹不再反映 reader 的真实字节需求。

4.1 Reconfiguration
This section presents the design of the Reconfiguration component: evidence collection, the action space, candidate generation, the L0 feasibility gate and the L1 pricing model, and finally how the selected plan is materialised by a Parquet writer.

4.1.1 Evidence Collection and Access Profile
Collection. RECAS attaches an interceptor to the outgoing HTTP request path and emits one record per transmission attempt. Each record carries the method, host and path, which together identify whether the request is a ranged GET and which object on which endpoint it targets. For a ranged GET, the Range header is parsed into range_offset and range_length. The record further carries the audit identifiers that S3A encodes as a query string in the Referer header — id, ps and p1, recorded as audit_span_id, audit_process_id and audit_path — together with the issuing thread and the wall-clock issue time ts_wall_ms. A missing audit field is normal rather than an error, since S3A truncates the header once it grows too long.

In parallel, RECAS parses the footer of every Parquet file with PyArrow and derives the byte range each column chunk occupies in the object. Two quantities are computed rather than read, because the format does not expose them directly. A chunk's byte_start is taken as min(dictionary_page_offset, data_page_offset), since the file_offset field points at the first page rather than at a clean chunk boundary, and its byte_end as byte_start + total_compressed_size. A row group's range is the union of its column chunks' ranges,. The pass is strictly read-only and emits one row per (file, row_group, column) triple, recording the byte range, compressed and uncompressed sizes, the physical type, the encodings in use, and the presence of an OffsetIndex and ColumnIndex. The latter fields are what the L0 encoding-compatibility check and the L1 page-index term later consume.

Correlation. We define an access span as one logical open of one object, and take it as the unit at which columns are read together. S3A stamps this identity on every GET, so a span is identified by the triple (audit_process_id, audit_span_id, audit_path). When fewer than half of the records carry an audit span — older traces, or non-S3A readers — RECAS falls back to grouping by (thread, object) and cuts a span wherever two consecutive requests are more than 2000 ms apart. That threshold sits far above the inter-request spacing within a single vectored read, even at the 228 ms RTT we measured cross-cloud, and far below the gap between two Spark tasks sharing a pool thread; the span-size distribution is reported so that a degenerate setting is visible rather than silent.

Correlation then joins the two layers purely geometrically, with no reference to query plans or predicates:

GET [offset, offset+length)∩chunk [byte_start, byte_end)

The chunk table is loaded into memory, grouped by object and sorted by byte_start, and a binary search over that ordered list resolves the chunks each GET overlaps, recording the per-chunk overlap_bytes. One GET may cover several chunks.Taking the union over the GETs of one span yields the set of chunks that span read.A GET that overlaps no chunk and begins beyond the end of the last column chunk is classified as format metadata. Such requests would be retained and further split by issuing thread into file-level discovery and scan-span metadata. This distinction is what later allows L1 to scale the two kinds of metadata traffic by different quantities — object count and input-split count respectively — rather than by one conflated factor. Correlation is gated on attribution coverage: at least 95% of data bytes must be attributed to a column chunk, or the stage fails. The denominator deliberately excludes format-metadata bytes, which are real traffic but by construction cannot land in a column chunk.

Access profile. The footer labels every chunk with its logical column name path_in_schema. Unioning the labels of all chunks a span intersected gives the set of columns that logical read touched; a column appearing in several row groups of the same span is counted once in that set, while its overlap bytes accumulate. From the per-span records RECAS derives four artefacts:

column_weight — per column, the overlap bytes, the byte share, the number of spans touching it and the corresponding span share. Columns in the schema that no span touched would be placed at the tail of the order.
coaccess — an undirected column graph whose nodes are columns and whose edge weight is the number of spans reading both endpoints. The emitted document retains only the heaviest 400 pairs; this bounds the serialised artefact.
patterns — spans grouped by (table, set of columns read). Each pattern records the number of spans exhibiting it together with the mean bytes, mean data GETs, mean metadata GETs and mean number of row groups touched.
request_shape — the request-size histogram, the fraction of GETs below 64 KiB, the counts and bytes of data versus metadata GETs split into the file and scan kinds, the per-object open overhead, the mean number of GETs per touched chunk, and the share of data spans that read more than one column.
These artefacts feed distinct consumers downstream. column_weight supplies the greedy seriation with both its seed and its restart rule — the heaviest unplaced column begins a new contiguous block whenever the co-access chain breaks, which is what produces clusters without a separate clustering pass — and also supplies L1 with per-column byte shares. coaccess is the sole evidence behind the column-order action. patterns are the units L1 prices and rank. request_shape serves two roles: it gates whether an action is addressable at all, as when the column-order axis is skipped because multi-column data spans fall below 25% of all data spans, and it provides the measured GET and byte totals against which L1's baseline replay is validated.
