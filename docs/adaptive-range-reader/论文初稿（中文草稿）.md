## 1. Introduction 
随着 datalake 和 lakehouse 的使用范围越来越广，对象存储上的数据湖和湖仓已经从原始文件仓库变成同时承载大规模摄入、交互式 SQL、机器学习和图处理的平台，覆盖的数据规模从小于 1 TB 的表一直到数百 PB[^15]。因此，优化针对对象存储的访问性能显得尤为重要。Snowflake 已经证明，把热的持久化文件机会式地缓存在临时存储里，能缩短很多查询的执行时间[^6]。Hadoop[^7] 和 Spark[^8] 也进行了各自的缓存优化。此外，PTO、Pixels、Wide Table 等工作证明了，改写文件布局可以优化访问性能，减少 I/O 成本。然而，这些工作都有一定的不足之处。Hadoop 的 S3A prefetch 和 Spark 的 persist 没有准入和淘汰策略，

数据布局的优化责任被放在各个 individual client 或 back-ground services 上，却没有任何一个组件能观察到完整的负载，因此很难判断该做哪些优化[^5]。于是许多厂商各自开发额外的、专有的加速层，造成重复劳动，也削弱了开放生态[^5]。

Hadoop 的 S3A prefetch 以固定块大小进行预取，Spark 则以 RDD 分区为粒度缓存。如表 xx 所示，固定块大小缓存会被反复淘汰重取造成度放大灾难[^10]。PTO[^9] 在 Iceberg 上优化跳过行数，Pixels[^11] 使用新的列存布局加 I/O 调度，这些工作共同的问题是依赖特定的 lakehouse 格式或存储格式，缺乏通用性。Qd-tree[^12] 用谓词将记录切到块里，从而改写查询。但是对于不含谓词查询的 KV、ETL或机器学习负载，这一优化无法使用。因此，在一个能够观察到完整负载的组件中实现一个通用且可插拔的优化器是必不可少的。

SDK 是访问中必经的中间件，但迄今为止，尚无工作进行 SDK 中的缓存优化。Durner、Leis 和 Neumann 的工作[^13]中提到现有 SDK 具有单次对象请求延迟高、网络 CPU 开销大等缺陷，但他们的工作着眼于对单次 GET 请求的成本优化，而非减少 GET 请求。由于 SDK 层可以拦截全部的 GET 请求，因此在 SDK 上进行访问优化可以观察全部的负载。这一点使得更加精细的缓存策略成为可能，避免 S3A prefetch 的固定块缓存策略造成的抖动。进一步地，SDK 观测到的 GET 请求与 parquet footer 结合，可以看到每次访问了 parquet 文件的哪部分，从而根据访问热点进行文件布局的优化。如图 xx 所示[^14]，不同工作负载的访问热点大相径庭。在随机访问为主的负载中，缓存的优化空间可能较小。但文件布局重排的灵活性使得其在各种负载上都有很好的效果。这一工作完全是可插拔的，不依赖任何特定的查询引擎和存储格式。实验证明，在经典 OLAP 负载 clickbench 上，我们的方法在 AWS 和腾讯云环境下分别取得了 25.9%和 55.0%的效果。在机器学习的真实负载 NYC Taxi 上，在 AWS 和腾讯云环境下分别取得了 xx 和 69.7%的效果。

我们的贡献：
- 完成了一个可插拔的 smart SDK
- 重写文件布局，生成布局计划便于后续 parquet writer 重写布局
- 使用优化的 wtinylfu 算法进行自适应缓存
- 在 5种不同负载上取得了平均 xx（AWS）和 xx（腾讯云）的效果

## 3. Overview
### 3.1 系统架构
图 x 给出了 RECAS 的高层架构，分为两部分：Reconfiguration 和 Caching。前者为离线重写，一次重写所有 reader 都可收益。后者为在线缓存，运行时以请求为单位进行缓存准入与淘汰，消除重复的远端 HTTP GET。两部分只依赖 SDK 能够观测得到的证据——每次请求的字节级 Range 轨迹和 Parquet footer。下面简要介绍一下这两个模块：
Reconfiguration。SDK 拦截发出的 HTTP GET 请求头，获取请求的字节级轨迹，并从 Parquet footer 中解析出文件的物理布局。之后对轨迹和文件布局进行几何关联，产出 access profile。文件重布局的动作空间为五维，对每一维生成有限候选。候选计划为五维候选的笛卡尔积。为了确保生成的计划是 writer 可写的，并补偿估价时的盲区，候选需要先经过 L0 可行性校验，对不满足硬标准的候选进行剪枝。然后进行 L1 估价。L1 从实测基线几何缩放出候选几何，再根据目标函数为每个候选进行定价并排序。根据估价最终得到的重布局计划，使用 parquet writer 重写原文件，得到 Reconfigured Layout parquet。之后所有 reader 都可以读取这一 parquet 文件并从中受益。
Caching。在这一部分中，代理拦截getObject，在每次 HTTP GET 请求发出前获取请求范围。RECAS 将其归一化为半开区间\[start, endExclusive)，用于检查这段内容是否在缓存中。如果命中缓存，那么就将 cache 中的这部分块 pin 住，通过 zero copy 返回内存流，不再发起 HTTP GET。未命中缓存进行两步决策。先进行尺寸与模式过滤，未通过的请求走 exact-range GET，通过的请求走 S3 响应流，同时将字节收入 buffer。buffer 读满后使用优化的 w-tinylfu 算法进行请求级原子缓存准入和淘汰。优化的 w-tinylfu 算法增加了代价感知机制，比较分数为候选请求 `频率 × 估计远端代价`，与所有 victim 的收益之和比较。被拒绝的请求计入 range ghost，准入的请求替换 victim 进入缓存。
### 3.2 协同机制
具体运行方式分为三阶段：观测、重构、服务。观测阶段，在一次基线运行中记录每个请求的偏移、长度、起止时间与线程，用于重构阶段的候选估价。重构阶段，离线运行一次，通过上述 Reconfiguration 过程重写布局，产物是标准 Parquet。服务阶段，每进程运行时启动，开启透明缓存，运行时以请求为单位做准入与淘汰，消除重复的远端 Range GET。两部分在设计上弱依赖——布局重排不改变缓存的准入逻辑，缓存也不改变 footer 几何——因此可以各自单独部署，也可以叠加。§x 的 2×2 网格既是最终结果，也是这一弱依赖假设的实证检验。注意采集器独立于缓存层：轨迹必须在缓存关闭的基线运行中采集，否则命中会抑制 GET，轨迹不再反映 reader 的真实字节需求。

## 4. Design
### 4.1 Reconfiguration

在这一部分将介绍 Reconfiguration 部分的具体设计，包括数据收集、动作空间选择、候选计划生成、L0 可行性约束和 L1 估价器，以及最终生成的优化计划如何被 parquet writer 重写。
#### 4.1.1 Evidence Collection and Access Profile

Collection. RECAS 拦截即将发出的 HTTP 请求，记录这次请求的 method、host、path，用于区分这一请求是否为 Range GET 请求，并记录实际访问的对象存储 endpoint 和请求 object。对于 Range GET 请求，首先将 Range 头解析成 ` range_offset ` 和 ` range_length `，并记录 `Referer` 里的 `id`、`ps`、`p1` ，标记为 `audit_process_id, audit_span_id, object`，以及调线程名 `thread`，发出时的 `ts_wall_ms`。同时，使用 pyarrow 读取 每个 parquet 文件的 footer，根据 footer 计算该 parquet 中每个 column chunk 的字节范围，将计算结果输出成一张 parquet 表。

Correlate. 一次 S3A 打开视为一次逻辑读取。一次逻辑读取发出 GET 请求的 `audit_process_id, audit_span_id, object` 一致，记为一组 episode。当超过一半的记录没有 audit 字段时，使用 `(thread, object)` 划分 episode。同一组里按 `ts_wall_ms` 排序，相邻两条的间隔小于等于 2000 ms 记为一组 episode。correlate 阶段将 collect 阶段生成的 parquet 表读入内存，按 path 分组，每组按 `byte_start` 排序，用这个有序列表和 GET 的 范围做物理相交，获得本次读取的 chunk，再将这些 chunk 取并集，作为一组 episode 读取的 chunk。例如，同一 episode 中的两个Range GET 分别读取了 chunkA 末尾和 chunkC 开头，那么就说这一组 episode 读取了 chunk AC，并记下各自的 overlap_bytes。

Access profile. paruqet footer 为每个 chunk 标注了对应的逻辑列名 `path_in_schema`。一个 episode 里所有 GET 相交到的 chunk，把这些列名并成一个集合，就是这次逻辑读取同时碰到的列。同一个列在多个 row group 里只算一次。在 access profile 阶段，RECAS 产出 4 种东西：
1. `column_weight`：每一列的重叠字节、字节占比、碰到它的 episode 数和 episode 占比。
2. `coaccess`：列访问无向图。节点为列名，权重为同时读到这两列的 episode 数，默认只保留最重的 top-K 对。
3. `patterns`：访问模式表。一种模式为一次逻辑读取同时碰到的列。记下拥有该访问模式的episode 数、平均字节、平均 GET 数、平均碰到的 row group 数。
4. `request_shape`：请求大小直方图。记录小于 64 KiB 的 GET 比例、数据 GET 与 footer/page-index GET 的数量和字节、每个对象的打开开销、每个被碰到的 chunk 平均对应几次 GET。

其中，column weight 用于标识 greedy seriation 开始的起点，coaccess 用于重排列顺序，patterns 用于 L1 估价器估价，request shape 用于为估价做回放校验。
#### 4.1.2 Five-Dimensional Action Space and Candidate Generation

动作空间的界定。 重布局可触及的变量众多——列顺序、文件大小、行组大小、压缩与编码、页几何，直至分区与排序。我们采用的方案是五维动作空间上的有界穷尽枚举。借鉴 Zeng 等人对列式存储格式的实证分解[^16]，我们将 Parquet 的物理结构划分为文件、行组、列顺序、列块表示、页五个层级，并在每一层级选取一个由 writer 直接控制的主变量作为动作维度。入选的变量须同时满足五个条件：(i) 其定价证据可由 SDK 轨迹、Parquet footer 或小规模 probe 获得；(ii) 可经公开 writer API 表达；(iii) 产物仍是标准 Parquet，无需任何 reader 侧改动；(iv) 能够改变 GET 数、远端字节或元数据成本之一；(v) 不依赖 SQL 谓词、查询计划或应用语义。表 x 给出五个维度的完整规格。

| ---- | ----------------- | ---------------------------------- | ---------------------------------------- | ------------------------------------------- | ---------------------------------------------------------- |

以此标准，若干常见动作被排除。Partitioning、global sort 与 Bloom filter 的收益取决于谓词列、选择率与值分布，而字节级 Range 轨迹无法可靠恢复这些语义；更本质的是，前两者会改变每个查询读到的行集，从而使 L1 的核心前提——执行残差跨候选恒定，因而按 t_io 排序等价于按端到端时间排序（§4.1.4）——不再成立，保留它们将迫使估价器重新引入选择率估计。格式替换、列复制与外部索引则越过了"产物仍是标准 Parquet 且无需查询改写"的边界。另有动作可由已选维度派生而无需独立优化：列块大小由行组大小、列字节分布与 (codec, encoding) 共同决定，不存在独立的控制变量。最后，压缩与编码不对压缩后列大小独立作用，故将其合并为单一维度联合定价。
候选的有界生成。 直接搜索上述动作的原始空间不可行：C 列的列顺序有 C! 种，若每列有 E 种表示方式，逐列组合可达 E^C。RECAS 因此不枚举原始空间，而是先为每一维生成少量、可解释且有证据支撑的候选，并在每一维都保留基线取值作为候选之一。

此处有两个设计选择值得说明。其一，文件与行组的有限候选集在计数空间而非字节空间构造，即一次扫描要打开多少个对象，以及可被跳过的行组有多少。其二，各维的候选集合均经过可行性检查前置过滤，剔除 writer 无法写出或明确没有收益的候选。

五个维度的收益并不彼此独立，这正是必须在联合空间上定价的原因。例如，一个缩小字节的 codec 会在同一目标文件大小下减少文件数，进而改变扫描任务数，最终导致并发度降低。RECAS 因此枚举这些有界候选的笛卡尔积，将每个组合视为一个候选计划，逐点交由 L0 门禁（§4.1.3）与 L1 估价器（§4.1.4）处理。在 clickbench负载上，这一空间共产生 384 个候选计划，其中 312 个通过 L0，72 个被拒。
我们选择有界穷尽枚举而非生成式模型或贝叶斯优化，理由有三。第一，确定性与可复现性；第二，约简显式、搜索穷尽，空间的每一步收缩都有可解释的证据来源；第三，由于每一维都保留基线取值，在同一套 L1 下胜出计划必然不劣于基线，这是有限预算下的随机搜索无法给出的保证。此外，枚举的代价本身很低：RECAS 的 virtual_footer 可直接由 footer、probe 比率与 reader 合并规则推出候选的请求计划，单点定价无需写出任何数据，因此数百量级的候选可在秒级完成全部定价。

#### 4.1.3 L0 Feasibility and L1 Virtual-Footer Pricing

所有枚举得到的 plan candidate 根据 access profile 构造对应的 virtual footer。随后，这些 virtual footer 在 L1 过程中被当作物理上已存在来考虑。在枚举过程中，对于每一个 layout plan，先进行 L0 feasible check。若通过，则 L1 估价器接下来在假定这些 virtual footer 物理存在的前提下，计算最优执行计划。具体的 L0 可行性检查和 L1 估价器在五个维度上的表现如表 y 所示：

| Target file size  | 文件数不低于并行度下界，且处于 [2, 2×10⁴] 区间               | 文件发现元数据按对象数比例缩放；扫描跨度元数据按输入分片数缩放；每次打开计一次 HEAD               |

#### 4.1.4 Layout Materialization and Verification
从 canonical action 到 writer 参数。 L1 选出的计划以 writer 中立的 canonical action 形式表达，落地时再渲染为具体的 writer 参数。RECAS 提供两条渲染通道：直接调用 pyarrow.parquet.ParquetWriter，对应可以直接修改 writer 代码的场景；经由 Spark SQL 的 writer 选项表达，对应只能配置引擎的场景。由于可行性判定是 writer 相关的，所以目标 writer 与网络 regime、冻结的 reader 配置一同构成规划的环境描述，其能力矩阵作为参数进入 §4.1.3 的 L0 判定。
本文的主结果经 ParquetWriter 写出，五种 canonical action 均可落地。写出完成后，RECAS 抽样回读输出文件的 footer，逐项核对：五种 canonical 动作是否与计划一致，写出的 footer 是否与 L1 估价时使用的 virtual footer 一致。任何一项不符都判为写出失败。
### 4.2 Caching
#### 4 .2.1 Request Path
缓存以 JDK 动态代理挂在 S3Client 之前，仅拦截 getObject。请求发往网络前，代理从 GetObjectRequest 取出 bucket、object key 与 Range 头，并将后者归一化为半开区间 \[𝑠𝑡𝑎𝑟𝑡, 𝑒𝑛𝑑𝐸𝑥𝑐𝑙𝑢𝑠𝑖𝑣𝑒)。缓存对象标识由三段构成：bucket、object key，以及依次取自 VersionId、If-Match 或响应 ETag 的版本 token；同一对象的不同版本因而在键空间中天然隔离。
**命中判定与 pin**。 查找在单次加锁内完成：从 start 出发，沿块索引逐段寻找能覆盖当前位置的缓存块，命中一段即将其加入跨度并递增其引用计数，位置推进至该块末端，直至覆盖 endExclusive。跨度可由多个相邻块拼接，但其中任一段缺失即判为未命中，此时在同一临界区内回滚已递增的全部引用计数。引用计数不为 0 的块不得被淘汰。同一块可被多个并发读者同时持有。命中时返回一个直接读取块内存的合成响应流，关闭时递减引用计数。
**未命中的两步决策**。 发起 GET 前需要经过尺寸与模式过滤：超过单次 Range GET上限（默认 8 MiB）的请求，或控制器处于旁路模式、预算为零时的任何请求，直接走原始的 exact-range GET，不进入缓存路径。这么做的原因是，这类请求通常是一次性大扫描，复制其字节既无复用前景，也会挤占小热点的容量。
对于通过过滤的请求，调用方直接从 S3 响应流读取，同一批字节同时被收入一个与请求等长的缓冲区。缓冲区填满后，整个请求交由 §4.2.2 的准入算法裁决。被拒的请求丢弃缓冲区交由垃圾回收，并将其键记入 ghost 表，用于反事实遥测；准入的请求则把缓冲区的所有权移交缓存：按块边界（默认 1 MiB）切出的各个块共享同一个底层数组，仅以偏移与长度区分，因而入缓存过程本身不产生第二次拷贝。
**异常语义**。 缓存内部的任何异常一律回退为原始的 exact-range GET；S3 错误原样抛出。缓存失败不造成查询失败。
#### 4.2.2 Cache Algorithm
**基础算法的选择**。 在以远端 GET 数主导墙钟的读路径上，缓存策略的关键决策是准入而非淘汰。SF8 的容量实验显示,即便把缓存从 4 GiB 加到 16 GiB、淘汰量降到接近零,墙钟也几乎不动,真正限制复用的是被准入环节拒收的那部分字节。这把两项要求推到首位:其一,策略必须抗扫描——一次性的大扫描不应挤掉被反复访问的小热点;其二,对象是尺寸不等的 Range GET,容量核算必须按字节而非按条目。W-TinyLFU 的频率准入过滤器恰好同时满足这两点:它以访问频率的紧凑估计决定新内容是否值得挤占已有内容,从而在准入层就抵御扫描污染。本文因此以 W-TinyLFU 为基础算法。

### 5.1 实验设置

#### 5.1.1 硬件与软件环境

全部实验在单机 Spark上运行，数据常驻对象存储，查询过程中不生成本地数据副本。两个评测环境均采用计算与存储同区部署，该配置将网络往返时延压至最低，构成对读路径优化最为保守的评测条件：同区部署下墙钟中可归因于远端读取的份额最小，因而本文测得的收益构成该机制在更高时延环境中收益的下界。

#### 5.1.3 实验协议与时延刻画

**2×2 因子设计。** 本文将两个机制各设为一个二值因子：布局 ∈ {原始, 重构}，缓存 ∈ {关闭, 启用}，构成四个实验格，记作 00、10、01、11。采用因子设计的目的在于同时获得两个主效应与其交互项，后者刻画一个机制对另一机制有效性的影响（见 5.3 节）。交互项定义为

$$\Delta = (01 - 11) - (00 - 10),$$

即缓存在重构布局上节省的时间与其在原始布局上节省的时间之差，即组合收益减去两项单独收益之和。$\Delta > 0$ 表明两机制相互增强，$\Delta < 0$ 表明两机制的收益存在重叠。

**抖动控制。** 每格运行 n=5 轮，以每轮全查询墙钟之和的中位数作为该格的代表值。为使机器状态的漂移与机制效应相互可分，实验中四个格在每轮内交替执行，使缓慢漂移均摊至各格；每格以独立的冷启动 JVM 与冷缓存运行。

**跨云对照。** 同一份数据快照、同一构建产物与同一查询集在两个云环境上各运行一遍完整网格。该设计将「单个被消除请求的时间价值」作为可控变量引入：物理削减量（远端请求数与字节数）由布局与缓存共同决定，在两个环境中保持一致；而同一组削减在不同的单请求成本下兑现为不同的墙钟收益。Criteo 提供了该机制最清晰的例证——两个环境的 IO 指标几乎逐位一致（重构布局均为 44,242 次 GET / 187.87 GiB；重构加缓存分别为 15,357 与 15,510 次 GET），其墙钟差异可归因于单请求成本的差异。

两个环境的单请求固定成本相差约 3.4 倍，具体数据如表y所示。这一观测构成本文两个机制均以削减请求数为主要手段的直接依据。

#### 5.2.1 资源代价

上述收益以内存占用为代价换取，表 z 的末列给出各网格 00 格与 11 格的峰值堆。

**堆是主要代价。** 组合启用后峰值堆的增量介于 3.15 GiB（Criteo / AWS）至 28.62 GiB（TPC-H SF350 / AWS）之间，最高的绝对值出现在 TPC-H SF350，两云分别达 43.07 与 42.90 GiB，约为 48 GiB 堆上限的 90%。该增量显著超出 4 GiB 的缓存预算，原因在于它并非仅由被缓存的字节构成：命中路径上存活的 SDK 与 Spark 对象、不同查询阶段峰值时刻的错位以及垃圾回收的时序均计入该观测值，因此峰值堆的差额是启用缓存的总内存代价，而非缓存本体的容量。这一事实决定了内存缓存层的可扩展上限由堆而非命中率给出，5.6 节据此确定 4 GiB 的容量取值。

**垃圾回收开销未随堆增长而上升。** 在堆占用显著提高的同时，各网格的垃圾回收时间保持不变或下降：ClickBench SF8 / AWS 由 30.9 s 降至 17.2 s，Criteo / AWS 由 77.9 s 降至 13.1 s，NYC Yellow Taxi 的四个格则一致处于 4.0 至 5.4 s。其机制是请求数的削减同时削减了短生命周期分配——元数据对象与读取缓冲随请求数线性产生，请求数下降一个数量级后，该部分分配压力随之消失，足以抵消缓存块长期存活所带来的回收成本。因此内存代价体现为驻留容量的占用，而非回收时间的增加。

**布局重构对堆的影响呈双向性。** 单独启用布局重构时，峰值堆在部分负载上下降、在另一些负载上上升，取决于该负载的瓶颈形态。Criteo / AWS 由 11.97 GiB 降至 4.78 GiB，NovoMCP / AWS 由 13.25 GiB 降至 6.50 GiB，原因是文件数由 973 收至 32、由 21 收至 20 后，元数据与读取对象的短期分配量大幅下降；NYC Yellow Taxi / AWS 则由 1.99 GiB 升至 12.89 GiB，原因是重构后单次读取的体积显著增大（109.33 GiB 仅由 9,266 次 GET 承载），解码与聚合批次同时存活的对象随之增多。两类效应均由请求形态的改变所致，方向取决于负载原有的碎片化程度。

### 5.3 敏感性分析：两个机制各自的有效条件

5.2 节给出的是组合收益。本节将其拆解为两个机制的单独效应，并证明本设计中的两种优化均有其必要性，不能互相替代。二者的有效性分别由负载的两个相互独立的属性决定，二者缺一则覆盖不全。本节随后考察环境时延与数据规模这两个条件变量对各机制的调节作用，最后给出二者的交互形态。图 b 给出各网格上 Caching、Layout 与 Combined 三项效应的分解。

#### 5.3.1 缓存的有效条件：每查询远端读取量与容量之比

缓存的作用由单条查询读取的远端数据量与缓存容量之比决定。本文从原始基线（00 格）的请求级 I/O 轨迹出发，按查询边界归属每一次远端请求，得到**每查询远端读取量**；该量与缓存容量 4 GiB 之比记为**容量压力比**。各负载的查询轻重差异极大——ClickBench SF8 的单查询读取量跨越 0.04 至 111.66 GiB，达三个数量级——故本文以中位数作为该分布的代表值。

| 数据集 | 每查询读取量中位数 | 容量压力比 | 缓存的 GET 削减 |
|---|---:|---:|---:|
| ClickBench SF8 | 2.71 GiB | 0.7× | 73.0% |
| NovoMCP Compound | 2.74 GiB | 0.7× | 77.2% |
| Criteo CTR | 4.92 GiB | 1.2× | 74.8% |
| NYC Yellow Taxi | 26.00 GiB | 6.5× | **10.6%** |
| TPC-H SF350 | 26.81 GiB | 6.7× | **11.3%** |

该关系呈阈值形态：容量压力比不超过 1.2 的三个数据集削减 73.0% 至 77.2% 的请求，而压力比达 6.5 以上的两个数据集削减量塌至 11% 左右。ClickBench SF8 与 NovoMCP 的压力比几乎相同（0.68 与 0.69），其请求削减亦相近（73.0% 与 77.2%），构成对该指标的一次独立印证。

更直接的机制刻画是**读取量不超过缓存容量的查询在查询集中所占的比例**。ClickBench SF8 的 43 条查询中有 26 条（60%）读取量低于 4 GiB，TPC-H SF350 的 22 条中仅有 1 条，NYC Yellow Taxi 的 4 条中没有一条。缓存的请求削减与该比例同向，说明收益并非均匀来自全部查询，而是集中于读取量落入容量之内的那一部分。ClickBench 即为典型：其 Q21 至 Q24、Q28、Q29、Q34、Q35 等大扫描单条读取 17 至 112 GiB，被频率准入拒于缓存之外，而 73.0% 的请求削减来自其余小查询对同一批热点列的反复访问。

NYC Yellow Taxi 提供了一个反直觉的例证。该负载的时间局部性在五者中最强——其查询集全部由同一次扫描的四个 epoch 构成，复用是确定的而非偶然的。然而四个 epoch 的读取量分别为 25.96、25.98、26.01 与 26.14 GiB，无一条落入 4 GiB 容量之内，因此在下一个 epoch 开始之前缓存已被完整冲刷，最终只削减 10.6% 的请求。**因此，缓存有效性和访问的空间局部性不完全一致，还收到缓存压力比的影响。**

在压力比远超 1 的负载上，缓存退化为小对象缓存：TPC-H 的 11.3% 削减来自 nation、region、supplier 等被 22 条查询反复连接的小表，其总体积远小于 4 GiB 而得以常驻；lineitem 的一次性大扫描则被频率准入正确地拒于缓存之外，未造成扫描污染。

#### 5.3.2 布局的有效条件：原始布局的碎片化程度

布局重构的效力由原始布局中可供合并的碎片量决定。以每 GiB 数据对应的远端请求数衡量该碎片化程度，可得表 v。

| 数据集 | 碎片化（GET / GiB） | 布局的 GET 削减 | 布局墙钟收益（AWS） |
|---|---:|---:|---:|
| TPC-H SF350 | 11,422 | 76.4% | 26.3% |
| NYC Yellow Taxi | 3,099 | 92.4% | 17.6% |
| ClickBench SF8 | 2,342 | 30.0% | 22.8% |
| Criteo CTR | 1,869 | 45.7% | 19.0% |
| NovoMCP Compound | 634 | 22.5% | **3.8%** |

该关系呈阈值形态而非单调关系：碎片化程度不低于 1,869 GET/GiB 的四个数据集均取得 17.6% 至 26.3% 的墙钟收益，而碎片化程度最低的 NovoMCP 仅取得 3.8%。NovoMCP 的失效原因是结构性的——其原始布局已仅含 21 个文件与 132 个行组，**本身已接近该负载的最优几何，重构只能将文件数由 21 降至 20，没有可供合并的余量**。换言之，布局重构的收益来自原始布局与最优布局之间的差距，当该差距本身很小时，机制无从施展。

阈值以上各数据集的收益并不随碎片化程度单调递增，原因是实际可合并的维度各不相同：NYC 的请求削减主要来自行组合并（原始 204 文件含 14,973 个行组），Criteo 则主要来自文件合并（973 文件合为 32 个）。碎片化程度界定了机制的作用空间上界，具体兑现比例取决于碎片所在的维度是否落在动作空间之内。

**两个条件相互独立。** 容量压力比刻画的是查询的时间维度性质，碎片化程度刻画的是数据的空间维度性质，二者在本文的样本中并不共变：TPC-H 的压力比最高而碎片化程度亦最高；NovoMCP 则相反，压力比为 0.7×而碎片化程度最低。单一机制因此无法覆盖全部负载，而两个机制的组合在本文的五个数据集上均至少有一方有效——这构成本文采用组合设计而非单一机制的直接依据。

#### 5.3.3 环境敏感性：时延放大与机制的请求削减占比

同一机制在两个云环境上的收益并不等比放大，其放大倍数由该机制收益中**请求削减所占的比重**决定。将缓存在 COS 与 AWS 上的墙钟收益之比与其 GET 削减对照，二者的 Spearman 秩相关为 0.80。

| 数据集 | 缓存的 GET 削减 | 缓存收益的放大倍数 |
|---|---:|---:|
| NYC Yellow Taxi | 10.6% | 1.58 |
| TPC-H SF350 | 11.3% | 1.10 |
| ClickBench SF8 | 73.0% | 1.99 |
| Criteo CTR | 74.8% | 1.59 |
| NovoMCP Compound | 77.2% | 3.10 |

其机制与 5.2 节的结论一致：单请求固定成本由 AWS 的 26.1 ms 升至 COS 的 86.2 ms，而带宽并非瓶颈，因此**一个机制的收益中由请求削减贡献的部分会随环境时延成比例放大，由字节削减贡献的部分则不会**。缓存只削减请求，布局同时削减请求与字节，故在高时延环境中缓存被放大的幅度普遍大于布局。

这一规律解释了 ClickBench SF8 上两个机制的次序反转。该数据集是样本中缓存的请求削减最大幅超过布局的请求削减的负载，因此由 AWS 迁至 COS 时缓存被放大 1.99 倍而布局几乎未被放大，两者的次序由 AWS 上的「布局 22.8% 对缓存 18.3%」反转为 COS 上的「缓存 36.5% 对布局 23.0%」。Criteo 呈现同向但未完成反转的位移：AWS 上布局以 19.0% 对 13.1% 领先，COS 上两者收敛至 21.4% 对 20.8%。

本文关于环境放大的定量依据以 Criteo 为准，该数据集两云的 I/O 指标几乎逐位一致（见 5.1.3 节）。

#### 5.3.4 规模敏感性

在缓存容量固定为 4 GiB 的条件下，数据规模的增长同时作用于两个相反的方向。以 ClickBench 由 SF1（14.11 GiB）增至 SF8（111.99 GiB）为例，AWS 环境下：

| 效应 | SF1 | SF8 |
|---|---:|---:|
| 缓存的 GET 削减 | 85.5% | 73.0% |
| 缓存墙钟收益 | 14.9% | 18.3% |
| 布局的 GET 削减 | 29.1% | 30.0% |
| 布局墙钟收益 | 14.5% | 22.8% |
| 组合墙钟收益 | 21.7% | 31.6% |

规模增长使原始基线的远端读取总量由 46.6 GiB 增至 371.9 GiB，每查询平均读取量由 1.08 GiB 升至 8.65 GiB，缓存的请求削减因此由 85.5% 降至 73.0%，与 5.3.1 节的关系一致。但两项机制的墙钟收益均随规模上升，组合收益由 21.7% 增至 31.6%。其原因是**远端读取在墙钟中所占的比重随规模增长**：同等比例的物理削减在 I/O 占比更高的负载上兑现为更大的墙钟收益，该效应超过了物理削减比例本身的下降。布局一侧没有这种抵消——其请求削减比例几乎不随规模变化，故其墙钟收益的增长更为显著。由此可得一项关于容量配置的推论：在缓存容量固定的前提下，数据规模增长会使布局重构在组合收益中的比重上升。

#### 5.3.5 两机制的交互形态

十个网格中有八个的组合收益小于两项单独收益之和，即交互项为负。其机制是两个机制争夺同一部分收益：布局重构在合并物理读取时，已经消除了一部分本可由缓存命中的小请求。该重叠可以直接量化——在 ClickBench SF8 / AWS 上，缓存在原始布局上削减 191,465 次请求，而在重构布局上仅削减 139,078 次，差额 52,387 次即为被布局提前消化掉的部分。

TPC-H SF350 的两个网格是例外，其交互项为正。其机制与上述重叠相反：重构将文件数由 2,130 收至 514、显著缩短重用距离，使原本无法落入 4 GiB 容量的工作集进入缓存的有效区间，命中率由 12.3% 升至 59.1%，缓存的绝对命中数反而增加。这与 5.3.1 节的结论一致——布局重构通过降低容量压力比，将缓存由失效区推入有效区。

该正交互的来源可由配对数据直接读出：缓存在重构布局上的逐轮收益稳定于 261.1 至 317.2 s，而在原始布局上则由第一轮的 268.3 s 逐轮衰减至第五轮的 91.3 s。原始布局下容量压力比为 6.7，缓存能否命中取决于运行时的偶然因素；重构后压力比落入有效区间，缓存收益随之变得确定。**因此布局重构不仅提高了缓存收益的均值，也降低了其波动。**

### 5.4 缓存算法选型

本节回答缓存层为何采用代价感知 W-TinyLFU。本文将该算法与五种缓存算法及无缓存基线在同一负载上对比：ClickBench SF8 的重构布局，容量固定 4 GiB，Spark `local[16]`，driver 堆 32 GiB，七臂各 n=5。各臂仅替换淘汰与准入策略，其余配置完全相同。

#### 5.4.1 对照算法的选取

实验从纯近因、分段近因、FIFO 淘汰、频率准入和大小感知准入五类主流缓存策略中，各选取一个代表性或近期提出的算法作为对照基线，并在同一 4 GiB 内存预算下与无缓存基线共同评测。具体包括：（1）LRU [1]，作为纯近因淘汰的经典基线，反映无扫描保护时的缓存表现；（2）SLRU [2]（保护区占 80%），代表分段近因淘汰，通过试用段与保护段隔离一次性大扫描，对应本文主缓存区在去除准入过滤器后的结构；（3）SIEVE [3]，代表近年提出的极简 FIFO 族淘汰算法，通过单指针扫描实现惰性提升与快速降级，作为当前先进的低开销淘汰基线；（4）W-TinyLFU（plain） [4]，代表基于 Count-Min Sketch 频率估计的准入控制算法，按单块频次进行准入裁决；（5）W-TinyLFU-AV [5]，代表面向变长对象的大小感知 W-TinyLFU 扩展，将新对象频次与待淘汰受害者集合的累计频次进行比较，是与本文代价感知准入最接近的近期工作。

#### 5.4.2 七臂矩阵结果

| 算法 | 中位数 (s) | 相对无缓存 | GET | 峰值堆 GiB |
|---|---:|---:|---:|---:|
| SIEVE | **1651.7** | 12.37% | 45,943 | 27.51 |
| **代价感知 W-TinyLFU（本文）** | 1656.1 | 12.14% | **44,116** | **23.90** |
| W-TinyLFU-AV | 1664.4 | 11.69% | 48,481 | 28.61 |
| W-TinyLFU（原生） | 1677.1 | 11.02% | 49,519 | 28.63 |
| SLRU | 1700.8 | 9.76% | 64,259 | 28.31 |
| LRU | 1731.9 | 8.11% | 86,250 | 28.03 |
| 无缓存 | 1884.8 | — | 183,675 | 12.42 |

（表注释）七臂的变异系数介于 0.23% 与 1.38% 之间，均远低于本文的 5% 门槛。表中省略的远端字节、命中数、垃圾回收时间与淘汰量在下文述及。

七臂的墙钟次序与其请求削减次序完全一致，再次印证 5.2 节的结论。两端的差距可量化本文设计的两条轴：代价感知 W-TinyLFU 相对原生 W-TinyLFU 的请求数低 10.9%，相对去掉准入过滤器的 SLRU 低 31.4%，相对纯近因的 LRU 低 48.8%。

#### 5.4.3 选型依据：墙钟持平，代价显著更低

本文方案与中位数最快的 SIEVE 在墙钟上**不分伯仲**：两者相差仅 0.26%。选型因此取决于达到同等墙钟所付出的代价，而本文方案在四项代价指标上均明显更优：**峰值堆低 3.61 GiB（13%）、请求数少 1,827 次、垃圾回收时间少 1.68 s、淘汰量低两个数量级（0.44 对 64.13 GiB）**。同时其命中数为全矩阵最高（139,559），高于 SIEVE 的 137,732。

两项机制解释了这组代价差异。

**请求级原子准入使同等字节覆盖更少的请求。** 本文方案与 SIEVE 的远端字节几乎相同（210.65 对 210.64 GiB），但请求数少 1,827 次，即平均单请求由 4.81 MiB 增至 5.01 MiB。其原因是本文以一次 Range GET 为准入的原子单位：缓存中保留的是完整的逻辑读取单元，一次命中即可消除一次完整的远端请求；而逐块准入会留下部分覆盖的区间，后续读取仍需发出请求才能补齐缺失的块，字节虽被节省而请求未被消除。该结果与 4.2.2 节采用请求级原子准入的设计动因一致。

**代价感知的准入判据使缓存周转趋近于零。** 本文方案仅在候选请求的收益严格超过其将挤占的全部 victim 的收益之和时才准入。缓存填入高收益内容后，后续候选难以越过该门槛，因此准入与淘汰均大幅减少，淘汰量仅 0.44 GiB，而其余六种算法均在 64 GiB 以上。低周转直接降低了瞬时对象的分配量，这同时解释了更低的峰值堆与最短的垃圾回收时间。

由于内存缓存层的可用容量受限于单机可分配堆（见 5.5 节），在墙钟相当的前提下更低的堆占用意味着同等资源下更大的可用容量或更高的同机并发。本文因此采用代价感知 W-TinyLFU。

### 5.5 缓存容量曲线与内存缓存的适用边界

主实验将缓存容量固定为 4 GiB。本节给出该取值的依据，并回答一个关于系统形态的边界问题：何时纯内存缓存已经足够，何时需要继续扩大容量乃至引入堆外或本地 SSD 分层。为避免事后挑选判据，本文在测量之前预先注册了两道门禁：**G0（设备门禁）**要求候选分层介质的随机读命中延迟显著低于远端对象存储的 GET 延迟；**G1（容量门禁）**要求在统一堆上限下，容量大于参照臂的各臂须取得不低于 5% 的墙钟降幅，且逐轮配对差值方向一致。

本节在两个压力比截然不同的负载上测量容量曲线：ClickBench SF8（4 GiB 下压力比 0.68）与 NYC Yellow Taxi（压力比 6.5）。两组曲线的形态相反，而 5.5.3 节表明二者是同一条曲线上的两个采样位置。

#### 5.5.1 设备门禁与低压力比负载上的饱和

G0 在 AWS `m5dn.4xlarge` 上以 `fio`（`O_DIRECT`、`randread`、队列深度 1）测量。在代表缓存命中粒度的 64 至 256 KiB 块上，实例存储 NVMe 的 p99 延迟为 0.18 至 0.51 ms，约为同区 S3 小请求 p50（23.6 ms）的 1/46，**G0 通过**。EBS 在 4 MiB 及以上的块上 p99 达 34.3 至 59.0 ms，慢于远端 S3，因此不可作为缓存介质。

设备足够快并不意味着容量构成瓶颈。在 ClickBench SF8 原始布局（111.99 GiB，43 条查询，独占 NVMe scratch，n=3）上扫描无缓存、4、8 与 16 GiB 四臂，曲线早期饱和：

| 臂 | 容量 | 压力比 | 中位数 (s) | 相对前一档 | GET | 淘汰 GiB |
|---|---:|---:|---:|---:|---:|---:|
| 无缓存 | — | — | 2286.6 | — | 262,309 | 0.00 |
| 4 GiB | 4 GiB | 0.68× | 1954.6 | **+14.5%** | 75,605 | 0.29 |
| 8 GiB | 8 GiB | 0.34× | 1905.8 | +2.6% | 56,480 | 0.00 |
| 16 GiB | 16 GiB | 0.17× | 1913.0 | −0.38% | 43,961 | 0.00 |

收益集中于首档：装入 4 GiB 缓存使墙钟下降 14.5%，此后 4→8 GiB 仅再降 2.6%，落入 2% 至 5% 的不确定带；8→16 GiB 为 −0.38% 且三轮配对差值符号翻转，**G1 未通过**。

该饱和的机制可由淘汰与准入数据直接读出：8 GiB 与 16 GiB 两臂的整轮淘汰字节均为 0.00 GiB，淘汰后再次被请求的块数分别为 1 与 0，而被准入环节拒收的块为 59,266 与 21,150。由于本地 SSD 分层的作用在于承接由内存层淘汰出的块，当淘汰本身为零时，增加慢速下层介质无从发力。ClickBench SF1 的七臂扫描（128 MiB 至 16 GiB，n=5）进一步显示工作集封顶：4 GiB 与 16 GiB 两臂的峰值驻留缓存均停在 2.67 GiB，远端请求数（4,798）与远端字节（36.2 GiB）逐位相同。

#### 5.5.2 高压力比负载：NYC Yellow 上的断崖跨越

ClickBench 的饱和结论不可外推。在本文的五个负载中，TPC-H 虽然单查询读取量亦远超容量，但布局重构可将文件数由 2,130 收至 514，把可复用内容推入 4 GiB 窗口（命中率由 12.3% 升至 59.1%，见 5.3.5 节）。NYC Yellow Taxi 的结构与之不同：布局重构通过放大行组将请求数由 121,730 压至 9,266（−92.4%），但**完全不减少单轮扫描的字节量**，因此两种布局下的压力比均维持在 6.5 左右，缓存在两侧均处于失效区（原始布局下请求仅削减 10.7%，重构布局下墙钟仅降 7.5%）。对这类负载，容量是跨越断崖的唯一杠杆。

本文在单请求固定成本最高、因而检出力最强的 COS 环境上，对 NYC 原始布局（39.27 GiB，204 文件，4 个 epoch）扫描六臂，n=5，六臂统一使用 48 GiB 堆。各臂的最大容量先经 n=1 冒烟确认堆可行性后方进入正式扫描。单轮 epoch 的完整工作集实测为 25.98 GiB（56,600 个逻辑块），故 32 GiB 臂的驻留缓存受工作集封顶，其有效压力比为 1.0。

| 臂 | 压力比 | 中位数 (s) | 单档步进 | 相对 4 GiB（配对） | GET（相对无缓存） | 峰值缓存 GiB | 命中率 | tee 效率 | 峰值堆 GiB |

#### 5.5.3 一条曲线：拐点位于压力比等于 1 处

将两组实验按压力比而非绝对容量排列，形态上的对立随即消解：

| 负载 | 步进 | 压力比区间 | 单档收益 |
|---|---|---:|---:|
| NYC | 2→4 GiB | 13.0 → 6.5 | +8.1% |
| NYC | 4→8 GiB | 6.5 → 3.25 | +13.8% |
| NYC | 8→16 GiB | 3.25 → 1.63 | +23.8% |
| NYC | 16→32 GiB | 1.63 → **1.0** | **+34.6%** |
| ClickBench | 4→8 GiB | 0.68 → 0.34 | +2.6% |
| ClickBench | 8→16 GiB | 0.34 → 0.17 | −0.38% |

两个负载的十个臂落在同一条以压力比为自变量的 S 形曲线上，**拐点位于压力比等于 1 处**，即容量恰好覆盖单轮工作集之时。该位置并非拟合所得，而由两侧的直接观测确定：NYC 在压力比 1.0 处出现零拒收、零淘汰与理论上限的 tee 效率，继续扩容不再产生命中；ClickBench 的全部臂（0.68、0.34、0.17）均已位于该点右侧，故其扩容收益为 +2.6% 与 −0.38%。

因此 ClickBench 上的饱和并非该负载不需要容量，而是其容量在基准配置下已经过剩；NYC 上的陡降亦非另一类行为，而是同一规律在拐点左侧的表现。两个看似矛盾的结论由单一参量统一。

这同时确定了主实验的容量取值。本文五个负载中有三个（ClickBench、Criteo、NovoMCP）的压力比低于 1.2，4 GiB 已使其处于收益平顶；其余两个（TPC-H、NYC）则需要更大容量，而 TPC-H 可由布局重构降低压力比（5.3.5 节），NYC 不可。故 4 GiB 是覆盖多数负载的合理取值，而非对全部负载的最优配置——本文的主结果因此在压力比较高的负载上低估了缓存的潜力。

一项附带观察是，在容量充足时两个机制成为替代而非互补：仅靠扩容即可在**原始布局**上取得 63.9% 的墙钟降幅（659.07 → 237.84 s），与布局重构单独取得的 67.2% 接近。这与 5.3 节的结论一致——二者都以削减请求数为作用面，差别在于一方缩短重用距离、另一方直接容纳工作集。需要说明的是，上述两个数值取自不同网格（容量扫描为 48 GiB 堆，2×2 网格为 32 GiB 堆，无缓存基线分别为 659.07 与 632.04 s），故仅可比较量级而不宜直接相减。

#### 5.5.4 内存层的边界

缓存容量的上限由单机可分配堆给出。本文实测的边际堆代价为：无缓存至 4 GiB 一档为 2.85 至 3.80 倍，而 8 GiB 以上各档收敛至 1.09 至 1.19 倍。较高的首档倍率主要来自启用缓存的一次性开销——命中路径上存活的 SDK 与 Spark 对象、tee 缓冲区等，不随容量线性放大；在零拷贝与共享底层数组的实现下，**缓存本体的边际堆代价接近 1:1**。峰值堆的绝对值则同时由查询引擎自身的执行内存决定：ClickBench 16 GiB 臂达 45.2 GiB（堆上限的 94%），而 NYC 同容量下为 26.09 GiB（56.9%），二者的无缓存基线分别为 8.3 与 3.05 GiB。

关键的观测出现在 NYC 的 32 GiB 臂上。该臂是全部容量实验中**唯一触发堆水位告警的配置**：五轮峰值堆中位数为 40.49 GiB，占 48 GiB 上限的 84.4%，单轮最高 41.18 GiB（85.8%），而其余五臂均在安全水位之内。其构成为 25.98 GiB 的缓存驻留数组加约 13.7 GiB 的执行内存。若按本文主实验所用的 32 GiB 驱动堆配置，该臂直接不可运行。

由此，NYC 给出了一个完整且收敛的边界论证：

1. **收益是真实且大幅的**——跨越压力比断崖需约 26 GiB 容量，可换取 63.9% 的墙钟降幅；
2. **该容量恰好越过堆内缓存的安全水位**——26 GiB 缓存对应约 40 GiB 峰值堆，占 48 GiB 上限的 84%，且在常见的 32 GiB 堆配置下不可达；
3. **因此 16 GiB 以上的容量应当下沉到堆外或本地 NVMe 介质**，而非继续占用 JVM 堆。

设备侧的可行性已由 G0 确认：NVMe 在命中粒度上的 p99 延迟约为远端 GET p50 的 1/46，单盘 279 GiB 的容量足以容纳上述量级的工作集。本文据此将分层缓存列为未来工作，而非在当前实现中引入。

需要指出该论证的适用边界。上述结论建立在单机 62 GiB 内存、48 GiB 堆的配置之上；堆预算更充裕的部署可以把更大的容量留在堆内。但 5.5.2 节的线性关系表明所需容量与单轮工作集成正比，因此当工作集增长至数百 GiB 量级（生产规模的训练扫描），或单机需为多个并发租户各自保留工作集时，所需容量将超出任何单机堆配置——此时分层由"更优"变为"唯一可行"。

#### 5.5.5 由容量曲线导出的两项后续工作

本节结果直接指向两项相辅相成的后续工作。

**容量的自适应配置。** 本文主实验为保证各负载间的公平比较而固定 4 GiB 容量，该取值对压力比低于 1 的负载处于收益平顶，但对 NYC 这类负载仅兑现了其潜力的一小部分（4 GiB 下墙钟降 16.0%，而 26 GiB 下可达 63.9%）。由于单轮工作集可由本文已有的请求级轨迹在线估计，而收益与容量占工作集之比近似线性，容量具备按负载自动配置的可行基础：目标是使压力比趋近 1，同时在堆水位接近上限时停止增长。本文的 ghost 表与反事实遥测已为该决策提供所需信号（拒收后再被请求的块数在 4 GiB 下为非零，在 32 GiB 下为零），其完整的自适应策略留待后续工作。

**堆外与本地 SSD 分层。** 自适应容量在堆上限处必然终止，而 5.5.4 节表明该上限在高压力比负载上恰好落在收益仍然陡升的区间内。两项工作因此相互依赖：自适应容量决定"应当缓存多少"，分层介质决定"这些容量能否被提供"。在压力比高且工作集超出堆预算的负载上，二者缺一则无法兑现本节测得的收益。

ETag 在响应元数据上，不在字节流里。命中时用对象键到旁边的 `etags` 表取上次真实 GET 写下的 ETag。有值就做成 `GetObjectResponse`，只填这个 ETag 和 `contentLength`，再和这条流一起装进 `ResponseInputStream` 交给 S3A。

未命中时，在 GET 发出之前先进行尺寸过滤：大于 8M 的请求直接发 exact-range GET 绕过缓存，小于等于 8M 的进入 `CachingTeeStream`。8M 是单次 fetch 的物理上限。`CachingTeeStream` 会按整个请求长度分配一块连续的 `byte[length]`，边读边收满，再把这一整块交给 W-TinyLFU。超过 8 MiB 的一般是一次扫很大一段；先复制进这块数组，拒收就白占堆，收下又是一整块连续的 backing。而且只读一次的大扫描频率低，收了也很难通过 w-tinylfu 进入缓存。

未命中且长度不超过 8 MiB 时，`openTee` 先发出原来的 exact-range GET，再把 S3 响应体包进这条流交回去。S3A 调用 `read(buf)` 时，流先从 S3 响应体读进 S3A 自己的数组，再把这 `n` 个字节 `arraycopy` 到内部的 `buf`，从 `filled` 接着写。调用方拿到的就是刚从 S3 读到的那些字节。
`buf` 写满后，`publishIfComplete` 把这块数组、起始偏移和响应里的 ETag 交给 `cache.put`，由 W-TinyLFU 决定收不收。这一步发生时，S3A 已经拿全了这 `length` 个字节。没收进去的话，这块数组随后可以被回收。没读满就关闭或读到末尾时，`filled != buf.length`，不会入库。
block 是逻辑块。长条的 buffer 读满后直接存入 cache 中，用 dataoffset 标注块切分处，指针指向切分处。（这也是请求级原子准入而非块级原子准入的原因）
