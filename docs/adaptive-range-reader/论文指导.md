## DB2 论文对 L0/L1 方法部分的启发
下面按"论文怎么讲 → 对你有什么启发"来说。

一、论文中与"候选计划"相关的四处机制
1. 问题定义只有一句话（§4 开头）

"Given a workload W (a set of SQL statements...), a set of selected features F, and a disk space constraint D, find a set of recommendations for F that reduces the total cost of W the most, while using no more space than D."

然后紧接着给出搜索空间规模的量化恐吓：2^(NI+NM+NP+NC)，理由是不同 feature 会相互影响。先定义问题、再量化空间、最后才说方法——这个三段式是整篇 overview 的骨架。

2. 候选生成与候选估价是引擎里两个独立的"模式"（§5.1）

这是你 L0/L1 真正的源头。DB2 把优化器改造出两个 EXPLAIN 模式：

RECOMMEND INDEXES：语句只编译不执行，优化器在飞行中生成"虚拟"索引（virtual indexes），像物理存在一样参与优化；只有进入最终最优计划的那些虚拟索引才被当作该语句的候选，写进 advise_index 表。
EVALUATE INDEXES：从 advise_index 里取出标了 in_use 的候选，在优化前生成对应虚拟索引——"causes the virtual indexes in the advise_index table to act as a temporary extension to the DB catalog information"，然后重新优化拿代价。
客户端循环就四步：get workload → get candidates → try candidates → output results（Figure 1）。

注意两个细节很关键：

候选不是枚举出来的，是让优化器自己说它想要什么（"it is able to find candidates quicker and more accurately"）——天然带了一层剪枝。
估价阶段候选是"目录的临时扩展"，也就是假装已经建好再算一次代价。这就是 what-if。
3. 依赖强弱分类 + hybrid 搜索（§4.2–4.3，Table 1）

论文没有对所有维度一视同仁。它先定义：

"feature A 'strongly' depends on feature B, if a change in selection of B often results in a change in that of A."

然后给出一张 4×4 的 S/W 表（注意不对称：partitioning 强依赖 MQT，反之不成立），再据此决定搜索结构：

依赖关系	处理方式
互为强依赖（index ↔ MQT）	合成一个 component 联合搜索
单向强依赖（P 依赖 IM）	迭代，但强制 A 先于 B
弱依赖	拆开，顺序任意；但允许 component 内部做一次"quick and simple search"以免完全丢失弱依赖
最妙的是他们用实验验证了弱依赖假设：原型里让 IM 和 P 来回迭代，发现"the second invocation of IM (with the solutions for partitioning) does not change the previous index and MQT recommendations significantly. This actually verifies our assumption that indexes and MQTs only weakly depend on partitionings. Therefore, we currently only iterate through each component exactly once."

二、对你 overview 的直接启发
你现在的 §3.3 把 L0/L1 写成了两段紧凑的技术说明。参照这篇论文，我建议改成先立框架、再填内容：

(1) 用一句话给出形式化问题定义，和 DB2 同构。 例如：

给定 SDK 观测到的字节访问轨迹 T 与 Parquet footer 元数据 M、一组启用的布局维度 F ⊆ {列顺序, 行组, 文件大小, 压缩+编码, 页几何}、以及一组可行性约束 C（schema 排列合法性、目标 writer 能力、page ≤ row group、RG ≤ 128 MiB、scan task 数不低于基线），求一个布局计划，使估计的 t_io 最小。

这样 L0 就不是"一堆检查项"，而是约束集 C 的实现；L1 不是"一个公式"，而是目标函数的实现。读者立刻知道它们各自在框架里的位置。

(2) 明确借用 generate → gate → price → select 的四段式，并指出你和 DB2 的分工不同。 DB2 的 RECOMMEND 模式之所以不需要独立的 L0，是因为优化器本身就是合法性的守门人——它生成的虚拟索引天然合法，不合法的设计根本不会出现在计划里。而你的执行器（pyarrow.parquet.ParquetWriter）在规划器之外，没人替你守门，所以你必须把 L0 显式化。这正是你文档里那句"能力检查按目标 renderer 做，并且在排名之前"的理论依据，值得在 overview 里写成一条设计原则：

没有优化器可借时，what-if 必须拆成两层：L0 回答"这个计划能不能被目标 writer 真实渲染出来"，L1 回答"如果渲染出来值不值"。先门禁再定价，避免把不可实现的点排进榜单。

把"312 个合法点 / 72 个被 L0 拒绝"这个数放到 overview 里——它和 DB2 那个 2^(NI+NM+NP+NC) 起的作用一样，是"我确实面对了组合空间并且把它收住了"的证据。

(3) 补一张 6×6 的维度依赖表。 这是我认为最值得抄的一点。你现在 §3.2 的六维表只说了每维"是什么"，没说"维之间什么关系"，于是 §3.3 里那些设计决策看起来像是经验之谈。有了 S/W 表，它们立刻变成推论：

你的做法	用 DB2 的语言解释
压缩和编码按 (codec, encoding) 联合元组实测定价，"不做两个比例相乘"	二者互为强依赖 ⇒ 必须联合搜索，这是 integrated 的部分

(4) 把你的 2×2 网格重新定位成"弱依赖假设的验证实验"。 这是我读完论文后觉得对你最有价值的一点。DB2 验证 IM 弱依赖 P 的办法是"再跑一遍 IM，看推荐有没有变"。你的 reconfiguration 与 caching 之间，用的是同一个逻辑：

单独 reconfiguration：−14.5% (SF1)
单独 caching：−14.9% (SF1)
两者叠加：−21.7%
你现在把这张表当"最终结果"呈现。但它同时是一个结构性论证：两条路线弱依赖，因此可以用 hybrid/iterative 方式分别优化而不损失太多——这就解释了你为什么有资格把两部分分开设计、分开评测，而不必做一个联合搜索。建议在 overview 里就把这句话说出来：

reconfiguration 改变"字节放在哪里"，caching 改变"字节要不要再传一次"。二者在 DB2 Design Advisor 的意义上是弱依赖的：布局重排不改变缓存的准入逻辑，缓存也不改变 footer 几何。2×2 网格既是最终结果，也是这一弱依赖假设的实证检验——叠加收益接近但不等于两者之和（−21.7% vs 朴素相加 −29.4%），差额来自二者都在削减同一批重复 GET。

顺带一提，这个"接近但不等于相加"的差额，恰恰是弱依赖而非完全独立的证据，值得显式分析一句，比单纯报 −21.7% 有信息量得多。

(5) 把 §3.6"已测试并否决的分支"升级成停止准则。 论文 Figure 5 的结论是"a large portion of the performance improvement is achieved in a relatively short amount of time... Subsequent searching only further improves the performance marginally. This is very useful for designing the stopping criteria"。你的 order_refined（−0.89% 但 GET +2.4%）、decode_veto（−1.14% 不稳定）、叠加后 −0.18% 落在噪声里——这组数据讲的是同一个故事：确定性算法一次出手就吃掉了大部分收益，精化阶段进入噪声区。按这个框架写，否决就不是"我们试了但失败了"，而是"我们据此确定了停止准则"，说服力完全不同。

(6) 补一组"L1 排序保真度"的数据。 DB2 敢把 88.01% 和 84.54% 并排放，是因为那是它全部的信誉来源。你很克制地写了"L1 只用来给候选排序，不预测墙钟"——这个限定是对的、也更诚实，但只要你声称是"排序器"，就该给出排序质量的证据。哪怕只是把 2×2 网格那几个点（baseline / joint2，以及 §3.6 里几个被否决的候选）的 L1 预测名次与实测墙钟名次做个秩相关，也比完全不给强。如果数据不够，至少说明"L1 在被实际写出并实测的 N 个点上，预测方向与实测一致 N/N 次"。

(7) 保守主义原则值得明写。 DB2 §5.5 不删索引（怕没看到完整 workload）；你的对应物有两处——Track1 任何内部异常回退 passthrough（"性能决策上的错误不能变成查询失败"），以及 L1 对行组/页几何保持 baseline（证据不足就不动）。这两件事看起来不相关，其实是同一条原则在在线和离线两侧的体现：在部分观测下，默认动作是不动。这条可以作为 overview 里的一个设计原则单列，很能提升整篇的理论密度。

三、一个需要注意的差异（别抄错的地方）
DB2 的候选是优化器替它生成的（RECOMMEND 模式），所以它的候选集天然"语义相关"且已剪枝。你没有优化器，候选来自 plan_deterministic.py 的确定性算法（共访问矩阵上的贪心 seriation、实测压缩比探测等）。这意味着：

你不能照搬"只保留出现在最优计划里的候选"这条剪枝——你没有最优计划这个概念。你的等价物是"每一维生成有限候选 + baseline 兜底"，剪枝靠 L0 和维度分解，而非靠优化器的内在选择。这个区别在 overview 里讲清楚，会显得你对两者的差异有自觉，而不是简单套用。
反过来，你有 DB2 没有的优势：你的"workload"是字节级真实轨迹，不是 SQL 文本。DB2 需要 workload compression（top-K 最贵查询，X% 阈值，三档 60/25/5）来控制优化器编译次数；你的成本结构完全不同——瓶颈不在"编译 43 条查询"，而在"重写 112 GiB 数据"（SF8 写出 64 分钟）。所以你的 overview 不该提 workload compression，而应该强调计划评估廉价、计划落地昂贵，这正是为什么你必须在写出之前把 L0/L1 做扎实——DB2 可以反复 what-if，你只有一次重写机会。这个不对称性是你方法论的真正动机，值得在 overview 里占一段。
如果你要在 related work 里引用，建议的引用姿态是：沿用其 generate/evaluate 两阶段与依赖强弱驱动的 hybrid 搜索框架，但在没有查询优化器、且仅有 SDK 字节轨迹与 footer 作为证据的设定下，把 what-if 重构为"显式可行性门禁（L0）+ 外部解析代价模型（L1）"。

## L1怎么做的
读完 whatif.py（L1 的实现本体）、virtual_footer.py（候选的"虚拟 footer"）、advisor_policy.py（常量与承认的模型盲区）、sysconst.py（RTT/BW/K 的拟合）。L1 的估价不是"一个公式",而是一套以实测总量为锚、只预测比率的差分定价。下面按实际执行顺序讲。

0. 候选长什么样：虚拟 footer
virtual_footer.py 开头就把定位写明了：

virtual_footer.pyL2-L7
"""Virtual footer: predict Parquet geometry without rewriting the data.

This is the lakehouse stand-in for DB2's virtual indexes. A candidate exists
only as predicted metadata -- file count, row-group count, per-column chunk
sizes and the physical order they sit in -- and L1 prices the reader's request
plan against that.
"""
predict_geometry(table, candidate) 从实测基线几何缩放出候选几何：先按压缩比算出 compressed 总字节，再由目标文件大小推 n_files、由目标 RG 大小推 n_rg，然后用 Spark 的分片规则算出 n_scan_units（ceil(size/128MiB) 求和）和 n_scan_tasks（复刻 FilePartition.getFilePartitions 的 next-fit 装箱，含 openCostInBytes）。注意它刻意不做取整美化：

virtual_footer.pyL427-L430
Baseline (no file-size or row-group action) is replayed as measured:
fractional `rg_per_file` is kept, and `n_rg` is *not* rounded up to a
multiple of `n_files`. That rounding used to turn ClickBench's 165 row
groups into 220 before L1 ever priced a point.
1. 目标函数
核心三行在 evaluate_pattern：

whatif.pyL250-L252
requests = data_gets + scan_meta + heads
nbytes = data_bytes + scan_meta_bytes
t_io = (requests * rtt + (nbytes / bw if bw else 0.0)) / k
即 t_io = (请求数 × RTT + 字节数 / BW) / K_eff。三个系统常数都是拟合出来的，不是设的（sysconst.py）：

常数	怎么来的
rtt_s	<64KiB 请求桶的中位延迟——这个尺寸下传输可忽略，剩下的就是纯固定成本
bw_bps	(大桶中位字节 − 小桶中位字节) / (大桶中位延迟 − 小桶中位延迟)，即边际传输率，天然剔除了固定成本
K_busy	Σ单请求延迟 / union(请求在飞区间)——只统计"至少有一个请求在飞"的时间，所以查询间隙的空闲已被排除
K_eff 取三者下限（whatif.py:248）：

python
k = max(1.0, min(k_busy, geom.get("n_scan_units") or geom["n_files"], PARALLELISM))
PARALLELISM = 16 是冻结的 local[16]。这一步的含义是：并发不可能超过有多少个可独立扫描的分片——这也是 L0 要守一条"scan task 数不低于基线"的原因（见第 5 节）。

3. 列序为什么能被定价：_merge_one
比率里唯一真正"算"出来的是 gets_per_rg，由 merge_gets → _merge_one 完成。它复刻了冻结 reader 的 vectored 合并规则（min_seek=128KiB、max_merged=2MiB），按候选的物理列序走一遍：

virtual_footer.pyL604-L618
for col in order:
    b = float(sizes.get(col, 0.0))
    if col in wanted:
        if run and run_bytes + b > max_merged and b > max_merged:
            flush()
        run.append(b)
        run_bytes += b
    elif run:
        if b > min_seek:
            flush()
        else:
            run.append(b)
            run_bytes += b
flush()
三条语义：

要读的列加入当前 run（连续区间）；
不要读的列如果大于 min_seek，触发 flush()——这是一次 seek，run 结束，GET 数 +1；
不要读但小于 min_seek 的列被吞进 run：GET 数不增，但它的字节计入 run_bytes，也就是"读穿过去的浪费字节"。
flush() 内部再按 max_merged 把一个 run 切成 ceil 份。于是"热列相邻"的收益被精确表达为：run 变长 → 被 flush 的次数变少 → GET 数下降；代价是吞进去的冷列字节上升。这两个方向同时体现在 merge_gets_ratio 和 merge_bytes_ratio 里，L1 不需要额外规则去权衡——RTT 和 BW 的比值自己会决定哪边划算。

每 RG 的列字节来自 footer 实测样本（_rg_size_maps 用 RG_CHUNK_SAMPLES，多个样本取平均），per-column 的 codec/encoding 改变只是给对应列乘一个实测比率 ratios[col]；没测到的元组不乘（保持 baseline 字节），宁可低估该动作也不编造比率。

4. 三条独立的流量轴
除了数据 GET，L1 还分开定价三类元数据流量，各自按不同的量缩放：

轴	缩放依据	代码
数据 chunk GET	merge_gets 比率 × n_rg 比率	evaluate_pattern:232
scan-span 元数据（footer / page index，每个 split 一次）	n_scan_units 比率	_scan_scale → whatif.py:239
file-discovery 元数据（listing / footer 发现，每个对象一次）	n_files 比率	_file_scale → _file_meta
HEAD	HEAD_PER_OPEN × episodes × scan_scale	whatif.py:241
page index 字节	只算字节，不算往返	_page_index_bytes
最后一条是刻意的"单边定价"。_page_index_bytes 的 docstring 说明理由：

whatif.pyL393-L395
Bytes only: the page index rides inside the metadata range the reader
already issues, so changing the page size makes that range fatter or
thinner without adding or removing a round trip.
而且页轴只能亏不能赚——advisor_policy.py:41-51 写明 PAGE_RANGE_INTERSECTION = False：要知道页跳过的收益就得知道谓词消除了哪些页，而谓词正是这个 advisor 拒绝读的输入。于是页几何被设计成"结构上只有成本、没有收益"，再配一个 PAGE_SWITCH_MARGIN = 0.02 的阈值——赢不到 2% 就不动。这正是你文档里"变化小于 2% t_io 时不动"的出处。

5. 为什么 t_io 排序就等于墙钟排序
这是 L1 敢于"只排序、不预测墙钟"的理论依据，写在 whatif.py 的模块 docstring 里：

whatif.pyL13-L19
r5 simplified this in one structural way worth stating plainly. v1's actions
(sort, partition) changed *which rows* a query read, so the model needed a
selectivity estimate... None of the six v2 actions change the
row set: every candidate reads exactly the same data, just laid out
differently. So the residual is a constant across candidates, ranking by t_io
is ranking by t_e2e, and the whole CDF/prune apparatus is gone.
六维动作都不改变读到的行集，所以执行残差（filter / aggregation / shuffle 的 CPU）对所有候选是同一个常数 → t_io 的序 = t_e2e 的序。--residual-s 只是为了让打印出来的 t_e2e_s 能和实测墙钟对照，不参与排序。

这个论证有一个洞，而且是显式记录而非掩盖的：codec 改变会移动 decode CPU，它落在残差里，不是常数。于是 decode 被单独定价、单独报告、但不进排序：

advisor_policy.pyL112-L117
# Whether the ranking is allowed to spend the decode term. L1 can *price*
# decode as soon as a layout probe (encoded bytes) and a decode probe (rates)
# are both bound -- `t_decode_s` appears in every evaluation either way. This

注意 decode 用的是自己的除数 k_decode（whatif.py:260），不复用 K_busy——因为 K_busy 本身低到 7 就是因为任务有一部分时间在 decode 而不是等 S3，用它去除 CPU 项等于把 IO 空闲重复计费一次。而且报告的是 decode_core_s（核秒，可直接对账 event log 的 Executor CPU Time）和 t_decode_s（除以并行度假设）两个数，只有前者会被拿去和测量对比。另有一条保守规则：任何一个 pattern 的 decode 定不了价，整体就标为 unpriced（whatif.py:459-464），否则"未测元组更多的候选反而报出更小的 CPU 账单"。

6. 排序之前的三道闸
L1 的输出不是直接拿来排名，中间有三层拦截：

(a) L0 门禁（l0_check）：先过 layout_actions.check_l0（列序必须是 schema 的排列、codec 可读、encoding 与物理类型匹配、writer 能力矩阵），再加几何硬界——RG ≤ 128 MiB（因为 parquet-hadoop 把 vectored 超时硬编码成 300s，M2 金丝雀的 35–182 MiB range 直接超时）、文件数 ≥ 2、RG 数 ≥ 4、文件数 ≤ 20000、以及并行度地板：

这条尤其值得注意：它是为了堵住 L1 自己的已知盲区而存在的 L0 规则——L1 把 I/O 除以 K 得到的是总量，看不见"最慢任务决定墙钟"，所以干脆禁止候选减少任务数。还有一个顺序细节：能力检查必须在 strip_for_spark 之前做，否则所有候选都会通过 parquet-mr 的检查，然后 L1 给 UC2 定了一个 renderer 根本写不出来的布局（whatif.py:99-102）。

(b) 基线自洽回放（run_validate）：用 L1 给 baseline 定价，预测的 GET 数和字节必须和"建模所用的那份轨迹"实测值相差不超过 VALIDATE_TOL = 10%，否则拒绝进入搜索：

这一步相当于 DB2 的 Figure 2 第 2 行"get initial cost of the workload"，但严格得多——DB2 只是拿基线代价当比较基准，你这里还要求模型能复现它自己的输入才允许发言。

小结：L1 到底是什么
一句话：L1 是"冻结 reader 的请求计划"在虚拟 footer 上的重放器。它不预测墙钟，只做三件事——

用 footer 实测的列字节 + 冻结的 vectored 合并规则，算出候选列序/几何下每 RG 的 GET 数与字节数；
把它与基线的同一量作比，乘到轨迹实测的总量上，得到候选的请求数与字节数；
代入 (requests × RTT + bytes / BW) / K_eff，其中三个常数全部从同一份轨迹拟合。
它的诚实之处在于把三个盲区都显式化了：页跳过不定价（需要谓词）、decode CPU 定价但不排名（量级太小且未独立标定）、关键路径看不见（由 L0 的任务数地板代偿）。

对照 DB2：它的 EVALUATE 模式把虚拟索引当作目录的临时扩展，交给优化器重算代价；你的虚拟 footer 把候选当作 footer 的临时替换，交给一个你自己写的、只有三个拟合常数的解析模型重算请求计划。DB2 的代价模型是既有资产（优化器），你的代价模型是本工作的产出之一——所以你比 DB2 多了两道它不需要的闸：基线自洽回放（证明模型可信）和写出后的分项对账（证明模型没骗人）。这一点在 overview 里值得明写。
