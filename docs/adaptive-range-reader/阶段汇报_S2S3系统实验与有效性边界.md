# 阶段汇报 —— 自适应 Range Reader 落地 AWS SDK（S2/S3）与有效性边界

> 对应 `PROJECT2.md` §7.3（S2/S3 实施）、§8.1–8.5（评测方法与结论）、§9 更新日志（2026-07-28）。
> 汇报范围：把 Track 1 从离线 simulator POC 迁移进 AWS SDK 之后的**系统实验结果**，
> 明确区分**有效果**、**没有效果/被证伪**，以及过程中发现的**评测口径问题**。
> 全部原始数据见本文 §6「实验产物索引」。

---

## 0. 一句话结论

在真实 SDK 实现上，**「缓存 + 策略路由」确实有效（有 RTT 时 IO 时延 −23.7%）**；
**「异步预取」无效（相对无预取仅 +1.6%，即打平略亏）**；
而**「学习式选择器优于手写规则」这件事的成立与幅度，强依赖缓存预算工况**
（远端字节增益从 8MiB 下的 **+1.0%（更差）** 到 256MiB 下的 **−16.2%**）。

本阶段最有价值的产出并非某个性能数字，而是**发现并修正了四处评测口径缺陷**——
它们此前会系统性地误判整个方法的价值（§5）。

## 1. 本阶段做了什么

### 1.1 系统实现（SDK 侧）

| 内容 | 说明 |
| --- | --- |
| S2 自适应 reader | 决策树选策略 + 4 个策略执行器 + 字节预算 page cache；关闭时行为与原生 `getObject` 逐字节一致 |
| S3 异步预取 | `Prefetcher`（in-flight 去重 / 取消 / 回退）+ 统一进程级预算 + **appID 环境隔离**（每 app 独立 cache/预算/指标） |
| `template_auto` 手写基线 | `RuleBasedPolicySelector`，按 IO 形状阈值路由到**同 4 个执行器**，作为「学习式到底有没有用」的对照 |
| `SelectorMode` public API | `DECISION_TREE` / `TEMPLATE_AUTO` 可在部署时切换 |

### 1.2 评测基础设施（本阶段新增，是主要工作量）

| 工具 | 作用 |
| --- | --- |
| `AdaptiveReaderSystemBenchmark` | 四模式对照系统基准：`passthrough` / `template_auto` / `S2(learn,d0)` / `S3(learn,d1)` |
| RTT 成本模型注入 | `-Ds3arr.rttMs/bwMiBps/thinkMs`，把 `rtt + bytes/BW` 作为**真实延迟**注入每次 GET，使时延维度可测 |
| `tools/build_mixed_trace.py` | 5 类负载均衡、保结构的综合 holdout trace（11189 reads） |
| `tools/policy_agreement.py` | oracle 命中率诊断：逐读比较各 selector 的选择与最优策略 |
| `tools/label_flip_check.py` | 标签是否随缓存预算翻转（「是否该重训」的前置判据） |

## 2. 有效果的部分

### 2.1 缓存 + 策略路由：有 RTT 时时延显著下降 ✅

综合 trace（11189 reads），成本模型 `rtt=5ms, bw=200MiB/s, think=5ms`，预算 64MiB：

| 模式 | IO 时延 | GET 数 | 读放大 | 缓存命中率 |
| --- | --- | --- | --- | --- |
| passthrough（关闭） | 75.96s | 11189 | 1.000 | 0 |
| template_auto（手写） | 60.46s | 6633 | 1.366 | 0.407 |
| **S2（学习式）** | **57.96s（−23.7%）** | **6294（−43.7%）** | 1.293 | 0.437 |
| S3（+异步预取） | 58.90s | 7264 | 1.601 | 0.431 |

> 产物：`results/report-rtt-mixed-20260728-155127.txt`

**注意这是一个权衡而非纯赢**：64MiB 下缓存以**多抓 29% 字节**换取 −43.7% GET 与 −23.7% 时延。
在带宽受限而非 RTT 受限的场景，该权衡方向会反转。

### 2.2 学习式优于手写规则，且优势随预算单调放大 ✅

缓存预算扫描（同一 trace，零-RTT，指标为确定性的 IO 形状）：

| 预算 | 读放大（pt / 手写 / **S2** / S3） | S2 vs 手写（远端字节） |
| --- | --- | --- |
| 8MiB | 1.000 / 1.429 / **1.444** / 1.770 | **+1.0%（学习式反而更差）** |
| 32MiB | 1.000 / 1.394 / **1.412** / 1.679 | **+1.3%（仍更差）** |
| 64MiB | 1.000 / 1.366 / **1.293** / 1.601 | −5.3% |
| 256MiB | 1.000 / 1.094 / **0.917** / 0.953 | **−16.2%** |
| 1024MiB | 1.000 / 0.716 / **0.610** / 0.632 | −14.8% |

> 产物：`results/benchmark_results.csv`、`results/report-sweep-*.txt`

两个要点：

1. **256MiB 起读放大跌破 1.0**（S2 0.917 → 0.610），即缓存开始实现**字节级复用**（只抓 61% 逻辑字节）。
   64MiB 及以下全部 > 1.0——那一档缓存只减 GET/RTT，字节反而多抓 29–44%。
2. 增益曲线呈**两端趋零、中间取峰的倒 U**（+1.0 → −16.2 → −14.8）。理论上也自洽：
   缓存极小则所有策略都颠簸、缓存极大则所有策略都装得下，**自适应红利只存在于中间带**。

### 2.3 决策树判准率高 ✅

逐读比较各 selector 的选择与该负载 oracle 最优策略（held-out，从未参与训练）：

| selector | 读加权命中率 | 按 trace 宏平均 |
| --- | --- | --- |
| 手写规则 `template_auto` | **12.4%** | 23.8% |
| **决策树 + 滞后** | **93.1%** | 82.7% |

> 产物：`results/policy_agreement.json`
> 保真度已交叉验证：该工具算出的四策略分布（1006/1622/5129/3432 与 3497/2237/2142/3313）
> 与 Java 基准打印的计数**逐读完全一致**。

### 2.4 工程性目标达成 ✅

- **appID 环境隔离**可用：`RuntimeMetrics` 可报告每 app 预留/占用/块数/在飞峰值（Flink、Spark 各自独立）。
- **关闭开关零行为变化**：`passthrough` 读放大恒为 1.000、GET 数 = 逻辑读数。
- **无失控预取**：预算上限不被突破，`fallback reads = 0`，取消字节可计量。

## 3. 没有效果 / 被证伪的部分

### 3.1 异步预取（S3）无效 ❌

| trace | S3 vs S2（IO 时延） | 预取 useful / 总预取字节 |
| --- | --- | --- |
| mixed_holdout | **+1.6%（打平略亏）** | 28.2 MiB / 697 MiB ≈ **4%** |
| ml_taxi_epoch（纯顺序） | +0.3% | **0.00 MiB（0%）** |

> 产物：`results/report-rtt-mixed-*.txt`、`results/report-rtt-epoch-*.txt`

**机制本身是正常的**：929 次预取确实异步发出、不阻塞主线程（否则 S3 会显著慢于 S2，而实测仅差 1.6%）。
**瓶颈是推测命中率**——depth-1 的「下一个 1MiB 块」几乎从不等于真正的下一次读。

补充：训练期预取「看起来有用」，是 simulator 用激进的 8MiB×depth8 近似实现了小工作集的**整文件预热**，
SDK 端的保守参数（1MiB×depth1）不复现该行为。

### 3.2 滞后（hysteresis）目前不起作用 ❌

- 对判准率影响为 **0**（有滞后 93.1% vs 无滞后 93.1%）。
- 且**策略切换在当前实现中没有直接代价**：`policySwitches` 只是指标计数器；
  `AdaptivePolicySelector.reset()` 在主流程**无任何调用者**；4 个执行器共享同一 `AppCache`，
  故切换不失效缓存、不重取（实测取消字节 = 0）。切换的间接影响（块粒度变化导致重叠抓取）
  已被 GET 数/读放大完整计入。

→ 结论：**切换次数只是「规则对噪声敏感」的诊断信号，不是成本项**，不应作为选型理由。

### 3.3 被数据推翻的三个假设 ❌

| 原假设 | 实测 |
| --- | --- |
| 手写规则可能已经足够准，故换模型无意义 | **推翻**：手写命中率仅 12.4%，几乎从不收敛到最优策略（tpch 0.3%、lance_small 0%、ml_lastfm_emb 把 19988/20000 个读判错） |
| 判准率高 → 端到端性能好 | **解耦**：判准率差 80 个百分点，64MiB 下端到端只差 4%（但 256MiB 下差 16%） |
| ml_embedding（工作集 67MB）会在 64MiB 下翻转标签 | **证伪**：没翻。其远端字节仅 0.9–1.3 MiB（读放大 0.014–0.020），工作集远小于估计 |

### 3.4 小预算下学习式反而略差于手写 ❌

8MiB / 32MiB 下 S2 比 `template_auto` **多抓 1.0% / 1.3% 字节**。
根因见 §5.3——这是「标签在错误工况下标定」的直接证据，不是模型能力问题。

## 4. 数据小结（一页版）

| 结论 | 证据 | 判定 |
| --- | --- | --- |
| 缓存 + 策略路由降低时延 | RTT 下 −23.7%、GET −43.7% | ✅ 有效 |
| 学习式优于手写 | 字节 −5.3%（64MiB）→ −16.2%（256MiB） | ✅ 有效，但依赖工况 |
| 大预算实现字节级复用 | 读放大 0.917（256MiB）/ 0.610（1024MiB） | ✅ 有效 |
| 决策树判准 | held-out 93.1% vs 手写 12.4% | ✅ 有效 |
| appID 隔离、关闭零变化 | RuntimeMetrics / 读放大 1.000 | ✅ 有效 |
| 异步预取 | +1.6%；推测命中率 4% / 0% | ❌ 无效 |
| 滞后 | 判准率影响 0；切换无代价 | ❌ 当前无用 |
| 小预算下的学习式 | +1.0% / +1.3%（更差） | ❌ 工况错配 |

## 5. 过程中发现的评测口径缺陷（本阶段最重要的产出）

这四处缺陷任一不修，都会导致对整个方法价值的误判。

### 5.1 预算不公平（已修）

早期 S2 用「每对象各一份 `PageCache`」，S3 用「全 app 共享预算」，**两者不可比**。
现已统一：`template_auto`/S2/S3 一律走同一 `AdaptiveReaderRuntime`、同一 work-conserving 全局预算，
差异被收敛为「选择器大脑 + 预取深度」两项，`S3 vs S2` 才是干净的纯预取增量。

### 5.2 测试 trace 不具代表性（已修）

只用 TPC-H 会误判——它几乎全是 `s3a_random`，**根本触发不到预取/局部性路径**。
现改用 5 类均衡、保结构的 `mixed_holdout.csv`（分段拼接而非交错，保留各类自身时序，
并天然构造跨段策略切换场景）。

### 5.3 评测工况与标签标定工况不一致（关键，未完全修）

**§6.2 的标签是在 256MiB 预算下标定的，而我们默认用 64MiB 评测**——
等于**在错误工况下给决策树打分**。这才是「93% 判准率只换来 4%」的真正根因，而非模型选型问题；
小预算下它甚至略差于手写规则，正是该错配的直证。

### 5.4 标签口径被反推出来（新发现）

用「最小时延」取 argmin **对不上** §6.2 的标签；换成**最小远端字节**后，
256MiB 下 argmin **5/6 精确复现**标签（唯一不符的 tpch 差 1.6%，实质并列）。

→ **后续任何重标定都必须沿用字节口径**，否则会得到一批「时延最优但读放大灾难」的标签
（例：tpch 按时延会选 `s3a_prefetch`，时延 8.0s vs 42.7s，但多抓 5.5 倍字节）。

### 5.5 模拟器与真实实现的代价不对应（限定条件）

跨预算标签翻转检查（只有 lance 两类会翻，6 个负载中 4 个与预算无关）：

| 负载 | §6.2 标签 | 字节口径@64 | 字节口径@256 | 64MiB 沿用旧标签的代价 |
| --- | --- | --- | --- | --- |
| lance_small | `s3a_prefetch` | `s3a_random` | `s3a_prefetch` ✓ | **+11073.7%**（读放大 228.6x） |
| lance_large | `template_locality` | `template_multimodal` | `template_locality` ✓ | +40.0% |
| 其余 4 类 | — | 不变 | ✓ | 0.0% |

> 产物：`results/label_flip_check.json`、`results/label_flip_check.log`

**但这个「灾难」不会在 SDK 上重现**：simulator 的 `s3a_prefetch` 是 8MiB×depth8，
SDK 执行器是保守的 1MiB×depth1，故 SDK 在 64MiB 下读放大只有 1.293，不会出现 228x。

→ 即**模拟器标签所反映的策略代价与 SDK 执行器的实际代价并不对应**。
因此比「在 64MiB 重训」更根本的修法是：**用 SDK 自己的执行器在目标预算下重新标定标签**。

## 7. 下一步

### 7.1 立即要做的两件（互为前提）

1. **动态 oracle 上界**。当前标签是「一个负载一个常量」，意味着模型**最好也只能复现
   「每负载最优静态策略」，永远超不过它**。用事后视角算「每 K 个读窗口的最优策略」，
   与静态 per-workload oracle 对比：
   - 明显更好 → 负载**内部**相位切换有价值，bandit/RL 这条被搁置的路才值得走；
   - 差不多 → 该方向可直接判死，省掉大量投入。

   **这是所有后续工作的天花板，应最先测。**

2. **预算压力进入特征空间**。目前 10 维特征全是 IO 形状，**没有一维能看到预算或缓存压力**，
   而最优策略恰由工作集/预算比 ρ 决定——**模型被要求预测一个它看不见的自变量的函数**。
   拟加入：`log2(预算)`、近期淘汰率、预算占用率、**重用距离（reuse distance）**估计。
   注意这会引入反馈闭环（策略 → 淘汰 → 又影响策略），可能振荡——
   **届时滞后才会从「无用」变为「必需」**，正好与 §3.2 的干净基线形成对照。

### 7.2 口径修正（应与上述并行）

- 用 **SDK 自己的执行器**在目标预算下重新标定标签（§5.5），替代继续沿用 simulator 标签。
- 评测默认预算对齐标定预算，或显式报告各类工作集/预算比 ρ。

### 7.3 值得作为研究点深入的

| 方向 | 为什么有价值 | 现有证据 |
| --- | --- | --- |
| **分类精度与端到端收益的解耦** | 「ML for systems」普遍把分类精度当交付物；我们有干净反例，可刻画「精度何时才是有效代理指标」 | 80 个百分点 → 4%（64MiB）/ 16%（256MiB） |
| **自适应红利 vs ρ 的曲线** | 可给出「何时**不**该上自适应」的部署判据，比「快 X%」更有分量 | 倒 U 已测出：+1.0 → −16.2 → −14.8（峰位待补 2048/4096 点确认） |
| **模拟器 → 实现的保真度差** | 该领域大量工作只在 trace 模拟器上评测；我们两套都有，可量化哪些结论迁移 | 同一策略：模拟器 228x vs SDK 1.29 |
| **预取的可预测性上界** | 若「给定历史预测下一块」的条件熵本就高，则**任何**预取器都赢不了——带上界的负面结果 | 预取命中率 4% / 0% |

**不构成贡献、仅作动机的部分**（需在写作中明确区分）：「不同负载需要不同策略」（前人已确立）、
「缓存更大更好」（平凡）、「决策树能分类 IO 模式」（学习式缓存/预取已有大量先例）。
