# 湖仓 S3 自适应预取 —— 访问热力图阶段汇报

> 汇报人：李皓月　|　阶段：负载访问特征观察与刻画　|　日期：2026-06-29

---

## Summary

本阶段用统一的访问采集 + 热力图工具，刻画了四类典型湖仓负载（TPC-H 分析、Lance 向量检索、ML 训练、多模态湖仓）的 I/O 访问模式，并用真实数据集做了锚点验证。核心结论有两条：

1. **不同类型负载的访问模式差异巨大**——请求大小（从 0.4 KB 到 4 MB，跨 4 个数量级）、顺序性（24%～90%）、时间局部性、字段异构度四个维度上各占一角，没有任何一种固定 buffer/预取策略能同时适配。
2. **同一类型负载的访问模式高度一致、且与具体数据无关**——例如 Lance 向量检索在合成数据、真实 SIFT1M、真实 fashion-mnist 三个数据集上，直方图与热力图形态**几乎完全重合**；差异只体现在"绝对请求大小随向量维度线性缩放"这一可解释的量上。

**推论**：访问模式由"**数据格式 + 引擎 reader + 查询/索引逻辑**"决定，而非由数据数值决定。因此**负载是可分类的**，可以"先识别负载类型、再针对该类型选择访存优化策略"。这为后续"轻量、可选、对 SDK 无侵入"的自适应预取/缓存方案提供了可靠的特征基础——模型本身无需复杂，关键特征已被观察出来。

## 1. 背景与本阶段目标

- 场景：通过 AWS SDK 访问湖仓，数据以对象形式存放在 S3，单次访问首字节延迟高（~20–100 ms）。
- 已知问题：Hadoop S3A 的固定大块预取基于"访问局部性"假设，对顺序 I/O 有效，但**对随机 I/O 预取常常预测错误，反而降低效率**。
- 本阶段任务：**观察、刻画真实负载的访问特征**，判断"是否存在可被利用、且未被现有方案发现的规律"。
- 工具：通过pyarrow / Rust原生I/O采集数据访问trace，通过python脚本绘图，对每类负载产出 5 张图（偏移直方图、offset×time 热力图、请求大小分布、热点对象、按对象分面热力图）+ 1 份量化 summary。

---

## 2. 采集方法

| 引擎类型 | 采集方式 | 适用负载 |
|---|---|---|
| 走 pyarrow（Parquet） | `LoggingFileSystem` 在文件系统层拦截每次 `read(offset, length)` | TPC-H、ML 训练 |
| Rust 原生 I/O（Lance） | `strace` 在 syscall 层抓 `pread64` | Lance 向量、多模态 |

两条链路输出统一的 trace 格式（`timestamp, object_key, offset, length, file_size, query_id`），保证四类负载可横向对比。

## 3. 四类负载访问特征实测结果

| 负载 | 数据来源 | 请求数 | 总读取 | 请求大小 p50/p99 (KB) | footer 占比 | 顺序性 |
|---|---|---|---|---|---|---|
| TPC-H 分析 | DuckDB 官方 dbgen sf=1 | 4,855 | 1,243 MB | 190 / 620 | 4.4% | 57.0% |
| Lance 向量（真实 SIFT1M） | ANN_SIFT1M 1M×128 | 181,224 | 10,100 MB | 0.5 / 16 | 40.2% | 23.8% |
| ML 训练 `epoch_scan` | NYC taxi 真实表 | 659 | 1,015 MB | 201 / 4,456 | 5.3% | 89.9% |
| ML 训练 `embedding_gather` | MovieLens-1M 真实 Zipf | 180,964 | 67 MB | 0.4 / 0.4 | 0.0% | 78.4% |
| 多模态湖仓 | 合成异构表（blob+向量+小列） | 2,785 | 543 MB | 137 / 1,092 | 21.8% | 27.0% |

### 3.1 四类负载的访问形态

- **TPC-H 分析**：离散大 chunk（数百 KB 列分片），热力图呈**对角高亮**，表明访问模式为**顺序读**，footer 恒为热点。→ 适合**大块顺序预取**。
- **Lance 向量检索**：**大量 0.5 KB 左右随机小读**（IVF_PQ 拿候选后逐条回读原始向量），直方图显示 98% 的读集中在数据列。热力图近乎全图散点 + auxiliary.idx 处一条水平热带，表明数据随机性较强。→ 若每次裸发 S3 GET，大量随机小读会造成性能严重下降，**coalesce 收益最高**。
- **ML `epoch_scan`**：块级顺序扫，**多 epoch 重复访问同一批 offset**，热力图呈横带贯穿整个时间轴，表明同一批数据被反复读取，存在时间局部性。→ 适合**块级 buffer / page cache 复用**。
- **ML `embedding_gather`**：行级随机抽取，请求大小为一个 col chunk。偏斜集中在 ID 维度。→ 适合**行级 LRU 缓存**。
- **多模态湖仓**：**异构同表**——一张表里大 blob（图，几百 KB）与小向量/列（几十 B～KB）混存，请求大小**双峰跨 ~70 倍**；检索走"先小向量召回、后大 blob 回表"的两段式。→ 需**按命中字段自适应预取粒度**。

## 4. 核心发现：同类负载的访问模式高度一致

这是本阶段最重要的发现，也是支撑"分类后针对性优化"的直接证据。

### 4.1 Lance 向量检索：三个数据集形态同构

对 Lance 向量负载，分别用**合成数据、真实 SIFT1M、真实 fashion-mnist** 跑同一套 pipeline，访问形态高度一致：

| 指标 | 合成 1M（128d） | 真实 SIFT1M（128d） | 真实 fmnist（784d） |
|---|---|---|---|
| data 列读取占比 | 98.5% | 97.8% | 99.1% |
| 请求大小 p50 | 0.5 KB | 0.5 KB | **3.1 KB** |
| auxiliary.idx 热带位置 | rel≈0.57 | rel≈0.57 | rel≈0.45 |
| 热力图/直方图形态 | 散点 + 跳跃热带 | **完全一致** | **完全一致** |

- 三者形态**完全同构**；唯一变量是请求绝对大小：单向量 128×4 B = 512 B → 784×4 B ≈ 3.1 KB，**严格随维度线性变化**。
- **意义**：这印证了"访问形态与数据数值/维度无关、绝对大小由维度可解释地决定"。换言之，**只要知道这是 Lance 向量检索负载，就能预测它的访问指纹**——无需对每个新数据集重新学习。

### 4.2 ML embedding：访问偏斜可被结构掩盖

用 MovieLens 真实 Zipf 访问序列 vs 合成均匀随机跑 `embedding_gather`：
- **I/O 层 trace 完全相同**（两者均 180,964 reads / 67 MB / 请求 0.4 KB）——因为 batch（256）远大于 row group 数（58），每个 batch 都命中全部 row group，偏斜在 I/O 层被抹平。
- 但在**行级 LRU 缓存**上，真实 Zipf 与均匀随机差异巨大：25% 缓存容量下真实命中 57.9% vs 均匀基线 25.0%。

**意义**：这说明"访问偏斜住在哪个粒度"由 `batch_size / row_group_count` 比值决定——粗粒度看不出偏斜的负载，必须下沉到行/页级缓存才显价值。这是一个直接可作为策略判别特征的洞察。

## 5. 对优化方案的启示

### 5.1 负载可分类 → 两层切分的优化框架

四类负载在 **请求大小量级 × 顺序性 × 时间局部性 × 字段异构度** 四维上各占一角，构成清晰的负载特征空间。据此可把问题切成两层、分别处理：

| 层 | 不确定性 | 处理手段 |
|---|---|---|
| 文件结构层（footer/索引/列分片布局） | 几乎没有（格式规范公开） | **format-aware 规则**（直接按 spec 读） |
| 查询负载层（下一秒查哪行/哪个 item） | 用户决定 | **轻量在线学习 / 惰性缓存** |

结论：**结构层用热力图挖出的规则即可；只有不确定的查询层才需要在线自适应**。

### 5.2 "模型不必复杂"得到支撑

由于访问形态由格式 + 引擎 + 查询逻辑决定、与数值无关且可泛化，**大部分预取/缓存收益可由"识别负载类型 + 套用该类型对应策略"获得**，无需端到端学习地址序列的复杂模型（如 LSTM）。

### 5.3 针对每类负载的优化方向

| 负载 | 优化要点 |
|---|---|
| TPC-H 分析 | 大块顺序预取 + 列级 coalesce |
| Lance 向量 | 把海量 512 B 小读 coalesce 成大 GET |
| ML epoch_scan | 块级 buffer / OS page cache 复用 |
| ML embedding | 行/页级 LRU |
| 多模态 | 按命中字段自适应预取粒度；两段式检索的"预取时机"决策 |

## 6. 下一步计划

1. **量化"可预测性"与"复用收益"**：把当前定性的热力图升级为量化指标——结构可预测字节占比、复用距离分布、"缓存容量 vs 命中率"曲线，直接给出每类负载的预取/缓存 ROI 上限。
2. **落地在线判别特征**：将请求大小量级、`batch/row_group` 比、顺序性等特征落进 summary，验证仅凭一小段在线窗口即可区分负载类型（评估在线方案在高 IOPS 下的可行性）。
3. **先评简单规则 baseline**：用现有四类 trace 做回放，量化一个 format-aware 简单规则能达到的省延迟/省 RTT/浪费字节，再据此判断是否值得引入 contextual bandit 等学习方案。
4. **方案设计为可选功能**：确保最终预取/缓存对现有 SDK 正常功能零侵入。
