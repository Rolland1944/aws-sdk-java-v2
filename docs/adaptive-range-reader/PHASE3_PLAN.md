## 0. 阶段目标

在已定稿的 `joint2`（Track2）+ 固定 4 GiB 代价感知 W-TinyLFU（Track1）基础上，回答评审必然追问的四件事：

1. **为什么选这个缓存算法**：与常见置换算法相比，优势来自哪里。
2. **内存之外还有没有出路**：把缓存放在 SSD，或内存 + SSD 分层，能否以更小的堆达到接近大内存缓存的效果。
3. **结论是否只属于 ClickBench**：补充 TPC 系列和 Spark ML 典型负载。
4. **能否落到普通 Spark ETL 上**：只用 Spark SQL / DataFrame 的配置项，不改 Parquet Writer 源码。

同时并行完成论文写作（引言初稿、方法、实验章节）。

## 3. 研究问题与假设

每个问题给出**可证伪的判据**，没有判据的问题不立项。

| 编号 | 问题 | 假设 | 判据 |
| --- | --- | --- | --- |
| RQ1 | 代价感知 W-TinyLFU 相对常见算法的优势来自哪里？ | 优势主要来自请求级准入和按远端代价加权，而不是分段结构本身 | 同容量、同布局下，最终方案的墙钟中位数不劣于 LRU 与频率型 W-TinyLFU；GET 数更低，且差异能用污染 / 准入统计解释 |
| RQ2 | 缓存容量应随什么变化？ | 缓存收益取决于工作集与容量之比，超出该比例后增加容量收益递减 | 在 SF1、SF8 上给出 4 GiB 与 8 GiB（或更多档）的同协议对照，画出收益随容量的曲线。会议提出的“100G 上 4→8 GiB 增加 16%”作为待验证数据点 |
| RQ3 | SSD 能否替代一部分内存缓存？ | 命中延迟远小于一次远端 GET（毫秒级对比几十毫秒），因此 SSD 缓存仍有净收益 | SSD-only 在同 Xmx 下优于无缓存，且单次命中延迟显著低于远端 GET |
| RQ4 | 内存 + SSD 分层能否接近大内存缓存？ | 小容量内存（约数据量 1%）加较大 SSD（约 10%）能逼近 8 GiB 以上内存缓存 | 在同 Xmx 下，分层方案优于 4 GiB 纯内存；或以更低的堆峰值达到与大内存缓存相同的墙钟 |
| RQ5 | 结论是否跨负载成立？ | Track2 的方向在 TPC-H / TPC-DS 成立但幅度不同；Track1 在多 epoch 重读的 ML 负载上收益更大 | 每个新负载均给出 2×2（或其子集）的同协议结果，并解释幅度差异 |
| RQ6 | 能否只靠 Spark SQL 配置落地？ | 列序、文件数、行组、页和全局压缩可由 Spark 表达；逐列编码不可表达 | 落地版本的收益与 UC1 的差距被量化，不可表达的动作显式记录而不静默降级 |

## 5. 统一实验协议

所有新实验沿用 `FINAL_TRACK1+TRACK2.md` §1.3，并补充以下条款。**不满足协议的数据只能用于粗筛，不得进入论文主表。**

### 5.1 继承的规则

1. **排名指标**：只按墙钟中位数排名。GET 数、远端字节、命中率、堆、GC 只用于解释。
2. **进程隔离**：每个 `(格, 轮)` 独立启动一个 Spark 进程，Track1 缓存每次冷启动。
3. **调度**：同一轮内各格交替运行，每轮轮换起始格。
4. **不接受跨时段 / 跨主机比较**：只比较同一时段、同一主机内的配对结果。
5. **轮数**：正式结果 n=5；冒烟 n=1 只用于判断“能否运行 / 方向是否合理”，不得报告百分比。
6. **不用 trace 重放替代真实运行**：重放可以做粗筛，但必须标明“不含并发与缓存反馈”。

### 5.2 本阶段新增的规则

| 编号 | 规则 | 理由 |
| --- | --- | --- |
| P-1 | 每次实验记录并归档：JAR 的 SHA-256、`git rev-parse HEAD` 和工作区 diff 摘要、全部 `-D` 属性、Spark 与 Hadoop 版本、实例规格、对象存储与区域、数据集路径与大小 | 之前曾因 JAR 过期而让一批结果作废 |
| P-2 | 构建一律使用 `package`，并在运行前确认 JAR 内含最新类 | 同上，见 `FINAL_TRACK1+TRACK2.md` §8.1 |
| P-3 | 同一网格内只改变一个自变量。算法网格固定容量和布局；容量网格固定算法；分层网格固定准入与 Xmx | 避免混淆 |
| P-4 | 容量用绝对值和**占数据量的比例**两种方式同时报告；工作集与容量之比 ρ 作为解释变量 | 缓存收益本质上取决于 ρ |
| P-5 | 比较内存缓存与 SSD / 分层缓存时，**固定 driver 最大堆**（Xmx）；另设一个降低 Xmx 的对照臂，用于回答“内存紧张时是否仍有效” | 堆峰值是缓存的真实代价，也是引入 SSD 的动机 |
| P-6 | 任何一格的 CV 超过 5% 时，增加到 7 轮；仍不收敛则标为“不稳定”，只引用同轮配对的方向，不引用百分比 | COS 已出现 11% 的 CV |
| P-7 | 同轮配对差值必须逐轮列出；若某配对出现符号翻转，不得使用“显著”一词 | 与现有结果表一致 |
| P-8 | 每个新负载在进入多轮实验前，先做**结果正确性校验**：缓存开关与布局重写不得改变查询结果（行数与校验和一致） | 避免把错误的快速结果当成收益 |
| P-9 | 每个新负载先确定其**原始（默认 Spark 写出）基线**，不用 DuckDB 生成的源 Parquet 作基线 | 沿用 M0 合同：Spark / parquet-mr 的默认输出才是对照 |
| P-10 | 对象存储环境按名称标注（AWS S3 us-east-2 / 腾讯云 COS ap-guangzhou）。跨云比较只比较“各云内部的相对收益”，不比较绝对秒数 | 主机与网络不同 |
| P-11 | 失败、被否决的配置同样归档，并写明否决原因 | 论文中需要负面结果表 |

### 5.3 结果归档

- 目录：`docs/adaptive-range-reader/results/phase3/<workload>_<env>_<date>/`，每个网格一个目录。
- 每个目录至少含：`status.json`、`report.json`、各轮 `report.json`、环境与版本元数据（P-1）、汇总表。
- 本文件只引用汇总表的路径和结论，不复制原始数据。

### 5.4 报告格式

每个网格统一给出下面四张表，不做裁剪：

1. 五轮墙钟、中位数、CV、GET、远端字节、峰值堆；
2. 效应分解：各自单独、组合、简单相加预期、实际；
3. 同轮配对差值（逐轮列出）；
4. 逐查询（或逐阶段）回归检查：不得出现较基线明显变慢的查询而不加说明。
