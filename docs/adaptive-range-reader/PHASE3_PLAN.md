## 0. 阶段目标

在已定稿的 `joint2`（Track2）+ 固定 4 GiB 代价感知 W-TinyLFU（Track1）基础上，回答评审必然追问的四件事：

1. **为什么选这个缓存算法**：与常见置换算法相比，优势来自哪里。
2. **内存之外还有没有出路**：把缓存放在 SSD，或内存 + SSD 分层，能否以更小的堆达到接近大内存缓存的效果。
3. **结论是否只属于 ClickBench**：补充 TPC 系列和 Spark ML 典型负载。
4. **能否落到普通 Spark ETL 上**：只用 Spark SQL / DataFrame 的配置项，不改 Parquet Writer 源码。

同时并行完成论文写作（引言初稿、方法、实验章节）。

### 0.1 缓存算法口径变更（2026-10-15）

**决定**（项目负责人）：自 2026-10-15 起，本阶段所有新实验（容量曲线、SSD / 分层缓存、新负载）统一使用 **W-TinyLFU-AV**，即 `-Dtrack1.d1.policy=wtinylfu-av`，替代 `FINAL_TRACK1+TRACK2.md` §4.3 的代价感知 W-TinyLFU（`wtinylfu`）。AV 已在代码中实现（`AppCache` 的 `WTINYLFU_AV` 分支，论文版 Aggregated Victims，Einziger 等，ACM TOS 2022）。

两种算法的差别，决定了哪些旧结论不能原样沿用：

| 项 | 定稿 W-TinyLFU（`wtinylfu`） | W-TinyLFU-AV（`wtinylfu-av`） |
| --- | --- | --- |
| 准入单位 | 请求级原子：一个请求的全部切片要么都进，要么都不进（`FINAL_TRACK1+TRACK2.md` §4.5） | **块级**：一个请求的各块独立准入或丢弃（`AppCache` 源码注释） |
| 准入依据 | 频率 × 远端代价，代价由 `RemoteCostEstimator` 在线拟合 | 候选块频率不低于聚合牺牲者的频率和；**不用远端代价** |
| 大小感知 | 无 | 有（聚合牺牲者按所需字节收集） |
| 频率计数 | 计数上限 15，表超过 262,144 项时减半 | 精确计数，上限 S/C（`AV_SAMPLE_FACTOR=10`），每 S 次访问减半 |

由此产生的后果：

1. **`FINAL_TRACK1+TRACK2.md` §4.5 的“请求级原子准入”不变量对 AV 不成立。** 本阶段对 AV 的不变量只保留：字节与原始 GET 逐字节一致、hard cap 始终成立、缓存失败不得变成查询失败。
2. **RQ1 的原假设（优势来自请求级准入和按代价加权）不再适用于 AV**，已在 §3 改写。
3. **已定稿的 −14.9% / −11.8% / −45.7%（Track1 单独）和 −21.7% / −25.9% / −55.0%（组合）都由 `wtinylfu` 产生**，不能与 AV 的新结果混在一张表里比较。若论文主表要换成 AV，需要用 AV 重跑对应 2×2 网格，这是待办，依赖 §7 的门禁。
4. **证据强度要如实标注。** 目前支持 AV 的只有 `PHASE3_RESULT.md` §1：SF1、512 MiB、n=3 的筛选。AV 与定稿 W-TinyLFU 的区间不重叠（285–291 s 对 293–294 s），但 **AV 与 SIEVE 分不开**（中位数差 0.8%），`policy-4g` 与 SF8 的算法矩阵尚未跑。因此本阶段不写“AV 优于 SIEVE”，只写“本阶段统一使用 AV”。

## 3. 研究问题与假设

每个问题给出**可证伪的判据**，没有判据的问题不立项。

| 编号 | 问题 | 假设 | 判据 |
| --- | --- | --- | --- |
| RQ1 | W-TinyLFU-AV 相对常见算法的优势来自哪里？（2026-10-15 由“代价感知 W-TinyLFU”改写，见 §0.1） | 优势主要来自频率准入加大小感知（聚合牺牲者），使大扫描挤不掉小热点；而不是分段结构本身，也不是远端代价加权（AV 不用代价） | 同容量、同布局下，AV 的墙钟中位数不劣于 LRU、SLRU、定稿 W-TinyLFU 与 SIEVE；GET 数更低，且差异能用污染 / 准入统计解释。目前 AV 与 SIEVE 在筛选级别分不开，需 `policy-4g` 或 SF8 才能判定 |
| RQ2 | 缓存容量应随什么变化？ | 缓存收益取决于工作集与容量之比，超出该比例后增加容量收益递减 | 在 SF1、SF8 上给出 4 GiB 与 8 GiB（或更多档）的同协议对照，画出收益随容量的曲线。会议提出的“100G 上 4→8 GiB 增加 16%”作为待验证数据点 |
| RQ3 | SSD 能否替代一部分内存缓存？ | 命中延迟远小于一次远端 GET（毫秒级对比几十毫秒），因此 SSD 缓存仍有净收益 | SSD-only 在同 Xmx 下优于无缓存，且单次命中延迟显著低于远端 GET |
| RQ4 | 内存 + SSD 分层能否接近大内存缓存？ | 小容量内存（约数据量 1%）加较大 SSD（约 10%）能逼近 8 GiB 以上内存缓存 | 在同 Xmx 下，分层方案优于 4 GiB 纯内存；或以更低的堆峰值达到与大内存缓存相同的墙钟 |
| RQ5 | 结论是否跨负载成立？ | Track2 的方向在 TPC-H / TPC-DS 成立但幅度不同；Track1 在多 epoch 重读的 ML 负载上收益更大 | 每个新负载均给出 2×2（或其子集）的同协议结果，并解释幅度差异 |
| RQ6 | 能否只靠 Spark SQL 配置落地？ | 列序、文件数、行组、页和全局压缩可由 Spark 表达；逐列编码不可表达 | 落地版本的收益与 UC1 的差距被量化，不可表达的动作显式记录而不静默降级 |

## 5. 统一实验协议

所有新实验沿用 `FINAL_TRACK1+TRACK2.md` §1.3，并补充以下条款。**不满足协议的数据只能用于粗筛，不得进入论文主表。**

### 5.1 继承的规则

1. **排名指标**：只按墙钟中位数排名。GET 数、远端字节、命中率、堆、GC 只用于解释。
2. **进程隔离**：每个 `(格, 轮)` 独立启动一个 Spark 进程，Track1 缓存每次冷启动。
3. **调度**：同一轮内各格交替运行，每轮轮换起始格。
4. **不接受跨时段 / 跨主机比较**：只比较同一时段、同一主机内的配对结果。
5. **轮数**：正式结果 n=5；冒烟 n=1 只用于判断“能否运行 / 方向是否合理”，不得报告百分比。
6. **不用 trace 重放替代真实运行**：重放可以做粗筛，但必须标明“不含并发与缓存反馈”。

### 5.2 本阶段新增的规则

| 编号 | 规则 | 理由 |
| --- | --- | --- |
| P-1 | 每次实验记录并归档：JAR 的 SHA-256、`git rev-parse HEAD` 和工作区 diff 摘要、全部 `-D` 属性、Spark 与 Hadoop 版本、实例规格、对象存储与区域、数据集路径与大小 | 之前曾因 JAR 过期而让一批结果作废 |
| P-2 | 构建一律使用 `package`，并在运行前确认 JAR 内含最新类 | 同上，见 `FINAL_TRACK1+TRACK2.md` §8.1 |
| P-3 | 同一网格内只改变一个自变量。算法网格固定容量和布局；容量网格固定算法；分层网格固定准入与 Xmx | 避免混淆 |
| P-4 | 容量用绝对值和**占数据量的比例**两种方式同时报告；工作集与容量之比 ρ 作为解释变量 | 缓存收益本质上取决于 ρ |
| P-5 | 比较内存缓存与 SSD / 分层缓存时，**固定 driver 最大堆**（Xmx）；另设一个降低 Xmx 的对照臂，用于回答“内存紧张时是否仍有效” | 堆峰值是缓存的真实代价，也是引入 SSD 的动机 |
| P-6 | 任何一格的 CV 超过 5% 时，增加到 7 轮；仍不收敛则标为“不稳定”，只引用同轮配对的方向，不引用百分比 | COS 已出现 11% 的 CV |
| P-7 | 同轮配对差值必须逐轮列出；若某配对出现符号翻转，不得使用“显著”一词 | 与现有结果表一致 |
| P-8 | 每个新负载在进入多轮实验前，先做**结果正确性校验**：缓存开关与布局重写不得改变查询结果（行数与校验和一致） | 避免把错误的快速结果当成收益 |
| P-9 | 每个新负载先确定其**原始（默认 Spark 写出）基线**，不用 DuckDB 生成的源 Parquet 作基线 | 沿用 M0 合同：Spark / parquet-mr 的默认输出才是对照 |
| P-10 | 对象存储环境按名称标注（AWS S3 us-east-2 / 腾讯云 COS ap-guangzhou）。跨云比较只比较“各云内部的相对收益”，不比较绝对秒数 | 主机与网络不同 |
| P-11 | 失败、被否决的配置同样归档，并写明否决原因 | 论文中需要负面结果表 |

## 8. 工作流 B：SSD 与分层缓存（部分，2026-10-15）

本节只写**必要性验证**。架构、原型、实验网格和止损（§8.5 起）等 G1 出结果后再写：容量曲线若显示增大内存缓存没有收益，SSD 层就没有立项依据，提前设计是浪费。

### 8.1 为什么先验证必要性

- 当前证据说明堆压力不是引入 SSD 的强动机：SF1 / 512 MiB 下 GC 总时间约 3.9 s，墙钟约 290 s（`PHASE3_RESULT.md` §1）。
- 因此 SSD 的动机只能是**容量**：工作集与缓存容量之比 ρ 过大，内存放不下。这正是 RQ2。
- 旧的 SF8 单轮数据不能当证据：n=1、跨时段，且 4 GiB 臂用 32g 堆、8 GiB 臂用 48g 堆；其中 8 GiB 臂缓存被填满到 8.0 GiB、淘汰量只有 0.6 MB，墙钟反而比 4 GiB 臂慢。这提示容量曲线可能很平，G1 完全可能不通过。

### 8.2 容量曲线协议（RQ2）

**固定项**（P-3、P-12、P-13）：算法 `wtinylfu-av`，固定容量模式（`fixed.capacity=true`，`hard.mib` 等于 `cache.mib`），`admit.bytes=0`，doorkeeper 关闭，块 1 MiB，`local[16]`，driver 堆 48g。**唯一自变量是容量。**

**SF1 网格**（`--phase cap-sf1`，数据 `s3a://home-haoyue/track2/clickbench_sf1`，原始布局约 14.1 GiB，n=5）：

| 臂 | 容量 | ρ | 对应 SF8 的臂 |
| --- | ---: | ---: | --- |
| `000` | 无缓存 | — | 基线 |
| `pol-wtinylfu-av-128m` | 128 MiB | 0.9% | 1 GiB |
| `pol-wtinylfu-av-256m` | 256 MiB | 1.8% | 2 GiB |
| `pol-wtinylfu-av-512m` | 512 MiB | 3.6% | 4 GiB（参照臂） |
| `pol-wtinylfu-av-1g` | 1 GiB | 7.1% | 8 GiB |
| `pol-wtinylfu-av-2g` | 2 GiB | 14.2% | 16 GiB |
| `pol-wtinylfu-av-4g` | 4 GiB | 28% | 无对应 |
| `pol-wtinylfu-av-16g` | 16 GiB | 大于数据量 | 近似上界 |

SF1 容量按 SF8 的容量乘以 14.1 / 112.0 取整得到，所以两个网格的 ρ 对齐。`16g` 臂的容量大于整个数据集，但**只有不超过 8 MiB 的请求才可能入缓存**（`FINAL_TRACK1+TRACK2.md` §4.2），所以它是“近似上界”，不是真正的“无限容量”。

**SF8 网格**（`--phase cap-sf8`，数据 `s3a://home-haoyue/track2/clickbench_sf8`，原始布局 112.0 GiB）：

| 臂 | 容量 | ρ |
| --- | ---: | ---: |
| `000` | 无缓存 | — |
| `pol-wtinylfu-av-1g` | 1 GiB | 0.9% |
| `pol-wtinylfu-av-2g` | 2 GiB | 1.8% |
| `pol-wtinylfu-av-4g` | 4 GiB | 3.6%（参照臂） |
| `pol-wtinylfu-av-8g` | 8 GiB | 7.1% |
| `pol-wtinylfu-av-16g` | 16 GiB | 14.3% |

SF8 上没有真正的上界臂：本机 62 GiB 内存放不下整个工作集。这是 SSD 的动机之一，但 G1 的“上界”只能取 16 GiB 臂，不能取无限。

**执行顺序**：

1. **SF1**：`cap-sf1`，n=5，约 40 次运行，每次约 5 分钟。先跑，因为便宜，且能提前看出曲线是否平坦。
2. **SF8 堆可行性冒烟**：`cap-sf8-smoke`（只有 16 GiB 臂，n=1，约 35 分钟）。**不报告百分比**，只回答“48g 堆放不放得下 16 GiB 缓存”。峰值堆估计约 47 GiB，余量很小。
3. **SF8 筛选**：`cap-sf8`，n=3，6 臂共 18 次运行，每次约 35 分钟。
4. **SF8 补轮**：对 `000`、参照臂和 G1 中较优的较大臂补 2 轮到 n=5，约 6 次运行。用同一个 `--out`，加 `--cells` 指定这三个臂，`--runs 5`。注意 `run_track1_p3.py` 结束时会用这三个臂重写 `p3_report.json`，原来的六臂汇总会被子集覆盖；`phase3_capacity_report.py` 直接读 `cells/` 目录，不受影响，以它的输出为准。

**堆不可行的处理**（项目负责人确认）：16 GiB 臂若因内存不足或 GC 抖动失败，**归档为“堆不可行”，不换堆大小重跑**，并按 P-11 写明失败原因。`phase3_capacity_report.py` 把失败运行列在“失败或缺失的运行”表里，不会丢弃。这个结果本身支持“内存放不下，需要别的介质”。

**每次运行前后**：`run_track1_p3.py` 自动做 P-14 的运行前检查并写 `meta.json`；`ssd_device_bench` 与 `phase3_iso.py` 的隔离措施见 `PHASE3_RESULT.md` §2。内存缓存格不涉及缓存盘，但 Spark scratch 仍在 EBS 根盘，所有格相同。

### 8.4 门禁

**G0（设备够快）**：已于 2026-10-15 判定，见 `PHASE3_RESULT.md` §2.4。实例存储 NVMe 通过；EBS 只有 64–256 KiB 的块可用，≥ 4 MiB 比远端慢，不作为缓存介质。

**G1（容量确实是瓶颈）**：判据在看到数据之前写定：

- 取较大臂中墙钟中位数最小的一个，与参照臂（SF8 为 4 GiB，SF1 为 512 MiB，二者 ρ 同为 3.6%）做**同轮配对**。
- **通过**：每一轮配对差值同向（较大臂更快），并且中位数差距 ≥ 5%（SF8 上约 100 s）。
- **不通过**：中位数差距 < 2%，或配对出现符号翻转（P-7）。
- **不确定**：差距在 2%–5% 之间且同向，补到 n=5 再判。
- n < 5 的判定标为“筛选”，不得写成最终结论。

决策表：

| G0 | G1 | 动作 |
| --- | --- | --- |
| 通过 | 通过 | 进入 §8.5：写架构，做 S0 / S1 原型 |
| 通过 | 不通过 | 只写负面结果（P-11）：设备够快，但容量不是瓶颈，SSD 无立项依据；分层实验取消 |
| 通过 | 不确定 | 补轮；仍不确定则按“不通过”处理，并写明在该容量范围内未观测到收益 |
| 不通过 | — | 终止 |

**降低 Xmx 的对照臂**（P-5）不放进容量网格，因为 P-3 要求单变量。它在 G1 之后作为单独网格，只有 G1 通过、且需要论证“内存紧张时分层是否仍有效”时才做。
