# 多存储后端扩展实验汇总（GCS / 阿里云 OSS / 本地 MinIO vs AWS S3 / 腾讯云 COS）

> 本文汇总 RECAS 在新增的三个对象存储后端——**国外公有云 Google Cloud Storage (GCS)**、**国内公有云阿里云 OSS**、**本地自建 MinIO**——上的完整 5 轮 2×2 网格实验结果与单 GET 延迟特征，并与 [`EVALUATION.md`](EVALUATION.md) 及 [`修复后重跑结果.md`](修复后重跑结果.md) 中的 **AWS S3** 和 **腾讯云 COS** 原有数据进行系统性的**五存储后端 × 五评估维度**对比。
>
> **统计口径**（与 `EVALUATION.md` 完全一致）：
> - 墙钟时间取每格 5 轮轮换运行（`00 10 01 11` 循环移位）`query_sum_s` 的**中位数**；
> - 变异系数 $\text{CV} = \text{样本标准差} / \text{均值}$；
> - GET 请求数取 `io.gets` 中位数，远端扫描字节取 `io.remote_bytes` 中位数，峰值堆取 `track1.peak_heap_bytes` 中位数；
> - 单 GET 时延分桶（`< 64 KiB` 与 `≥ 8 MiB` p50）通过 `tools/track2/sysconst.py` 从 ClickBench SF1 基线（5 轮共 165,170 次 Range GET 轨迹）提取；拟合单请求成本通过 `TRACK1.md` §6.7 的两点联立方程 $\sum \text{lat} = N_{\text{GET}} \cdot r + \text{GiB} / \text{BW}$ 从扫描两端反解得到。
>
> 更新：2026-11-09。

## 0. 五存储后端单 GET 时延对比（小 GET / 大 GET / 拟合单请求成本）

按照 `FINAL_TRACK1+TRACK2.md` §7.1 与 `TRACK1.md` §6.7 的完全一致口径，下表对比五个对象存储后端在同区域（或本地回环）下的 **小 GET（`< 64 KiB`）p50**、**大 GET（`≥ 8 MiB`）p50** 以及 **拟合单请求固定成本 $r$**：

| 请求规模 | AWS S3（同区 `us-east-2`）p50 | 腾讯云 COS（同区 `ap-guangzhou`）p50 | Google Cloud Storage（同区 `us-central1`）p50 | 阿里云 OSS（同区 `cn-shanghai` 内网）p50 | 本地 MinIO（本机 `127.0.0.1`）p50 |
| --- | ---: | ---: | ---: | ---: | ---: |
| **小 GET（< 64 KiB）** | 23.6 ms | 81 ms *(重测 80.6 ms)* | **30.5 ms** | **11.4 ms** | **1.2 ms** *(1.17 ms)* |
| **大 GET（≥ 8 MiB）** | 48.3 ms | 112 ms *(重测 105.9 ms)* | **50.8 ms** | **18.3 ms** *(18.25 ms)* | **1.7 ms** *(1.69 ms)* |
| **拟合单请求成本** | 26.1 ms | 86.2 ms *(重测 85.1 ms)* | **32.4 ms** *(01–11)* / **35.0 ms** *(00–10)* | **12.8 ms** *(01–11)* / **13.7 ms** *(00–10)* | **1.3 ms** *(1.33–1.45 ms)* |

**详细分桶与并发常数（`tools/track2/sysconst.py` 实测，ClickBench SF1 `00` 格 5 轮 165,170 次 Range GET）**：

| 指标 | AWS S3 (`us-east-2`) | 腾讯云 COS (`ap-guangzhou`) | Google Cloud Storage (`us-central1`) | 阿里云 OSS (`cn-shanghai`) | 本地 MinIO (`127.0.0.1`) |
| --- | ---: | ---: | ---: | ---: | ---: |
| `< 64 KiB` GET p50 | 23.6 ms | 80.55 ms (原归档 81 ms) | **30.47 ms** | **11.41 ms** | **1.17 ms** |
| `64 KiB – 1 MiB` GET p50 | — | 84.18 ms | **37.63 ms** | **12.61 ms** | **1.26 ms** |
| `1 MiB – 8 MiB` GET p50 | — | 95.77 ms | **49.09 ms** | **17.81 ms** | **1.48 ms** |
| `≥ 8 MiB` GET p50 | 48.3 ms | 105.91 ms (原归档 112 ms) | **50.80 ms** | **18.25 ms** | **1.69 ms** |
| 拟合单请求成本 $r$ | 26.1 ms | 86.2 ms (新网格 85.1 ms) | **32.4 – 35.0 ms** | **12.8 – 13.7 ms** | **1.33 – 1.45 ms** |
| 单流有效带宽 $\text{BW}$ (`sysconst`) | ~557 MiB/s | 726.1 MiB/s | **905.5 MiB/s** | **2,694.3 MiB/s** | **35,452.5 MiB/s** |
| 繁忙期平均在飞并发 $K_{\text{busy}}$ | 4.42 | 8.10 | **7.45** | **3.94** | **2.29** |

**数据解读**：
1. **五个后端恰好张成跨越两个数量级的“单 GET 固定成本光谱”**：从 **腾讯云 COS（86.2 ms）→ GCS（32.4–35.0 ms）→ AWS S3（26.1 ms）→ 阿里云 OSS 内网（12.8–13.7 ms）→ 本地 MinIO（1.3 ms）**。
2. **服务端首字节地板主导单 GET 成本**：无论在哪个公有云，同可用区网络往返 RTT 都只有 1–2 ms，但小 GET p50 依然达到 **11.4 ms（OSS）、23.6 ms（S3）、30.5 ms（GCS）、81 ms（COS）**——这部分差额是对象存储软件栈与分布式元数据/索引层的**服务端首字节地板（First-Byte Floor）**，靠升级网卡带宽无法消除，只能靠**不发请求（Track1 缓存命中）**或**合并请求（Track2 布局重构）**消除。

## 3. 跨五后端的三大核心规律（供论文 Evaluation 讨论）

把全部五个存储后端放在一起后，RECAS 的性能行为呈现出一条极其清晰、物理可解释的主线：

### 规律一：物理 I/O 削减跨云完全不变量（Backend-Invariant Physical Reduction）
无论底层是 AWS S3、腾讯云 COS、Google Cloud Storage、阿里云 OSS 还是本地 MinIO，对于同一份 Parquet 布局：
- **ClickBench SF1**：无缓存 GET 恒为 `33,038`（基线）→ `24,079`（joint，−27.1%），远端扫描字节恒为 `46.60 GiB` → `30.50 GiB`（−34.5%）；开启 Track1 后，GET 统一降至 `3,957–4,384`（**总削减 −86.7% ~ −88.0%**），远端字节统一降至 `20.89–21.83 GiB`（**总削减 −53.2% ~ −55.2%**）。
- **NYC Yellow**：无缓存 GET 恒为 `121,730`（基线）→ `8,850`（joint，**−92.7%**），远端扫描字节恒为 `104.10 GiB` → `86.10 GiB`（−17.3%）；开启 Track1 后 GET 统一降至 `4,245–5,691`（**总削减 −95.3% ~ −96.5%**）。

这证明 RECAS 的 Track1（客户端自适应块缓存）和 Track2（工作负载感知布局重构）在 S3A 协议层实现的物理 I/O 削减是**严格与后端无关的不变量**。

### 规律二：端到端墙钟加速比与存储后端的单请求固定成本 $r$ 严格正相关（Latency-Driven Wall-Clock Scaling）
按 §0 实测的**小 GET p50 / 拟合单请求成本 $r$** 从高到低排列五个后端，ClickBench SF1 的端到端加速比呈现出完美的单调递减梯度：

| 后端排序（按单请求成本从高到低） | 小 GET (`<64KiB`) p50 | 大 GET (`≥8MiB`) p50 | 拟合单请求成本 $r$ | SF1 `Caching@00` | SF1 `Layout(off)` | SF1 `Combined (11 vs 00)` |
|---|---:|---:|---:|---:|---:|---:|
| 1. **腾讯云 COS** (`ap-guangzhou`) | **81 ms** *(80.6 ms)* | **112 ms** *(105.9 ms)* | **86.2 ms** *(85.1 ms)* | **−47.1%** (−217.1 s) | **−33.9%** (−156.2 s) | **−55.8%** (461.0 → 204.0 s) |
| 2. **Google Cloud Storage** (`us-central1`) | **30.5 ms** | **50.8 ms** | **32.4–35.0 ms** | **−31.3%** (−74.6 s) | **−24.8%** (−59.0 s) | **−38.7%** (238.4 → 146.2 s) |
| 3. **AWS S3** (`us-east-2`) | **23.6 ms** | **48.3 ms** | **26.1 ms** | **−14.9%** (−50.1 s) | **−14.5%** (−49.0 s) | **−21.7%** (337.2 → 264.0 s) |
| 4. **阿里云 OSS** (`cn-shanghai` 内网) | **11.4 ms** | **18.3 ms** | **12.8–13.7 ms** | **−9.0%** (−26.7 s) | **−9.9%** (−29.3 s) | **−14.1%** (295.8 → 254.1 s) |
| 5. **本地 MinIO** (`127.0.0.1` 热缓存下界) | **1.2 ms** | **1.7 ms** | **1.3 ms** | **−1.2%** (−2.0 s) | **−2.1%** (−3.5 s) | **−3.3%** (163.2 → 157.8 s) |

**物理机制公式**：
$$\Delta T_{\text{wall}} \approx \Delta N_{\text{GET}} \cdot \frac{r}{K_{\text{eff}}} + \frac{\Delta B_{\text{remote}}}{\text{BW}_{\text{eff}}} - T_{\text{cache\_cpu}}$$
在消除完全相同的 $\Delta N_{\text{GET}} \approx 28,660$ 次请求和 $\Delta B_{\text{remote}} \approx 24.8\text{ GiB}$ 远端流量时，拟合单请求成本 $r$ 越高（COS 86.2 ms > GCS 32.4 ms > S3 26.1 ms > OSS 12.8 ms > MinIO 1.3 ms），每次被省掉的 GET 折算成的墙钟秒数就越大。

### 规律三：为什么低时延云上「布局收益坚挺，而大表流式缓存收益收敛」？
对比 NYC Yellow 在五后端上的表现可以看到：
- **布局重构（`Layout(off)`）在所有云后端上都保持高收益**：COS **−67.2%~−77.2%**、GCS **−59.5%**、OSS **−19.8%**、AWS **−17.6%**。这是因为布局重构不仅把 GET 请求数直接砍掉了 **92.7%**（从 121,730 降到 8,850，消除了逾 11.2 万次请求），还通过列裁剪与紧凑编码减少了 **18.0 GiB** 的网络传输与 Parquet 尾部解析开销，且**零运行时内存/CPU 额外开销**。
- **客户端缓存（`Caching@00` / `Caching@joint`）对工作集与单 GET 成本高度敏感**：
  - 在 **ClickBench SF1**（可缓存工作集 ~2.67 GiB < 4 GiB 缓存容量，命中率 >81%，拦下 ~27,430 次 GET）上，缓存无论在 COS（−47.1%）、GCS（−31.3%）、AWS（−14.9%）还是 OSS（−9.0%）上都贡献了显著且稳定的正收益。
  - 在 **NYC Yellow**（单轮扫描 21.5 GiB >> 4 GiB 缓存容量）上，4 GiB 缓存在基线上只能拦下 ~9,000–11,000 次 GET（占 12.1 万次 GET 的 <9%），在 joint 上更只能拦下 ~3,160 次 GET。当后端单 GET 成本从 COS 的 86.2 ms 降到 GCS 的 32.4 ms 和 OSS 的 12.8 ms 时，拦截这几千次 GET 所省下的几秒网络延迟，在基线上仅够换取 **−3.5%（GCS）/ −3.3%（OSS）** 的微弱收益，在已经高度紧凑的 joint 布局上甚至会被缓存管理与堆内存开销抵消（GCS −2.5%，OSS +4.5%）。
- **设计启示**：这有力地证明了为什么 RECAS **必须将 Track1（在线缓存）与 Track2（离线布局重构）结合**——在工作集装得进缓存或中高时延对象存储上，Track1 即插即用立竿见影；而在超大工作集或极低时延内网存储上，Track2 的物理布局重构则充当主力，以零运行时开销兜底端到端性能。
