# 面向 AWS SDK 的 S3 读取 Buffer 策略

## 报告结论

第一阶段通过 AWS SDK 原生 Range GET、Hadoop S3A fadvise 和 Hadoop S3A prefetch 三套系统的对比，得到以下主要观察：

1. **AWS SDK 的主要问题是小 Range 请求过多，而不是单次响应缺少内存 buffer。
2. **fadvise 证明了复用长生命周期读取流和减少 GET 次数的价值。** 
3. **扩大请求粒度并异步下载后续数据，可以显著提升顺序读取性能。** 
4. **固定大块 buffer 不适合随机访问。** 
5. **随机访问更适合小而准确的并发 Range。**

从实验结果中观察得到，在 buffer 受限时，应优先保障 demand read 和已确认顺序流的下一个预取块，不为均匀随机访问保留固定大块预取空间。最终目标是形成 `AUTO → SEQUENTIAL/RANDOM` 的自适应读取层，在降低 GET 次数的同时控制内存占用和无效 S3 流量。

下一步计划：
1. 实现同步的 `BufferedRangeReader`：
- 维护一个 `[bufferStart, bufferEnd)` 窗口；
- 命中窗口直接复制；
- 未命中时按 1 MiB 或自适应大小发起 Range GET；
- 后向或远距离随机访问只取小窗口。
1. 增加顺序异步预取：
- 检测连续访问后预取下一个窗口；
- 从 depth=1 开始；
- 再根据消费速度增加深度；
- 与 AWS CRT/Transfer Manager 做完整下载对照。

# 第一部分：Hadoop S3A fadvise 和 S3A prefetch 策略

## 1.1 实验中的 AWS SDK 基线

基线使用 AWS SDK Java v2.25.70：

1. 每个逻辑读取操作生成一个带 `Range` 的 `GetObjectRequest`。
2. `ResponseTransformer.toBytes()` 等待整个 Range 响应完成，并将该响应全部放入内存。
3. 顺序读取 1 GiB 对象时：
   - 1 MiB 读取块产生 1024 次 GET；
   - 8 MiB 读取块产生 128 次 GET。
4. 不保留跨逻辑读取的对象数据窗口，也不自动把相邻 Range 合并。

因此，这个基线已经有“单次响应 buffer”，但没有“跨请求的 S3 对象读取 buffer”。

AWS 官方也提供了高性能下载方案。但这些方案只能解决部分完整文件高速传输的问题，对于随机读没有有效优化，仍存在实现 cache 读取层的空间。

## 1.2 Hadoop S3A fadvise

S3A fadvise 不是传统意义上的固定内存块 cache。它主要通过改变 HTTP Range GET 的范围和输入流在 seek 时的处理方式，匹配不同访问模式。

官方文档：[Maximizing Performance when working with the S3A Connector](https://hadoop.apache.org/docs/stable/hadoop-aws/tools/hadoop-aws/performance.html)

### `sequential`

- 面向从前向后读取以及短距离前向 seek。
- 打开一个覆盖整个对象或较大剩余范围的 HTTP GET 流。
- 前向 seek 时，如果目标仍适合在当前流中处理，就读取并丢弃中间字节，而不是立即关闭连接并重新发起 GET。
- 优点是减少 GET 次数和请求间 RTT，保持流式吞吐。
- 缺点是后向 seek 代价很高；较大的前向跳跃也可能传输大量不会被应用消费的数据。

### `random`

- 面向 `PositionedReadable.read()`、`readFully()`、远距离前向 seek 和频繁后向 seek。
- GET 范围接近应用实际需要的数据长度，并至少扩展到 readahead 范围。
- 实验配置的 readahead 为 64 KiB，因此 4 KiB 随机读可能实际获取最多约 64 KiB，而不是 1 MiB 或整个对象。
- 优点是限制无效传输，避免为一次随机访问读取对象的大段内容。
- 缺点是连续扫描时会产生大量 GET，每次请求都承担网络 RTT。

### `normal`

- 初始按顺序模式工作。
- 一旦检测到后向 seek，切换为随机模式。
- 它针对 Parquet/ORC 一类“先读尾部元数据，再向前读取选定列”的模式。
- 这是一个简单的自动策略，但识别维度有限，不能完整覆盖复杂混合负载。

实验中根据负载手工选择了策略：

| 负载 | fadvise | readahead |
|---|---|---:|
| 顺序读、短前向 seek | `sequential` | 1 MiB |
| 均匀随机、聚簇随机 | `random` | 64 KiB |
| 后向 seek | `normal` | 1 MiB |

## 1.3 Hadoop S3A prefetch

官方文档：[S3A Prefetching](https://hadoop.apache.org/docs/r3.4.3/hadoop-aws/tools/hadoop-aws/prefetching.html)

S3A prefetch 把对象切分成固定大小的块，为块分配 buffer，并异步读取后续块：

1. 对象小于一个块时，`S3InMemoryInputStream` 会把整个对象读入内存。
2. 对象大于一个块时，`S3CachingInputStream` 使用固定块、异步预取和本地缓存。
3. 当前块同步读取，相邻后续块异步读取；应用消费当前块时，网络线程并行下载后续块。
4. 未完全消费的块在跳转后可能被写入本地块 cache，以便后续回读。
5. `seek()` 本身只更新位置，真正取块发生在下一次 `read()`。

实验配置为：

- block size：8 MiB；
- prefetch block count：8；
- buffer pool 大小为 `prefetch block count + 1`，即每个流最多管理 9 个块；
- 仅按内存块计算，每个打开流的潜在 buffer 规模约为 `9 × 8 MiB = 72 MiB`，还未计算对象、线程和本地 cache 的其他开销。

prefetch 的核心价值是让网络读取和应用消费重叠。它不是只减少 Java 方法调用次数，而是主动并行获取未来数据。

# 第二部分：实验结果及原因分析

## 2.1 结果摘要

| 场景 | AWS SDK | S3A fadvise | S3A prefetch | 结果 |
|---|---:|---:|---:|---|
| 1 GiB 顺序，1 MiB，1 线程 | 24.762 MB/s | 86.550 MB/s | 263.326 MB/s | prefetch 最快 |
| 1 GiB 顺序，8 MiB，1 线程 | 77.290 MB/s | 86.037 MB/s | 311.855 MB/s | prefetch 最快 |
| 4 GiB 顺序，1 MiB，4 线程 | 73.814 MB/s | 66.402 MB/s | 457.532 MB/s | prefetch 最快 |
| 4 KiB 单线程均匀随机 | 0.153 MB/s | 0.158 MB/s | 0.044 MB/s | SDK/fadvise 接近 |
| 64 KiB 单线程均匀随机 | 2.411 MB/s | 2.508 MB/s | 0.698 MB/s | fadvise 最快 |
| 64 KiB、16 线程聚簇随机 | 38.056 MB/s | 35.793 MB/s | 10.427 MB/s | SDK 最快 |
| 4 KiB 短前向 seek | 0.157 MB/s | 8.182 MB/s | 6.533 MB/s | fadvise 最快 |
| 64 KiB 后向 seek | 1.956 MB/s | 2.043 MB/s | 0.693 MB/s | fadvise 最快 |

## 2.2 观察一：AWS SDK 在小数据量请求上的不足

1 MiB 和 8 MiB 用例读取的有效数据都是 1 GiB，但 GET 数量分别为 1024 和 128。

每次 GET 都包含请求调度、签名、连接池获取、S3 首字节等待和响应处理。即使底层 HTTP 连接被复用，请求 RTT 仍然存在。扩大 Range 后，单位数据承担的固定请求成本降低，因此吞吐从 24.762 MB/s 提升到 77.290 MB/s。

这直接证明：基线的首要问题是 **Range 过碎和请求过多**。仅在每个 1 MiB 响应上再增加 `BufferedInputStream`，不会把 1024 次 GET 变成更少的 GET，因而不会取得类似 fadvise 或 prefetch 的收益。

## 2.3 观察二：fadvise 通过减少 GET 次数提升吞吐

### 顺序读

`sequential` 策略维持一个长生命周期的远端输入流。应用的 1024 次 1 MiB 逻辑读取不再等价于 1024 次独立 GET，因此 1 MiB 单线程吞吐从 24.762 MB/s 提升到 86.550 MB/s。

8 MiB 基线本身已把 GET 数减少到 128，所以 fadvise 的优势缩小到 11.3%。两个 fadvise 顺序用例分别为 86.550 和 86.037 MB/s，也说明在同一条远端流上，应用每次调用读取 1 MiB 还是 8 MiB 已不再是主要瓶颈。

### 短前向 seek

该用例每次读取 4 KiB，然后前进 32 KiB：

- AWS SDK 为每个 4 KiB 逻辑读取发起独立 GET，平均延迟约 24.750 ms。
- fadvise `sequential` 可以继续消费当前远端流并跳过中间字节，避免绝大多数 GET RTT。
- prefetch 的 8 MiB 块也能让大量逻辑读取命中已取回块。

因此 fadvise 和 prefetch 的吞吐分别达到基线的约 52.1 倍和 41.6 倍。
## 2.4 观察三：扩大请求粒度和异步下载会提升顺序读取性能

prefetch 同时获得了两类收益：

1. **请求粒度扩大**：1 MiB 逻辑读取由 8 MiB 预取块承载，减少远端请求次数。
2. **读取与计算重叠**：消费当前块时，后续块异步下载，网络 RTT 和一部分传输时间不再完全暴露给调用线程。

这解释了以下现象：

- 1 MiB 单线程吞吐达到 263.326 MB/s，为基线的 10.63 倍。
- 8 MiB 单线程达到 311.855 MB/s；逻辑读取大小与预取块一致，浪费较小。
- 4 个流和后台预取共同增加并行 Range GET，吞吐达到 457.532 MB/s。
- 顺序用例的大多数逻辑读取直接从 ready buffer 完成，所以 P50/P95 延迟很低；少数等待新块的读取形成长尾。

这一结果与 AWS 官方建议一致：大对象下载可以通过多个并发 byte-range 请求更充分地使用网络带宽。

## 2.5 观察四：固定大小 buffer 在随机访问中反而导致性能下降

prefetch 以 8 MiB 为最小远端块，而实验随机读取为 4 KiB 或 64 KiB：

| 逻辑读取 | 单次 8 MiB 块相对逻辑数据的理论上限 |
|---:|---:|
| 4 KiB | 2048 倍 |
| 64 KiB | 128 倍 |

这里的倍数是“完全未复用时”的理论上限，不是本次实验测得的物理读放大。实际值取决于块命中、并发、取消和本地 cache。

均匀随机访问几乎不会连续命中下一个预取块，导致：

- 获取了大量不会被应用使用的数据；
- 后台预取占用连接和带宽，与真正需要的随机读竞争；
- 固定 buffer pool 被低价值块占据；
- seek 后需要等待目标块取回，平均延迟上升到约 88～93 ms。

聚簇随机用例也没有充分受益。其“热点”由 16 个、每个 64 MiB 的窗口组成，总工作集上限接近 1 GiB；而单流内存 buffer 规模约 72 MiB。热点集合相对 cache 仍然过大，随机访问很容易淘汰尚未复用的块。

因此，prefetch 的问题不是“随机读取永远不能使用 cache”，而是**固定 8 MiB 块、固定向前预取和有限 cache，与该随机工作集不匹配**。

## 2.6 观察五：并发 range 比固定 buffer 更适合随机访问

`random` 策略会让 GET 范围接近实际读取长度，并至少扩展到 readahead。实验 readahead 为 64 KiB：

- 64 KiB 逻辑读取与 readahead 对齐，基本没有额外扩大。
- 4 KiB 读取可能扩展到 64 KiB，存在最多约 16 倍的理论读放大。
- 均匀随机 offset 很少复用相邻数据，因此 readahead 的收益有限。

两者仍然都要为大量随机 GET 支付约 20～30 ms 的请求延迟，所以 fadvise 相对基线主要是 3%～4% 的小幅改善，而不是数量级提升。

16 线程通过并发隐藏 RTT，使 4 KiB 均匀随机吞吐从约 0.15 MB/s 提高到约 2.4～2.5 MB/s。64 KiB 聚簇随机在 16 线程下达到 35～38 MB/s，也说明对离散访问来说，“多个小而准确的并发 Range”比“固定 8 MiB 向前预取”更合适。

## 2.7 观察五：后向 seek 中 prefetch 明显退化

后向 seek 每次跨越约 8 MiB，恰好接近 prefetch 块大小。向前预取的块对下一次后向读取没有帮助，而每次目标变更又可能要求获取一个新的完整块。

fadvise `normal` 在检测到后向 seek 后切换到随机策略，使请求范围更接近所需数据，因此吞吐为 2.043 MB/s；prefetch 只有 0.693 MB/s。

# 第三部分：现有实现的缺陷和可改进方向

## 3.1 类似实现

| 已有实现                             | 已解决的问题                          | 不完全覆盖的场景                     |
| -------------------------------- | ------------------------------- | ---------------------------- |
| S3A fadvise                      | 按顺序/随机模式调整 GET 范围和 seek 行为      | 策略较静态；缺少通用异步块预取              |
| S3A prefetch                     | 固定块异步预取、内存 buffer、本地块 cache     | 固定块对随机访问读放大严重                |
| S3A Vectored IO                  | 合并相近 Range，并发读取多个已知 Range       | 需要调用者提前提供 Range 集合           |
| AWS CRT S3 client                | 并行 byte-range、连接池、DNS 负载均衡、分段重试 | 更偏向高吞吐对象传输，不是通用 seek cache   |
| AWS S3 Transfer Manager          | 大文件/目录并行传输                      | API 主要面向完整文件落盘或传输任务          |
| CloudFront/ElastiCache 等外部 cache | 跨请求、跨进程缓存热点对象                   | 引入基础设施、成本和一致性管理，不是 SDK 内部读窗口 |

“在 AWS SDK 上增加 buffer”本身并非空白方向。仍有价值的部分是：**为任意 offset 读取提供低内存、可自适应、可观测的统一读取层**，而不是再实现一个固定块 prefetcher。

## 3.2 S3A fadvise 的缺陷

### 策略粒度粗

官方文档所述的经典配置需要在创建 FileSystem 时选择策略，而不是对每个流或每个阶段动态选择。一个进程同时处理全表扫描和 Parquet 随机选列时，很难使用同一全局策略达到最优。

### `sequential` 可能产生隐藏读放大

短前向 seek 通过读取并丢弃中间数据来避免新 GET。延迟降低了，但 S3 流量和 EC2 网络带宽可能增加。跳跃距离增大后，这种交换不再划算。

### `random` 无法消除 GET RTT

它主要控制请求不要过大，却仍可能为每次随机读取发起 GET。对于 4 KiB/64 KiB 小块，RTT 远大于内存复制时间。

### `normal` 的模式识别过于简单

“出现一次后向 seek 就切换随机”不能识别：

- 短暂回读后继续长顺序扫描；
- 多个局部热点窗口；
- 交替读取两个相邻数据区；
- 已知的一批非连续 Range。

### 缺少以资源预算为核心的调度

策略重点是输入流行为，而不是在多个对象、多个调用方之间统一分配内存、连接、带宽和 in-flight bytes。

## 3.3 S3A prefetch 的缺陷

### 固定块大小同时承担多个目标

8 MiB 既是远端请求粒度，也是 cache 粒度。顺序吞吐希望块大，随机读放大希望块小，这两个目标冲突。

更好的设计应分离：

- 远端 GET 合并窗口；
- 内存 cache page；
- 异步预取深度；
- 本地磁盘 cache 单元。

### 固定向前预取缺少收益判断

即使最近的访问是均匀随机或后向，仍可能把带宽用于未来顺序块。应根据命中率、丢弃字节、seek 方向和消费速度实时关闭或缩小预取。

### 每流内存随并发线性增长

8 MiB × 9 buffers 约为 72 MiB/流。若 16 个流全部达到该规模，理论 buffer 占用可超过 1 GiB。固定“每流块数”不适合有严格进程内存上限的服务。

### cache 工作集不匹配时会污染

均匀随机访问和大热点集合会使刚取回的块在复用前被淘汰。本地磁盘 cache 还会增加写放大、文件管理和磁盘竞争。

### 小文件整对象入内存

对象小于 block size 时会整体读入内存。单个小文件问题不大，但高并发打开大量接近 block size 的文件时，峰值内存仍可能明显增加。

### 首块仍需同步等待

异步预取能隐藏后续块延迟，但第一个需求块和预测失败后的目标块仍在关键路径上。对短请求或频繁跳转，预取线程未必有机会产生收益。

### 可观测性不足会妨碍调优

若没有以下指标，很难判断 buffer 是否真正有效：

- 远端 GET 次数；
- 远端读取字节、应用有效字节和读放大；
- 内存/磁盘 cache 命中率；
- 被取消或未消费的预取字节；
- demand read 与 prefetch read 的带宽占比；
- 等待 buffer、连接和线程池的时间。

## 3.4 AWS SDK 现有方案的缺口

### `ResponseTransformer.toBytes()` 不是跨请求 cache

它只把当前响应放入内存。调用结束后，下一个相邻 Range 不会自动复用本次多取的数据。

### 普通 `ResponseInputStream` 仍是单个 GET 流

它适合顺序消费某个 GET 响应，但应用 seek 时仍需自行关闭并创建新 Range GET。官方 API 文档还指出，返回流后的 socket 读取失败不再由 SDK 的普通请求重试策略自动重试。

### Transfer Manager/CRT 更偏向完整传输

它们能够提供高性能的“大对象完整传输”，但在随机访问时效果不佳

## 3.5 可形成差异化的改进方向

1. **自动识别访问模式**，而不是要求用户提前指定 `sequential` 或 `random`。
2. **分离 demand cache 与 speculative prefetch**，避免随机请求驱逐真正热点数据。
3. **按成本合并 Range**：只有在“多传输 gap 的时间/费用”小于“节省一个 GET 的 RTT/费用”时才合并。
4. **全局内存预算**，按活跃流动态分配，而不是每流固定 N 个大块。
5. **批量 Range/Vectored API**：调用方知道多个 offset 时，排序、合并近邻 Range，并发读取远距离 Range。
6. **自适应块大小和预取深度**：根据 RTT、吞吐、消费速度和命中率变化。
7. **快速取消错误预测**：发生后向或大距离 seek 时，立即取消尚未开始或价值低的预取。

# 第四部分：建议采用的 Buffer 策略

## 4.1 顺序还是随机读取启用 buffer

如果只能二选一：

> 应优先在顺序读取中启用大 buffer 和异步预取；随机读取只做小范围按需读取，不做固定大块预取。

原因：

- 实验中 prefetch 对顺序读提高 4.04～10.63 倍，收益明确。
- 固定 8 MiB prefetch 对随机读造成约 71%～73% 的吞吐下降。
- 随机访问只有在存在稳定热点或局部性时，cache 才能抵消读放大；均匀随机无法保证这一点。
- buffer 有限时，顺序预取数据的使用概率接近 100%，随机预取数据的使用概率可能很低。

推荐以下自适应设计。

## 4.2 建议架构

```text
应用 read/seek/readFully
          |
          v
  Access Pattern Detector
   AUTO / SEQUENTIAL / RANDOM
          |
     +----+----------------+
     |                     |
     v                     v
Demand Range Cache   Async Sequential Prefetch
     |                     |
     +----------+----------+
                v
       Range Merge/Scheduler
                |
       Global Memory Budget
                |
       AWS SDK Async/CRT S3
```

### 层 1：Demand Range Cache

- 所有模式都先查 cache。
- cache 只保存实际请求触达的块，优先级高于推测性预取块。
- key 至少包含 bucket、key、对象版本标识（Version ID 或 ETag）和块号，避免对象更新后返回旧数据。
- 使用 LRU、TinyLFU 或带频率的分段 LRU，防止一次顺序扫描污染热点 cache。

### 层 2：访问模式识别

每个流维护最近 N 次访问：

- offset；
- length；
- 与上次读取末尾之间的 gap；
- seek 方向；
- demand cache 命中；
- 预取数据实际消费比例。

建议状态：

| 状态 | 行为 |
|---|---|
| `AUTO` | 保守按需读，收集前 2～4 次访问 |
| `SEQUENTIAL` | 大 Range、异步向前预取 |
| `RANDOM` | 精确 Range 或小窗口，不向前盲目预取 |
| `LOCALITY`（可选） | 对确认的热点页做 cache，但不连续预取 |

转换建议：

- 连续 2～3 次单调向前，且 gap 小于阈值：进入 `SEQUENTIAL`。
- 后向 seek：立即退出 `SEQUENTIAL`。
- 前向跳跃大于当前窗口或预取块：转为 `RANDOM` 或回到 `AUTO`。
- 预取消费率持续低于阈值，例如 50%：减小预取或关闭。
- 为避免模式来回抖动，状态转换应有滞后和最短驻留时间。

## 4.3 顺序模式策略

### 使用异步环形 buffer

- 一个块供调用方消费；
- 1～N 个块异步下载；
- 消费完成后复用最旧 buffer。

初始建议：

- block size：1～4 MiB；
- prefetch depth：2～4；
- 单流初始预算：8～16 MiB；
- 经过测量确认网络和内存允许后，再尝试 8 MiB 或更大块。

本实验的 8 MiB×8 在顺序读上很快，但 72 MiB/流的潜在占用不适合作为普遍默认值。

### 动态计算预取深度

可用以下近似关系：

```text
需要提前的数据量 ≈ 应用消费速率 × 一个远端请求的等待时间
prefetch depth ≈ ceil(需要提前的数据量 / block size) + 安全余量
```

如果应用消费慢，1 个后续块已经足够；如果应用消费快且 RTT 高，可以增加深度。达到 NIC、CPU 或全局内存上限后继续加深没有价值。

### 并行分段而不是重复扫描

多线程完整下载时，应把对象切成互不重叠的连续分区：

```text
线程 0：[0, P)
线程 1：[P, 2P)
线程 2：[2P, 3P)
线程 3：[3P, EOF)
```

不要像当前用例 003 那样让每个流交错读取相邻小 Range，否则会破坏流内连续性并可能重复传输。

### 优先评估 AWS CRT/Transfer Manager

如果业务只是把整个对象下载到文件或连续输出，优先使用并测试 AWS CRT S3 client 或 Transfer Manager。自研层应聚焦它们没有直接覆盖的可 seek、局部读取和热点复用场景。

## 4.4 随机模式策略

### 默认不进行方向性预取

随机模式的远端读取范围建议为：

```text
fetch size = max(request length, minimum range)
```

`minimum range` 可从 32～64 KiB 起测，但不应无条件使用 8 MiB。若业务大量读取 4 KiB，是否扩大到 64 KiB应由以下指标决定：

- 相邻字节后续命中率；
- GET RTT；
- S3 请求成本；
- 多传输字节成本；
- 网络是否为瓶颈。

### 对齐 cache page，但不要强制同等大小的 GET

cache page 可以是 64～256 KiB，而远端 GET 可根据请求和相邻待处理请求动态合并。这样能避免“为了 cache 一个小页，必须读取固定 8 MiB”的耦合。

### 已知多个 Range 时使用 vectored 读取

如果调用方能一次提交多个 offset：

1. 按 offset 排序；
2. 合并间隔较小的 Range；
3. 对距离较大的 Range 并发 GET；
4. 将大响应拆回各逻辑请求。

Hadoop S3A Vectored IO 也采用“最小 seek 间隔、最大合并大小和最大并发 Range”这一思路。

可使用成本条件决定是否合并：

```text
合并条件：
传输 gap 所需时间 + 额外字节成本
<
额外一次 GET 的 RTT + 请求成本
```

### 只有检测到局部性后才扩大 cache

对于聚簇随机或 footer/索引访问：

- 首次读取保持小 Range；
- 同一页或邻近页短时间内再次命中后，提高该区域 cache 优先级；
- cache 热点块，不要顺序预取热点块之后的无关数据；
- 对完全均匀随机访问，保持接近零的推测性 buffer。

## 4.5 全局内存预算

不要使用固定的“每流 N 个块”。设进程总预算为 `B`：

```text
所有流的 demand cache
+ 所有 in-flight response buffers
+ 所有 speculative prefetch buffers
<= B
```

建议优先级：

1. 正在等待的 demand read；
2. 已被重复命中的热点 cache；
3. 已确认顺序流的下一个预取块；
4. 更远的推测性预取。

当内存紧张时，先取消或淘汰第 4 类，再降低顺序预取深度，最后淘汰低频 demand cache。

如果必须预先切分预算，可以从以下比例开始实验：

- 60%～80%：已确认顺序流的 in-flight/prefetch；
- 20%～40%：随机 demand cache 和热点页；
- 均匀随机负载下，将未使用的顺序预算动态归还给全局池，而不是强制填满随机 cache。

## 4.6 连接、重试和取消

- 使用异步 SDK 或 CRT client，让 buffer 填充不阻塞调用线程。
- 限制全局并发 GET 和 in-flight bytes，避免连接池、S3 或 NIC 过载。
- 每个分段独立重试，避免大对象任一位置失败后从头开始。
- seek 使预取失效时，取消尚未开始的任务；已接近完成的小任务可根据剩余成本决定是否保留。
- 对慢请求可做受控的 hedged retry，但必须限制额外流量。

## 4.7 必须采集的指标

实现是否成功不能只看应用有效吞吐，至少应输出：

| 指标 | 用途 |
|---|---|
| logical bytes | 应用实际请求量 |
| remote bytes | 实际从 S3 获取的数据量 |
| read amplification | `remote bytes / logical bytes` |
| GET count | 判断请求合并效果 |
| demand/prefetch bytes | 判断带宽分配 |
| prefetch useful bytes | 判断预测准确率 |
| memory/disk cache hit rate | 判断 cache 价值 |
| cancelled/wasted bytes | 判断错误预测成本 |
| time to first byte | 识别请求 RTT |
| P50/P95/P99 logical latency | 观察应用体验和长尾 |
| connection wait / buffer wait | 识别本地资源瓶颈 |

## 4.8 推荐的实现顺序

### 阶段一：先证明请求合并价值

实现同步的 `BufferedRangeReader`：

- 维护一个 `[bufferStart, bufferEnd)` 窗口；
- 命中窗口直接复制；
- 未命中时按 1 MiB 或自适应大小发起 Range GET；
- 后向或远距离随机访问只取小窗口。

先验证它能复现 fadvise 在 1 MiB 顺序读和短前向 seek 中的主要收益。

### 阶段二：增加顺序异步预取

- 检测连续访问后预取下一个窗口；
- 从 depth=1 开始；
- 再根据消费速度增加深度；
- 与 AWS CRT/Transfer Manager 做完整下载对照。

### 阶段三：增加随机热点 cache 和 vectored API

- 支持批量 Range；
- 合并相近 Range；
- 对确认复用的页进行 LRU/TinyLFU 缓存；
- 均匀随机保持按需读取。

### 阶段四：加入全局预算和自动调参

- 在多流并发下统一限制内存和 in-flight bytes；
- 根据命中率、读放大和 P99 自动调整 block size、cache 和 prefetch depth。
