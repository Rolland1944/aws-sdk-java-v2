# 智能对象存储 SDK —— 第三阶段工作文档（PROJECT3）

> **定位**：本文件是 2026-07-30「对象存储 SDK 性能优化与论文推进研讨会」之后的**新阶段权威路线**。
> 上一阶段的全部背景、实验证据与资产清单见 `PROJECT2.md`（不作废，作为**证据库与资产索引**继续引用）。

## 0. 一句话总结

上一阶段证明了「在单个应用内、在四条 S3A 风格策略之间做自适应选择」这个杠杆**太弱**（时延天花板约 10%、
字节天花板 0.2%），而**缓存本身**才是真正的收益来源（GET −43.7%、IO 时延 −23.7%）。本阶段因此
**放弃「选策略」这一动作空间**，改为在 SDK 内部围绕**五个访存优化维度**（缓存 / 同步转异步 / 预取 /
IO 合并 / 长尾消除）重新设计参数化决策层，并把评测从本地模拟器搬到**真实 AWS S3 / 腾讯云 COS 的百 GB 级
数据**上，目标是 **9 月中旬完成主体实验、冲刺 SIGMOD 10 月 17 日截稿**。

## 2. 新的项目定位：Intelligent SDK

### 2.1 目标陈述

> 在对象存储 SDK 内部实现一个**对应用完全透明**的智能访存层：应用照常调用 `getObject` / `read(offset,len)`，
> SDK 自动根据在线观测到的负载特征，在**五个访存优化维度**上调整自身行为，无需用户配置任何参数、
> 无需应用改一行代码。

三条设计原则（相对 PROJECT2 有实质变化）：

1. **无配置（zero-config）**：PROJECT2 里 `cacheBudgetMiB / prefetchBlockMiB / prefetchDepth / apps` 全靠系统属性
   手动指定，而 §8.4 证明这些参数决定了整个工况。本阶段这些量**必须由 SDK 自己在线确定**，用户至多给一个
   「内存上限」。**「参数由谁决定」本身就是论文的贡献点之一。**
2. **参数化而非枚举化**：不再让模型在 N 条命名策略里做分类；模型输出的是每个维度上的**少量离散档位**
   （见 §3），维度之间由预算仲裁层协调。
3. **安全先于性能**：任何维度的激进档位都受硬约束（内存、in-flight bytes、并发 GET、额外请求比例）压制；
   模型异常、置信度不足、预算紧张时逐维度降级到保守档，最差回退到 passthrough demand read。

### 2.2 为什么「下沉到 SDK 层」不是换个说法

S3A 的 `fadvise` 模式是**面向应用暴露的开关**（用户要选 seq/random/normal），本质是把决策推给用户。
下沉到 SDK 层意味着三件具体的事：

- 决策点从「应用启动时选一次」变成「运行时按窗口连续调整」；
- 决策的观测面从「应用声明的意图」变成「SDK 实际看到的 offset/length/时序/时延分布」——后者是真实的，
  且 SDK 是**唯一**同时看得到「上层请求形状」和「下层网络时延分布」的层；
- 优化维度从「预读窗口大小」这一个旋钮，扩展到请求合并、同步异步转换、长尾重发等 S3A 根本不涉及的维度。

**第三点是本阶段相对上一阶段最大的增量**：上一阶段的四条策略其实只在动一个旋钮（每次读该抓多大、怎么对齐），
所以四个执行器坐在同一份缓存后面时 IO 形状高度趋同（PROJECT2 §9 2026-07-28 晚条已经诊断出这一点：
判准率差 80 个百分点，端到端只差 4%）。新的五个维度**在机制上互不重叠**，这是收益能叠加的前提。

## 3. 五大优化维度（新的动作空间）

> **总原则**：每个维度独立定义「决策变量（档位）—观测信号—安全约束—验收指标」。
> 先各自做成可单独开关的组件并**逐维度做消融**，再讨论联合决策。禁止一上来就做端到端联合模型。

### 3.0 维度总览

| 维度 | 代号 | 机制 | 上一阶段证据 | 预期收益来源 | 现有代码基础 |
| --- | --- | --- | --- | --- | --- |
| 缓存管理 | **D1** | 容量分配、块粒度、准入、淘汰 | 已证 −23.7% 时延 / −43.7% GET；剩余字节空间的 99.6% 在这里 | 命中率 + 字节复用 | `internal.cache`、`internal.budget`（成熟） |
| 同步转异步 | **D2** | 同步 API 下透明批处理与并发化 | 未做 | 并发度 / 重叠 | 有 sync 与 async 两条平行链路，无转换层 |
| 预取 | **D3** | 置信度门控的顺序预取 | 推测预取 useful 4%/0%，**须重设计** | 仅在确认顺序段上掩盖 RTT | `internal.prefetch.Prefetcher`（需改门控） |
| IO 请求合并 | **D4** | 邻近/跨线程 range 合并成大 GET | depth-0 块对齐合并在 RTT 下**高度有效** | 省 RTT（每 GET 50ms 量级） | `MultimodalPlanner` 的 64KiB 对齐（雏形） |
| 长尾延迟消除 | **D5** | 超时探测 + 对冲重发 + 负载感知抑制 | 完全未做（仅在旧汇报里作为设想） | P99/P999 | 无 |

### 3.1 D1 —— 缓存管理

**现状**：容量是 `-Ds3arr.cacheBudgetMiB` 手动给的；块粒度固定；淘汰恒为 LRU；**无准入控制**（任何抓回来的块
都进缓存）。

**为什么它是第一优先级**：§8.7 的 284 倍差距——字节维度上策略路由只能碰到 3.25MiB，而离字节地板还有 923.7MiB，
这 923.7MiB 全部在**缓存粒度与淘汰/准入策略**里。上一阶段把力气花在了那 3.25MiB 上。

**决策变量**：

| 变量 | 档位 | 说明 |
| --- | --- | --- |
| 有效容量 | 在用户给定的内存上限内自适应伸缩 | 由估计的工作集/预算比 ρ 驱动；ρ≫1 时收缩（缓存无用，省内存给合并缓冲） |
| 块粒度 | {64KiB, 256KiB, 1MiB, 4MiB} | 小读密集 → 小块（省字节）；大顺序 → 大块（省 GET） |
| 准入控制 | {always, reuse-gated, never} | **新增**：估计重用距离 > 容量的块直接不入缓存（扫描型负载不污染缓存） |
| 淘汰 | {LRU, LFU-ish/频率感知, cost-aware} | Zipf 型 embedding 用频率感知；顺序扫描用 MRU 友好行为 |

**观测信号**：重用距离直方图（用采样近似，不做全量）、工作集估计（HyperLogLog / 采样去重）、
ρ = 工作集/容量、命中率随窗口的斜率、块内实际使用字节占比。

**⚠ 反面教材（必须写进代码注释与论文）**：`cacheHitRate` 是**误导性指标**——PROJECT2 §8.7 中强制预取的命中率
随激进度单调从 0.526 升到 0.733，而同期总成本恶化 31 倍。**任何维度都不得以命中率作为优化目标或验收指标。**

**验收指标**：真实云上 wall-clock、P50/P95/P99、GET 数、remote bytes、读放大、峰值内存。

### 3.2 D2 —— 同步转异步

**现状**：SDK 里 sync（`S3ClientObjectStore` → `AdaptiveRangeReaderImpl`）和 async
（`S3AsyncClientObjectStore` → `PrefetchingRangeReaderImpl`）是两条**平行实现**，没有任何转换。
应用用同步 API 就永远拿不到并发收益。

**目标**：应用调用同步 `read()`，SDK 内部把请求投递到共享队列，由 worker 池以异步方式发出，
调用线程仅在自己那份结果上阻塞。这带来两件事：

1. **多线程场景下的跨线程合并**：多个线程对同一对象的邻近区间在队列里被 D4 合并成一次 GET；
2. **并发度自适应**：并发 GET 数不再等于调用线程数，可以在带宽未饱和时提高、饱和时回落。

**决策变量**：是否启用转换（单线程低时延场景应关闭）、批处理等待窗口 w（微秒级，等更多请求进来以便合并）、
worker 并发度。

**关键风险（必须实测）**：等待窗口 w 会给**每一次**读加上最多 w 的延迟，而只有一部分读能因此合并获益。
w 必须由在线的「到达率 × 可合并率」决定，且在单线程负载下自动为 0。**这个 trade-off 曲线本身就是一张论文图。**

**安全约束**：语义必须与同步调用完全一致（异常、取消、超时、字节内容）；worker 池不得与用户线程互相死锁；
关闭时零行为变化。

### 3.3 D3 —— 预取（重新设计）

**上一阶段的结论必须原样继承**：投机深度 ≥1 的「猜下一块」**无效且单调有害**——useful 4%（mixed）/ 0%（epoch），
成本随激进度恶化 31 倍。**本阶段不重复这个错误。**

**重新设计的原则：预取只在「已确认」的顺序段上开启，不做预测。**

| 决策变量 | 档位 | 门控条件 |
| --- | --- | --- |
| 是否预取 | on / off | 仅当同对象连续 N 次读构成单调顺序段（N 待定，从 4 起测）**且** ρ 允许缓存住预取块 |
| 深度 | {1, 2, 4} | 随已确认顺序段长度增长，段一断立即回落到 0 并取消在飞块 |
| 块大小 | 与 D1 块粒度绑定 | 不独立设档，避免动作空间爆炸 |

**与 D4 的边界（重要）**：PROJECT2 §8.7 已经辨明——`(1MiB, depth 0)` 下的 `s3a_prefetch` **不是预取**，
而是「块对齐把需求读合并成更大的单次读」。这部分机制本阶段**归入 D4**，D3 只保留真正的投机部分。
这样两个维度的消融结果才能各自解释清楚。

**验收**：D3 单独开启相对关闭，在**顺序型负载**上 wall-clock 改善显著且 wasted bytes 有界；在随机型负载上
必须**自动不开启**（wasted ≈ 0），这是门控是否有效的直接证据。

### 3.4 D4 —— IO 请求合并

**这是当前最有把握的收益来源**：mixed holdout 平均读只有 226KB，100MiB/s 下传输 2.2ms，而 RTT 是 50ms，
**RTT 项压过字节项约 23 倍**（§8.6）。少发一次 GET 就是省 50ms。

**两类合并**：

| 类型 | 场景 | 机制 |
| --- | --- | --- |
| **时间维（单线程）** | 一个 reader 短时间内发出多个邻近 range | 在窗口内累积，间隙 ≤ g 且总浪费 ≤ w 时合并成一次 GET |
| **空间维（跨线程 / 跨 reader）** | 多线程同时读同一对象的不同区间（依赖 D2 的队列） | 队列里按对象归并，间隙 ≤ g 合并 |

**决策变量**：间隙阈值 g（合并两个 range 之间允许跨过多少无用字节）、单次合并上限、等待窗口（同 D2 的 w）。
g 的最优值直接由 RTT/BW 比决定：**跨过 g 字节的成本是 g/BW，省下的是一次 RTT**，所以理论上
`g* ≈ RTT × BW`（50ms × 100MiB/s ≈ 5MiB）。这是一个**可以在线自估**的量——SDK 能同时测到 RTT 和实际带宽。

> **这条公式是本阶段最重要的设计洞察**：它把「该抓多大」从一个需要学习的黑盒问题，变成一个由在线测量的
> RTT 和 BW 直接算出的量。模型只需要处理它管不了的部分（是否会被浪费、缓存装不装得下）。
> 论文里应作为一个 analytical model 单独成节，并用实验验证 g* 的预测能力。

**安全约束**：单次合并请求大小硬上限（沿用 `maxSingleFetchBytes` 思路）；浪费字节比例上限；
合并不得跨对象边界。

### 3.5 D5 —— 长尾延迟消除（Straggler Mitigation）

**现状**：完全未实现。仓库中无 hedge/straggler 相关代码。

**机制**：SDK 内部维护每个 endpoint 的时延分布；当某个在飞 GET 的等待时间超过动态阈值（如当前 P95）时，
自动发出一份对冲请求（hedged request），先返回者胜出，另一个取消。

**会议特别强调的约束——负载感知抑制**：当整体 IO 负载已经很高时，重发请求不但没用，还会加剧拥塞。
必须实现抑制器，满足任一条件即禁止对冲：

| 抑制条件 | 观测量 |
| --- | --- |
| 并发已达上限 | `ConcurrencyLimiter` 饱和度 |
| 带宽已饱和 | 实测吞吐进入平台期（增加并发不再提高吞吐） |
| 对冲收益率过低 | 近期对冲的胜出率低于阈值（说明慢是全局的，不是个别请求的） |
| 额外请求预算耗尽 | 对冲请求数占总请求数超过上限（建议 ≤5%） |
| 时延分布方差小 | P99/P50 比值低，说明没有长尾可消 |

**决策变量**：是否启用、触发分位数（P90/P95/P99）、最大对冲比例。

**验收指标**：**P99 / P999 wall-clock 改善**为主指标；额外 GET 数与额外字节为必须同时报告的代价指标。
这是唯一一个「平均值可能不动、只动尾部」的维度，评测口径必须单列。

> **风险提示**：真实云上的长尾是否显著、是否稳定可复现，直接决定这个维度有没有论文价值。
> **8 月必须先做一次纯观测实验**（不实现对冲，只在真实 S3/COS 上大量发 GET 记录时延分布），
> 看 P99/P50 比值。若长尾不显著，D5 立即降级为次要维度，把时间还给 D1/D4。

## 4. 决策模型的重新设计

### 4.1 从「四分类」到「多维小决策」

上一阶段：10 维特征 → 一棵决策树 → 4 个策略名之一。
本阶段：共享特征 → **每个维度一个独立的小决策头** → 5 组档位 → 预算/安全仲裁层 → 执行。

```
            ┌──────────────── 在线观测 ────────────────┐
            │ IO 形状特征（继承 10 维，跨对象窗口）      │
            │ + 新增：重用距离、工作集估计、ρ            │
            │ + 新增：调用线程并发度、到达率             │
            │ + 新增：RTT / 带宽 / 时延分位数（在线自估） │
            └────────────────────┬───────────────────┘
                                 │
     ┌──────────┬──────────┬─────┴─────┬──────────┬──────────┐
     │ D1 头     │ D2 头     │ D3 头     │ D4 头     │ D5 头     │
     │ 容量/粒度 │ 转换/窗口 │ 门控/深度 │ g/上限    │ 阈值/开关 │
     └──────────┴──────────┴─────┬─────┴──────────┴──────────┘
                                 │
                    ┌────────────┴────────────┐
                    │ 仲裁层：全局内存 / in-flight │
                    │ / 并发 / 额外请求比例 硬约束  │
                    │ 冲突时按 D1 > D4 > D2 > D3 > D5 降级 │
                    └────────────┬────────────┘
                                 │
                          执行（每 app 隔离）
```

**为什么分解而不是一个大模型**：

1. 可消融——论文必须能说清每个维度各贡献多少；
2. 可解释与可审计——每个头都是小决策树，阈值可读；
3. 安全——单个头出错只影响一个维度，且有各自的保守档；
4. 符合会议要求的「简单决策树或小型神经网络，避免过度复杂化」。

### 4.2 模型形态与训练

- **首选：每维一棵浅决策树**（深度 ≤6），复用上一阶段已跑通的 `export_policy_tree.py` → JSON →
  `DecisionTreePolicySelector` 无依赖推理 → golden 一致性测试这条**完整工程链路**。这是上一阶段最值钱的
  可复用资产，不要重建。
- **备选：小型 MLP**（≤2 隐层、几十个神经元），仅当树在某个维度上明显不够时启用；同样导出为 JSON 常量。
- **部分维度可能根本不需要模型**：D4 的 g* 有解析式（§3.4），D5 的阈值就是在线分位数。**能用公式的不用模型**——
  这既减少代码量，也让论文的机制部分更有说服力。
- **标注口径**：**必须用真实云上的 wall-clock 打标签**。上一阶段的惨痛教训（§8.7）是标签口径错了会让整个结论
  反向：字节口径下自适应天花板 0.14%，成本口径下 10.71%，两者给出方向相反的答案。本阶段**只认 wall-clock**，
  bytes / GET 作为必须同时报告的代价指标，不作为优化目标。
- **训练数据**：真实云上的参数扫描结果（每个维度在若干负载 × 若干工作点上的实测 wall-clock）。
- **滞后（hysteresis）**：继续保留，防止抖动；但要重新测滞后长度对每个维度的影响（上一阶段测得滞后对判准率
  影响为 0，切换本身无直接代价）。

### 4.3 必须保留的工程约束（继承自 PROJECT2 §7.2）

1. 不把 Python/sklearn 运行时带进 Java SDK；模型只以 versioned JSON + checksum + provenance 形式进入 classpath。
2. Java 端特征实现与训练侧**逐位一致**，用 golden vectors 测；窗口作用域必须是**跨对象、per-app 共享**
   （S3 路径已经是这样，不要退回按对象窗口）。
3. 硬预算优先于模型输出；未知输出 / 异常 / 预算不足 → 逐维度降级 → 最差 passthrough。
4. 缓存 key 必须含 bucket/key + VersionId 或 ETag。
5. 指标内建：每维度的档位分布、切换次数、各自的收益/代价计数器。
6. 功能开关默认关闭；关闭时行为与原生 SDK 逐字节一致。

## 5. Track 2 复活：Writer 重写建议（8 月优先事项）

> 会议待办第一条：**8 月优先尝试第二大点**。这是本阶段 8 月的主攻方向之一，与实验环境迁移并行。

### 5.1 定位

Reader 侧（第 3 节）能做的是「在给定的文件布局下把访问做得更省」；Writer 侧要做的是
「**让布局本身更适合被访问**」。两者相乘才有会议里提到的更大收益空间。
约束不变：**非侵入式**——不改文件格式、不做地址重映射（PROJECT2 已否决，需维护映射表且表丢失即文件不可读）。

### 5.2 工作流

```
① 采集：SDK 侧已有的 offset 级 trace（复用现有采集链路）
        ↓
② 挖掘：共访问模式分析
        - 哪些列/块总是被一起读（频繁项集 / 共现图聚类）
        - 哪些读被 row-group 边界切碎
        - 哪些对象小到 RTT 主导（该合并成大文件）
        - 哪些字段从未被读（可下沉冷存）
        ↓
③ 定位：把访问模式映射回**应用代码中的写入点**
        （AI 辅助：读应用源码，找到 Parquet/Lance writer 的配置与 schema 定义位置）
        ↓
④ 产出：可读的优化建议 + 可直接 apply 的 Code Diff / PR
        - row-group / page 大小
        - 列顺序与共置
        - 分区键
        - 排序键（影响谓词下推与顺序性）
        ↓
⑤ 验证：按建议重写数据 → 用同一条 trace 在真实云上重放 → 报告端到端收益
```

### 5.3 AI 辅助的边界（必须自我克制）

- **AI 用于「代码定位与 Diff 生成」，不用于「性能判断」**。改哪里、改成什么值，由 ② 的量化分析给出；
  AI 负责把这个结论翻译成对具体代码库的最小改动。
- 所有建议必须**可验证**：每条建议附带「预期改善多少、依据是哪几条 trace 统计量」，并在 ⑤ 里实测。
  不可验证的建议不输出。
- 产出的 PR 必须是**建议性**的，人工审核后才合入；不做自动合并。

### 5.4 8 月的最小可交付（MVP）

1. 一个分析器：吃 trace，输出共访问矩阵 + 切碎率 + 冷字段列表 + 建议参数（JSON + 人读报告）；
2. 在 **1 个负载**（建议 TPC-H parquet，布局旋钮最清晰、收益最容易归因）上端到端跑通 ①→⑤；
3. 一次真实的 Code Diff 演示（对生成数据的 writer 脚本）；
4. 量化结果：按建议重写后，同一条 trace 的 wall-clock / GET / bytes 改善多少。

**判据**：若 MVP 在 TPC-H 上拿不到可观改善（建议门槛 ≥10% wall-clock），Track 2 在论文中降级为一节 discussion
而非独立贡献点，8 月下旬即止损，把时间转给第 3 节的五维实现。

## 6. 实验环境迁移：真实云 + 百 GB 级

### 6.1 为什么必须迁移

上一阶段所有数字都来自本地合成对象 + 注入的 `rttMs/bwBps` 一阶代理。它不具备：
真实的时延分布（**没有长尾就无法研究 D5**）、真实的带宽饱和行为（**D2/D4 的并发与合并上限无从确定**）、
真实的服务端行为（分片、限流、连接复用）。而 §8.6 已经说明 cost proxy 在 depth≥1 下对投机 GET 系统性偏悲观。

**决定：本阶段所有对外结论必须来自真实 AWS S3 或腾讯云 COS。模拟器只用于参数粗筛。**

### 6.2 环境与数据规模

| 项 | 规格 | 说明 |
| --- | --- | --- |
| 主环境 | AWS S3（同 region EC2 客户端） | 已有 `-Ds3arr.backend=s3` 接线（PROJECT2 §8.8），复用 |
| 对照环境 | 腾讯云 COS | 需新增 endpoint 适配（S3 兼容协议，改动应很小）；**双云对照是论文的加分项** |
| 数据规模 | **≥100GB**（目标 100–500GB） | 会议明确要求；上一阶段 mixed_holdout 仅约 16GiB |
| 客户端 | 同 region 云主机，记录实例规格 / 网络带宽 / JDK 版本 | 所有实验元数据必须归档 |

**为什么规模必须上去**：§8.4 已经证明**工作集/预算比 ρ 是决定一切的工况变量**。16GiB 数据配 256MiB 缓存，
ρ 已经偏大；但更重要的是，百 GB 级才能覆盖 ρ 从「缓存装得下」到「远超缓存」的完整区间，才能把
**「参数随 ρ 如何变」这条曲线**画完整。这条曲线是论文的核心图之一。

### 6.3 数据集设计（百 GB 级）

| 负载 | 目标规模 | 生成方式 | 保留理由 |
| --- | --- | --- | --- |
| TPC-H / 分析查询 | SF100（≈100GB） | DuckDB dbgen → Parquet | 顺序大块，D4 主场；Track 2 的布局旋钮最清晰 |
| 向量检索（Lance） | 1 亿量级向量或多副本放大 | 现有 `make_lance_dataset` 链路放大 | 海量小随机读，D4 跨线程合并 + D1 粒度的主场 |
| ML 训练 / embedding | 放大到十 GB 级 embedding 表 + 多 epoch | MovieLens 真实 Zipf 序列放大 | 强时间局部性，D1 准入/淘汰的主场 |
| 多模态 | blob 长尾放大到百 GB | 现有合成器 + 真实 size 分布 | 双峰请求大小，考验维度间协调 |
| 混合 holdout | 上述按比例拼接 | 复用 `tools/build_mixed_trace.py` 逻辑放大 | 多应用场景，也是「自适应省掉人工调参」这一价值主张的唯一舞台 |

**成本预估（需在动手前确认）**：100GB 标准存储在 S3 约 $2.3/月；同 region 内传输免费；GET 请求
$0.0004/1000（百万次 GET 约 $0.4）。**主要成本是客户端云主机的机时，不是存储**。腾讯云 COS 若能拿到
合作资源则优先在 COS 上跑规模实验（见 §9 待办）。

### 6.4 工具改造清单

| 工具 | 改造 |
| --- | --- |
| `MinioTraceObjectProvisioner` | 更名并泛化为 `TraceObjectProvisioner`，支持 AWS S3 / COS endpoint；已按对象大小幂等跳过，需增加**分片并行上传**以应付百 GB |
| `AdaptiveReaderSystemBenchmark` | 从「四列固定对比」改造为「按维度消融」的矩阵驱动；重复次数与 median 汇总下沉到工具内，不再靠外部人工汇总 |
| 凭证 | 当前只支持静态 key/secret；补 instance profile / STS，避免长期凭证落盘 |
| 结果归档 | 每次实验的原始 CSV + 环境元数据自动落到 `docs/adaptive-range-reader/results/<cloud>_<date>/`（`target/` 会被 `mvn clean` 清空） |
| `tools/prefetch_simulator.py` | 保留但标注「仅用于粗筛，结论不得引用」 |

### 6.5 度量口径（本阶段唯一标准）

**主指标**：端到端 wall-clock（整条 trace）、每次读的 P50/P95/P99/P999。
**必须同时报告的代价指标**：GET 数、remote bytes、读放大、峰值内存、CPU、额外请求比例（D5）。
**禁止作为优化目标**：cacheHitRate（§3.1 已说明为何误导）、单独的 remote bytes（§1.2 已说明会给出反向结论）。
**重复性**：每个配置至少 5 次独立运行，报告 median 与分布，不取最快一轮。
