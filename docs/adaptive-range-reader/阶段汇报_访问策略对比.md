# 湖仓 S3 自适应预取 —— 访问策略对比阶段汇报

> 汇报人：李皓月　|　阶段：Replay Simulator 策略基准评测　|　日期：2026-07-07

---

## Summary

本阶段基于 `prefetch_simulator.py`（trace-driven replay simulator）对 10 种策略（5 个现有系统 baseline + 5 个规则模板）在 7 条真实负载 trace 上做了离线回放评测。核心结论有三条：

1. **没有单一策略能在全部负载上取胜**——最优策略随负载类型翻转，顺序扫最优的策略在随机读上可产生 68–143 倍读放大，反之亦然。这是"混合负载必须自适应"的直接定量证据。
2. **对每种单一负载，规则模板已能接近静态最优**——`template_locality` 在多 epoch 扫描上远端字节最少，`template_multimodal` 在异构多模态上废字节接近零，规则足够在单一负载上取得良好结果。
3. **`s3a_prefetch` 的成败由"工作集 vs 缓存预算"决定**——工作集小于预算时接近最优（fmnist amp=0.04），超出预算后块被反复淘汰重取（SIFT1M amp=68）。固定块大小耦合取回粒度与缓存粒度是根本缺陷。

**推论**：单负载上不需要在线学习，规则模板已能接近最优。在线学习（contextual bandit）的价值点在于**混合负载与负载切换**，这是下一阶段的关键验证目标。

## 1. 实验设置

### 1.1 评测框架

脚本：`prefetch_simulator.py`（trace-driven replay，不需要连 S3）

成本模型（先用可标定的简化版）：

```
latency_per_GET = request_rtt + transferred_bytes / effective_bandwidth
```

参数：`request_rtt = 50 ms`，`bandwidth = 100 MiB/s`，`cache_budget = 256 MiB`。

> **注意**：cache 命中记 0 延迟，prefetch 记为完全异步重叠。`lat_sum` 系统性偏袒预取/缓存类策略，**跨策略排序以 remote bytes / read amplification / GET 次数为主**，`lat_sum` 作辅助参考。

### 1.2 评测 trace

| trace | 负载类型 | 逻辑读次数 | 逻辑总量 |
|---|---|---:|---:|
| `tpch_sf1_full` | TPC-H 列式分析（22 条 SQL） | 4,855 | 1.2 GiB |
| `ml_taxi_epoch` | ML epoch_scan（NYC taxi，4 epoch） | 659 | 1.0 GiB |
| `lance_sift1m_lance_all` | Lance 向量检索（SIFT1M 514MB 文件） | 181,224 | 9.9 GiB |
| `lance_fminist_lance_all` | Lance 向量检索（fmnist 188MB 文件） | 119,127 | 4.0 GiB |
| `ml_emb_real` | ML embedding_gather（真实 Zipf，MovieLens） | 180,964 | 66.7 MiB |
| `ml_emb_uniform` | ML embedding_gather（均匀随机，MovieLens） | 180,964 | 66.7 MiB |
| `mm_n2000_mm_all` | 多模态检索（小向量 + 大 blob） | 2,785 | 542.8 MiB |

### 1.3 评测策略

**现有系统 baseline（复刻 Hadoop/AWS 语义）**：

| 策略名 | 模拟对象 | 关键参数 |
|---|---|---|
| `aws_range_get` | AWS SDK 精确 Range GET | 每次读一个独立 GET，无缓存 |
| `s3a_seq` | Hadoop S3A fadvise sequential | 长流 + 前向 skip；`stream_window=128MiB` |
| `s3a_random` | Hadoop S3A fadvise random | `readahead=64KiB`，小窗口精确读 |
| `s3a_normal` | Hadoop S3A fadvise normal | 初始 sequential，遇后向 seek 切 random |
| `s3a_prefetch` | Hadoop S3A prefetch | 固定 `block_size=8MiB`，异步预取 8 块 |

**规则模板（基于四类负载访问规律）**：

| 策略名 | 设计意图 | 关键机制 |
|---|---|---|
| `template_seq` | 顺序扫描 + 小 gap 合并 | 2MiB 窗口 + gap 成本判据 |
| `template_small_random` | KB 级随机读合并 | 64KiB page 对齐合并，避免小 GET |
| `template_locality` | 多 epoch 重复/热点缓存 | 首次保守读；二次命中后放大至 256KiB page |
| `template_multimodal` | 异构双峰两段式 | 小读(<16KiB)→小页合并；大读→精确整取 |
| `template_auto` | 基于可观测特征的轻量状态机 | 按顺序性/请求大小/命中率动态选策略 |

## 2. 各负载最优策略

### 2.1 结论总表

| 负载 | 最优策略 | 次优 | remote bytes | read amp | lat_sum(s) | 原因摘要 |
|---|---|---|---:|---:|---:|---|
| TPC-H 分析 | **s3a_random** | template_auto | 203 MB | 0.16x | 42.7 | 后向 seek 使大窗口无效；64KiB readahead 缓存列分片重叠读 |
| ML epoch_scan | **template_locality** | s3a_seq | 253 MB | 0.25x | 18.0 | 多 epoch 重复访问同一 page；频率感知将热点页放大缓存 |
| Lance SIFT1M（大文件） | **template_locality** | template_small_random | 11.9 GB | 1.18x | 2,584 | 工作集 > 预算；按频率提升热点 GET 减少最多 |
| Lance fmnist（小文件） | **s3a_prefetch** | template_locality | 182 MB | 0.04x | 1.4 | 工作集 (188MB) < 预算 (256MB)，整个数据文件被块预取覆盖 |
| ML embedding_gather | **s3a_prefetch** | s3a_random | 0.9 MB | 0.01x | 0.1 | 67MB 工作集远小于预算；整文件首轮缓存后几乎全命中 |
| 多模态检索 | **template_multimodal** | s3a_random | 428 MB | 0.79x | 88.3 | 两段式自适应：小读合并 + 大 blob 精确取，废字节接近零 |

> `aws_range_get` 作为下界锚点：amp=1.0，GET 次数 = 逻辑读次数，lat_sum 最高（除 embedding 外均为最差）。

### 2.2 per-负载详细分析

#### TPC-H 分析（列式扫描 + 后向 seek）

| 策略 | GETs | remote | amp | waste | hit% | p99 ms | lat_sum s |
|---|---:|---:|---:|---:|---:|---:|---:|
| `aws_range_get` | 4,855 | 1,243 MB | 1.00 | 0 | 0 | 56 | 255.2 |
| `s3a_seq` | 2,243 | 4,112 MB | 3.31 | 2,869 MB | 0 | 80 | 153.3 |
| **s3a_random** ✓ | **814** | **203 MB** | **0.16** | **6 MB** | **83** | 56 | **42.7** |
| `s3a_normal` | 827 | 203 MB | 0.16 | 6 MB | 83 | 56 | 43.4 |
| `s3a_prefetch` | 166 | 1,109 MB | 0.89 | 673 MB | 98 | 111 | 8.0 |
| `template_seq` | 355 | 648 MB | 0.52 | 551 MB | 93 | 70 | 24.2 |
| `template_small_random` | 766 | 245 MB | 0.20 | 50 MB | 84 | 57 | 40.8 |
| `template_multimodal` | 864 | 199 MB | 0.16 | 1 MB | 82 | 56 | 45.2 |
| `template_auto` | 402 | 241 MB | 0.19 | 108 MB | 92 | 70 | 22.5 |

**最优：`s3a_random`**（或 `template_multimodal` 若更在乎废字节）。

TPC-H 22 条查询含大量后向 seek（先读 footer/index，再向前读列分片）。长流策略（`s3a_seq`）在前向 skip 中丢弃大量字节，读放大 3.31x。`s3a_prefetch` 延迟最低（8s）但浪费 673MB，不节省带宽。`s3a_random` 的 64KiB readahead 足以缓存相邻 col-chunk 的重叠访问，amp=0.16 且废字节仅 6MB，综合最优。`template_multimodal` remote bytes 仅 199MB、废字节更低（1MB），若以带宽成本为第一目标可作首选。

#### ML taxi epoch_scan（多 epoch 块级重复）

| 策略 | GETs | remote | amp | waste | hit% | p99 ms | lat_sum s |
|---|---:|---:|---:|---:|---:|---:|---:|
| `aws_range_get` | 659 | 1,015 MB | 1.00 | 0 | 0 | 94 | 43.1 |
| `s3a_seq` | 92 | 1,188 MB | 1.17 | 174 MB | 0 | 66 | 16.5 |
| `s3a_random` | 490 | 764 MB | 0.75 | 1 MB | 26 | 93 | 32.1 |
| `s3a_prefetch` | 305 | 2,160 MB | 2.13 | 1,717 MB | 72 | 130 | 11.0 |
| **template_locality** ✓ | **310** | **253 MB** | **0.25** | **22 MB** | **53** | 93 | **18.0** |
| `template_seq` | 366 | 1,035 MB | 1.02 | 314 MB | 45 | 93 | 28.6 |
| `template_small_random` | 474 | 791 MB | 0.78 | 28 MB | 28 | 94 | 31.6 |
| `template_auto` | 532 | 1,139 MB | 1.12 | 300 MB | 19 | 94 | 38.0 |

**最优：`template_locality`**。

NYC taxi 数据每文件约 100 万行/36 个巨大 row group，4 epoch 反复扫描，同一批 256KiB page 被重复访问。`template_locality` 在第二次命中时将页放大缓存，后续 epoch 直接命中，remote bytes 253MB（仅为 aws 的 25%）。`s3a_prefetch` 延迟虽更低（11s），但读放大 2.13x、废字节 1.7GB，带宽成本大。`s3a_seq` GET 最少（92），但该 trace 中 4 epoch 的 shuffle 会有后向 seek，seq 会产生回退代价。

#### Lance SIFT1M（向量检索，514MB 数据文件，工作集 > 预算）

| 策略 | GETs | remote | amp | waste | hit% | lat_sum s |
|---|---:|---:|---:|---:|---:|---:|
| `aws_range_get` | 181,224 | 9.9 GB | 1.00 | 0 | 0 | 9,162 |
| `s3a_seq` | 151,614 | 47.4 GB | 4.81 | 37.5 GB | 0 | 8,066 |
| `s3a_random` | 63,690 | 13.4 GB | 1.36 | 3.8 GB | 65 | 3,322 |
| **s3a_prefetch** ⚠ | 87,166 | **672 GB** | **68.14** | 671 GB | 79 | 4,908 |
| `template_seq` | 65,531 | 11.5 GB | 1.14 | 1.7 GB | 64 | 3,392 |
| `template_small_random` | 53,583 | 12.8 GB | 1.30 | 3.3 GB | 70 | 2,811 |
| **template_locality** ✓ | **49,292** | 11.7 GB | 1.18 | 11.5 GB | **73** | **2,584** |
| `template_multimodal` | 53,612 | 12.8 GB | 1.29 | 3.2 GB | 70 | 2,811 |
| `template_auto` | 54,179 | 12.8 GB | 1.30 | 3.3 GB | 70 | 2,840 |

**最优：`template_locality`**（latency 和 GET count 均最低），但注意 waste 偏高（11.5GB）；若以带宽为第一目标则选 `template_seq`（remote=11.5GB，amp=1.14，waste 仅 1.7GB）。

⚠ `s3a_prefetch` 在此负载上灾难性失败：工作集 (514MB) > 缓存预算 (256MB)，8MiB 固定块在 512B 随机访问下被反复淘汰重取，产生 672GB 远端读、读放大 68x。

任何含缓存的策略在大工作集下性能上限由命中率决定；`template_locality` 通过频率感知减少无效大页读，GET 数最少故延迟最低。

#### Lance fmnist（向量检索，188MB 数据文件，工作集 < 预算）

| 策略 | GETs | remote | amp | waste | hit% | lat_sum s |
|---|---:|---:|---:|---:|---:|---:|
| `aws_range_get` | 119,127 | 4.0 GB | 1.00 | 0 | 0 | 5,997 |
| `s3a_seq` | 102,504 | 52.0 GB | 13.13 | 49.2 GB | 0 | 5,657 |
| `s3a_random` | 16,279 | 1.2 GB | 0.30 | 0.97 GB | 86 | 826 |
| **s3a_prefetch** ✓ | **26** | **182 MB** | **0.04** | **78 MB** | **99.7** | **1.4** |
| `template_seq` | 24,348 | 482 MB | 0.12 | 227 MB | 80 | 1,222 |
| `template_small_random` | 7,114 | 778 MB | 0.19 | 575 MB | 94 | 364 |
| `template_locality` | 3,583 | 760 MB | 0.19 | 674 MB | 97 | 187 |

**最优：`s3a_prefetch`**，且优势极大（GETs=26, lat_sum=1.4s vs 次优 template_locality 的 187s）。

与 SIFT1M 对比，fmnist 数据文件仅 188MB，小于 256MiB 预算，整个数据文件只需约 24 个 8MiB 块即可缓存完毕。首轮预取结束后，剩余 11.9 万次逻辑读几乎全部命中缓存（hit=99.7%），延迟接近零。这直接证明"工作集 vs 预算"是 `s3a_prefetch` 效果的决定性因素。

#### ML embedding_gather（行级随机，67MB 工作集 ≪ 预算）

| 策略 | GETs | remote | amp | hit% | lat_sum s |
|---|---:|---:|---:|---:|---:|
| `aws_range_get` | 180,964 | 66.7 MB | 1.00 | 0 | 9,049 |
| `s3a_seq` | 39,162 | 9,511 MB | **142.67** | 0 | 2,053 |
| `s3a_random` | 19 | 1.3 MB | 0.02 | 100 | 1.0 |
| **s3a_prefetch** ✓ | **1** | **0.9 MB** | **0.01** | **100** | **0.1** |
| `template_seq` | 4 | 1.1 MB | 0.02 | 100 | 0.2 |
| `template_small_random` | 13 | 1.0 MB | 0.01 | 100 | 0.7 |
| `template_locality` | 7 | 1.1 MB | 0.02 | 100 | 0.4 |

**最优：`s3a_prefetch`**（仅 1 次 GET，lat_sum=0.1s）。但几乎所有缓存策略均达到 100% 命中率，属于"小工作集全装入缓存"场景，策略差异退化为 GET 次数之争。

⚠ `s3a_seq` 灾难失败（amp=142.67）：每次 0.4KB 随机访问触发 128MiB 流 + 前向 skip，把中间所有字节都当作已传输开销。

## 3. 跨负载策略横向评价

### 3.1 策略稳健性排序

按"在哪些负载上不会产生读放大 ≥ 2x"评估：

| 策略 | 无严重读放大的负载数（共 6 类） | 最差 amp | 总体评价 |
|---|---:|---:|---|
| `s3a_random` | 6/6 | 1.36 (Lance-SIFT1M) | 最稳健的 baseline；任何负载均可接受 |
| `s3a_normal` | 6/6 | 1.36 | 与 random 几乎相同，后向 seek 切换意义有限 |
| `template_multimodal` | 5/6 | 4.28 (TPC-H) | 稳健；TPC-H 顺序段误判 |
| `template_small_random` | 5/6 | 1.30 (Lance) | 稳健；小页合并对大顺序 chunk 无优化 |
| `template_locality` | 5/6 | 1.18 (Lance-SIFT1M) | 稳健；大工作集下 waste 偏高 |
| `aws_range_get` | 6/6 | 1.00 | 精确但 RTT 全暴露；是待优化对象而非解法 |
| `template_auto` | 4/6 | 1.42 (多模态) | 边界误判；需混合 trace 进一步调参 |
| `template_seq` | 3/6 | 4.28 (多模态) | 顺序场景好；随机退化明显 |
| `s3a_seq` | 2/6 | 142.67 (emb) | 危险；随机负载上不可用 |
| `s3a_prefetch` | 2/6 | 94.63 (多模态) | 工作集敏感；小文件极佳，大文件灾难 |

### 3.2 "单负载最优"汇总与规则模板的上限

| 负载 | 最优策略 | 相比 aws_range_get 的 lat_sum 倍率 |
|---|---|---:|
| TPC-H 分析 | `s3a_random` | 6.0x 加速 |
| ML epoch_scan | `template_locality` | 2.4x 加速 |
| Lance SIFT1M | `template_locality` | 3.5x 加速 |
| Lance fmnist | `s3a_prefetch` | 4,283x 加速 |
| ML embedding | `s3a_prefetch` | 90,490x 加速 |
| 多模态检索 | `template_multimodal` | 1.6x 加速 |

> 注：lat_sum 的绝对值受模型假设影响（cache hit=0延迟），倍率仅作趋势参考。

**关键发现**：在每种单一负载上，都存在一种规则策略能接近或达到静态最优。规则模板在这里的"上限"已经相当高——对于有明确访问规律的负载（小 embedding 表、顺序扫描 epoch），规则的效果远超"合理"预期。

## 4. 核心结论与对下一步的启示

### 4.1 固定 8MiB prefetch 的致命缺陷

`s3a_prefetch` 的 amp 在 6 条 trace 上跨越 5 个数量级（0.04x 到 94.63x），决定因素只有一个：**工作集大小 vs 缓存预算**。

- fmnist（188MB < 256MB）：整个数据文件被 24 个块覆盖，缓存后全命中 → amp=0.04。
- SIFT1M（514MB > 256MB）：32 个块无法同时驻留，随机访问不断驱逐未复用块 → amp=68。

这印证了 §3.3 的分析："固定块大小同时承担远端请求粒度和缓存粒度，两者目标冲突。"

### 4.2 单负载规则已够用，在线学习需要混合负载来证明价值

从单负载最优表格可以看出：
- TPC-H → `s3a_random`（或 `template_multimodal`）
- epoch_scan → `template_locality`
- Lance 大文件 → `template_locality`（退化优雅，不灾难失败）
- Lance 小文件 / embedding → `s3a_prefetch`（自动工作集感知会更好）
- 多模态 → `template_multimodal`

**如果允许手动选策略**，规则模板已经接近最优。`template_auto` 的状态机在单一负载上已经大致正确，但在 taxi/多模态边界有 1.12x/1.42x 的小额误判。

**bandit 的价值点**：
1. **负载切换时的快速收敛**（当前 template_auto 有误判滞留期）
2. **工作集感知**（自动识别 fmnist 类 vs SIFT1M 类，切换 prefetch vs small_random）
3. **混合 trace 中的全程最优**（不需要人工选策略）

### 4.3 下一步：混合 trace 实验

按 §17.6 构造 mixed trace：

```
TPC-H → Lance-SIFT1M → ML-epoch_scan → ML-emb → 多模态 → TPC-H
```

重点观测：
1. `template_auto` 切换后的收敛时间与误判期损失；
2. 与"per-workload best static"的综合指标差距；
3. LinUCB（action = 策略选择，context = req_size_p50 / sequentiality / hit_rate / file_size_proxy）是否能在混合 trace 上持续优于 template_auto。

这是 **M3 bandit 立项判据**的核心实验。
